# ユーザーストーリーの要否の判断（User Stories Assessment）

## 判断

**Execute（作る）**

## 理由

- 利用者が使う画面と LINE のトークの操作が中心のアプリで、利用者が 2 種類いる（母親＝管理者、子供）（`inception/requirements-analysis/requirements.md` の用語）
- 担当の状態の移り変わり（FR6.1）、確定と確定の取り消し（FR6.5）、代わりにやる（FR7）など、だれが何をできるかで結果が変わる決まりが多い
- 進め方は BDD で、機能ごとに Given/When/Then の筋書きを先に書く（`inception/practices-discovery/team-practices.md`）。ストーリーと受け入れ条件が、そのまま筋書きのもとになる

## 考えたこと

| 観点 | 内容 |
|------|------|
| プロジェクトの種類 | 新しく作るアプリ（既存のコードはない） |
| 利用者が触る範囲 | アプリの画面（スマホとパソコン）、LINE の 1 対 1 のトーク、家族のグループのトーク |
| 複雑さ | 状態の移り変わり、確定、担当の上書き、代わりにやる、無料枠を守るお知らせの数 |

## ストーリーが特に役に立つところ

- 母親と子供で、できる操作とできない操作を分けて確かめるところ（FR1.7、FR5.7、FR6.6）
- 記録・修正・確定の組み合わせで、お小遣いの金額が正しくなるところ（FR6、FR8）
- LINE のトークでの操作（記録の返事、代わりにやる、お知らせ）を、画面の操作と同じ決まりで扱うところ（FR5、FR7、FR9）
