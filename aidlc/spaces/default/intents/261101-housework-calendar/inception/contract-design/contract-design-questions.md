# 契約の設計 — 質問

作業単位（`inception/units-generation/unit-of-work.md`）と部品（`inception/domain-design/components.md`）のあいだで、どんなデータを、どんな形で、どうやってやりとりし、うまくいかないときにどうするかを決めます。この決まりを「契約」と呼びます。

すでに決まっていること（もう一度は聞きません）:

- 裏側の部品どうしは、同じコードの中で、部品ごとに決めた関数の窓口を通して呼ぶ（作業単位の分割の Q6）
- 画面と裏側で共有する型の置き場所は U1 の中に作る（作業単位の分割の Q9）
- 裏側の入口は Lambda を 3 つ（画面用、LINE 用、お知らせ用）に分ける（作業単位の分割の Q5）

そのため、ここで決める契約は次のものです。

| 境目 | 中身 |
|------|------|
| 画面 → 画面用の入口 | 画面が裏側を呼ぶ API |
| LINE → LINE 用の入口 | LINE から届く友だち登録・グループへの参加・トーク・ボタン（Webhook） |
| 裏側 → LINE | 返事とお知らせを送る（Messaging API）、ログインの確かめ（LINE ログイン） |
| 決まった時刻の仕組み → お知らせ用の入口 | 16 時と月末 21 時に動かす |
| 部品 → 部品 | 同じコードの中の関数の窓口（家族とメンバー、お手伝いの種類、カレンダー、お小遣い、お知らせ） |

## Q1. [アーキテクト] 画面と裏側の API の形

画面（React）が裏側（画面用の Lambda）を呼ぶときの形です。この形が、画面と裏側の契約の書き方（OpenAPI など）を決めます。

A. 操作ごとに URL を分ける REST の形（JSON を HTTPS で送る）。契約は OpenAPI で書く
B. GraphQL の形。1 つの URL で、画面が必要なデータを選んで取る
C. 関数を呼ぶような RPC の形。共有する型から画面と裏側の呼び出しを作る（tRPC など）
X. Other (please specify)

[Answer]: A

## Q2. [アーキテクト] 部品の窓口の失敗の返し方

裏側の部品の関数の窓口が、断るとき（例: 「この月は確定済みです」、子供による管理者の操作）や失敗したときに、呼んだ側にどう伝えるかです。すべての部品の窓口で同じ決まりにします。

A. 成功か失敗かを結果の値として返す（失敗には決まった種類の印を付ける）。呼んだ側は必ず両方を扱う
B. 決まった種類のエラーを投げる。呼んだ側は必要なときだけ受け止める
C. 断る場合（業務の決まり）は結果の値で返し、思いがけない失敗（データベースにつながらないなど）はエラーを投げる
X. Other (please specify)

[Answer]: C

## Q3. [アーキテクト] 利用者に見せる文言をどこが持つか

要件には「この月は確定済みです」「今日記録できる担当はありません」など、利用者に見せる文言が決まっています。画面と LINE の返事の両方に出るものもあります（例: 「この月は確定済みです」は、画面での記録（FR5.5）と LINE での記録（FR5.4）の両方）。

A. 裏側の部品は断った理由の印（例: `MONTH_CONFIRMED`）だけを返し、文言は画面と LINE のトークの受け口がそれぞれ持つ
B. 裏側の部品が文言も返し、画面と LINE のトークの受け口はそのまま表示する
C. 文言の一覧を共有する型の置き場所に 1 つだけ置き、画面と LINE のトークの受け口の両方がそこから引く（部品は理由の印だけを返す）
X. Other (please specify)

[Answer]: C

## Q4. [アーキテクト] 契約の変え方（バージョン）

作るのも手入れするのも 1 人で、画面と裏側は同じリポジトリから同時に配備します（`team.md`）。ただし、LINE の中で開いたままの古い画面が、新しい裏側を呼ぶことはあります。

A. バージョン番号は付けない。項目を足すのは自由（知らない項目は無視する）で、項目を消す・意味を変えるときは同じ変更の中で画面と裏側を両方直して同時に配備する
B. API の URL にバージョンを付け（`/v1/...`）、壊す変更のときは新しいバージョンを足して、古いほうをしばらく残す
X. Other (please specify)

[Answer]: B

## Q5. [アーキテクト] LINE から二重に届いたときの扱い

LINE は、届けられなかったと判断した Webhook を送り直すことがあります。また、子供がボタンを短い間に 2 回押すこともあります（FR5.3 の「記録は 1 件のまま」、FR7.3 の「最初に押した 1 人だけ」）。

A. 届いたイベントの ID を記録しておき、同じ ID は二度処理しない。それに加えて、記録や引き受けなどの操作そのものも、何度やっても結果が同じになる作りにする
B. 操作そのものを何度やっても結果が同じになる作りにするだけで、イベントの ID は記録しない
C. イベントの ID を記録して二度処理しないだけにする
X. Other (please specify)

[Answer]: A

## Q6. [アーキテクト] 日付・時刻・金額の表し方

契約の中の日付・時刻・金額の書き方です。日付の区切りと時刻は日本時間で扱います（NFR11）。金額は円の整数です（FR8.3）。

A. 担当の日付は日本時間の `YYYY-MM-DD`、記録した時刻などは UTC の ISO 8601（例: `2027-01-07T11:00:00Z`）で持ち、表示するときに日本時間にする。金額は円の整数
B. 日付も時刻も日本時間で持つ（時刻は `+09:00` 付きの ISO 8601）。金額は円の整数
X. Other (please specify)

[Answer]: A

## Q7. [アーキテクト] 決まった時刻の仕組みからお知らせを動かすときに渡すもの

16 時のリマインドと月末 21 時のまとめは、決まった時刻の仕組みがお知らせ用の Lambda を動かします。やり直しで同じお知らせを二重に送らないこと（FR9.5）にも関わります。

A. 「どのお知らせか（リマインドかまとめか）」と「どの日の分か（日本時間の日付）」を渡す。お知らせ用の Lambda は、その組み合わせで送ったかどうかを確かめる
B. 何も渡さず、お知らせ用の Lambda が動いた時刻から、どのお知らせかとどの日の分かを決める

[Answer]: A

## Q8. [セキュリティ] 画面から裏側へ、誰が使っているかを伝える方法

すべての要求で、LINE の認証の結果を確かめます（NFR4）。画面（LINE の中で開く画面と、パソコンのブラウザ）から裏側に、利用者が誰かをどう伝えますか。

A. LINE の画面の仕組み（LIFF）から受け取った ID トークンを、要求のたびにヘッダー（`Authorization: Bearer`）で送り、裏側が毎回 LINE の決まりで確かめる
B. 最初に ID トークンを裏側で確かめ、裏側が自分のセッション（Cookie など）を発行して、以後はそれで確かめる
C. LIFF のアクセストークンを送り、裏側が LINE に問い合わせて利用者を確かめる
X. Other (please specify)

[Answer]: B

## Q9. [セキュリティ] 裏側が発行するセッションの渡し方

Q8 で「最初に ID トークンを裏側で確かめ、裏側が自分のセッションを発行する」を選んでいただきました。発行したセッションを、画面がどう持って裏側に送るかで、画面と裏側の API の契約（OpenAPI の認証の書き方）が変わります。画面は LINE の中とパソコンのブラウザの両方で開きます（FR1.6）。

A. 裏側が HttpOnly の Cookie でセッションを渡す。画面と API を同じドメイン（例: 画面の配信の下に `/api` を置く）にして、Cookie が自動で送られるようにする。画面のスクリプトからはセッションを読めない
B. 裏側が署名付きのセッショントークンを返し、画面がそれを持って、要求のたびにヘッダー（`Authorization: Bearer`）で送る
X. Other (please specify)

[Answer]: B
