# 設計の決定の記録（ドメイン設計）

部品の分け方（`components.md`）で決めたことを、決定ごとに残します。

## ADR-001 部品を 7 つに分け、頼り方を一方向にする

### Context

要件は FR1〜FR9 のまとまりに分かれていて、入口は 3 つあります（画面、LINE のトーク、決まった時刻のお知らせ）。作るのも手入れするのも 1 人なので、どこを直せばよいかがすぐ分かる分け方が必要です。walking skeleton を最初に作るため、下から順に作って確かめられる形にしたいです。

### Decision

家族とメンバー、お手伝いの種類、カレンダー（担当と記録）、お小遣い、お知らせ、LINE のトークの受け口、画面、の 7 つに分けます。頼り方は一方向で、輪を作りません。データは持ち主の部品だけが書きます。（まとめの確認で承認）

### Consequences

- 下の部品（家族とメンバー → お手伝いの種類 → カレンダー → お小遣い）から順に作って確かめられる
- 入口の 3 つ（画面、LINE のトークの受け口、お知らせ）は、データを持たない、または送った記録だけを持つ
- 部品の数が多めなので、部品どうしのやりとりの決まり（契約）を次の段階で決める必要がある

### Alternatives Rejected

- 裏側を 1 つの部品にまとめる: データの持ち主があいまいになり、確定の決まりを守る場所がはっきりしない
- 画面ごとに部品を分ける: 同じデータを複数の部品が書くことになり、FR6.1 の状態の表を何か所でも守る必要が出る

## ADR-002 「月の確定」と「代わりにやる」をカレンダーに持たせる

### Context

月の確定（FR6.5）は担当・記録・状態・割り当て・加算・減額のすべての変更を止めます。代わりにやる（FR7）は担当の子供を変え、担当の状態・確定・管理者の変更で自動でなくなります（FR7.5）。

### Decision

どちらも「カレンダー（担当と記録）」に持たせます。お小遣いは、加算・減額を受け付ける前に、月が確定しているかをカレンダーに問い合わせます。[Q1: A]

### Consequences

- 担当を変える決まりが 1 か所に集まり、FR6.1 の状態の表と FR6.5 の確定の決まりを 1 つの部品で確かめられる
- カレンダーが大きめの部品になる。作業単位の分割で、さらに分けるかを見る

### Alternatives Rejected

- 確定をお小遣いに持たせる [Q1: B]: カレンダーがお小遣いに頼ることになり、頼り方が輪になる
- 代わりにやるを独立した部品にする [Q1: C]: 担当を変える決まりが 2 か所に散らばる

## ADR-003 記録のときに単価を担当に書き写す

### Context

単価を変えると、変えたあとに付いた記録から新しい単価を使います（FR2.2）。管理者が「済にする」ときは、操作した時点の単価を使います（FR6.3）。

### Decision

記録するとき（子供の記録、管理者の「済にする」）に、お手伝いの種類から今の単価を受け取り、担当に書き写します。お手伝いの種類は今の単価だけを持ちます。[Q2: A]

### Consequences

- お小遣いの計算は担当を読むだけで済む
- 取り消して記録し直すと、その時点の単価になる。これは FR2.2 と FR6.3 の決まりどおり
- 単価の変更の歴史は残らない。必要になったら別に足す

### Alternatives Rejected

- お手伝いの種類が単価の歴史を持ち、計算のときに記録の時刻で探す [Q2: B]: 計算のたびに探す必要があり、記録の時刻と単価の変更の時刻が近いと間違えやすい

## ADR-004 LINE のトークの受け口を独立させる

### Context

リッチメニューの記録（FR5.1）、代わりにやる（FR7）、友だち登録とお知らせ先の登録（FR1.1、FR1.5）は、どれも LINE から届きます。LINE から届いたことを確かめる必要があります（NFR4）。

### Decision

「LINE のトークの受け口」を独立した部品にし、届いたものを確かめて読み解き、家族とメンバーかカレンダーに渡して、返事を返します。データは持ちません。[Q3: A]

### Consequences

- LINE の決まりが変わっても、直すのは 1 か所で済む
- カレンダーや家族とメンバーは、画面から呼ばれても LINE から呼ばれても、同じ操作として扱える
- 返事の文言（記録しました、確定済みです など）はこの部品が持つ

### Alternatives Rejected

- それぞれの部品が LINE の受け取りを直接持つ [Q3: B]: LINE から届いたかの確かめが何か所にも散らばり、漏れやすい

## ADR-005 お小遣いの額は読むたびに計算し、保存しない

### Context

お小遣いの額は、記録・取り消し・状態の変更・加算・減額・確定の取り消しのたびに変わります（FR5.8、FR8.1）。月末のまとめのあとも、確定していなければ変わり、アプリには常に最新の額を出します（FR9.3）。

### Decision

お小遣いの部品が、画面を開いたときと月末のまとめのときに、担当（済のもの、書き写した単価）と加算・減額から計算します。合計は保存しません。[Q4: A]

### Consequences

- 額がずれることがない
- 家族 4 人で 1 か月分の担当は多くても数百件で、読むたびの計算でも 3 秒以内（NFR7）に収まる見込み [assumption]
- 人数が大きく増えたら見直す

### Alternatives Rejected

- 変わるたびに合計を計算し直して保存する [Q4: B]: 直し忘れでずれる恐れがあり、この量では速さの利点が小さい
