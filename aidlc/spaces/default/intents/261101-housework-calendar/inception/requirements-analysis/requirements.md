# 要件（Requirements）

最初の版で作るお手伝いカレンダーの要件です。もとにしたのは次の書類と回答です。

- 「意図の整理」（`ideation/intent-capture/intent-statement.md`）
- 「範囲の定義」（`ideation/scope-definition/scope-document.md`、`intent-backlog.md`）
- 「ラフな画面イメージ」（`ideation/rough-mockups/wireframes.md`、`user-flow.md`）
- 「進め方」（`inception/practices-discovery/team-practices.md`）
- このステージの回答（`requirements-analysis-questions.md` の Q1〜Q11）
- 承認の確認のときの指示（2026-11-01）: 「いつでも確定できる。いつでも確定を取り消しできる。確定しなければいつまででも修正できる」「矛盾があれば正して。基本的にはあとの決断を優先してうまく回るように仕様を決める」。以下では「承認時の指示」と書きます

要件には `FR{n}` / `FR{n}.{m}` / `NFR{n}` の ID を振っています。この ID は、あとの段階でもそのまま使います。受け入れ条件は Given/When/Then の形で書きます（`team-practices.md` の BDD）。

## 決め方の原則

承認時の指示に従い、決定どうしが食い違うときは、あとの決定を優先します。この書類で置き換えた決定は次のとおりです。

| もとの決定 | あとの決定（この書類で採用） |
|------------|------------------------------|
| 子供があとから記録できるのは同じ月の中、月末のまとめを送るまで（Q3） | 確定していない月なら、月をまたいでも記録できる（Q11、承認時の指示） |
| 月末のまとめを送ったあとも修正できる（Q8） | そのまま採用。修正できるかどうかは確定しているかだけで決まる（Q11、承認時の指示） |
| 子供同士で枠を交換する（`scope-document.md`） | 交換ではなく「代わりにやる」だけにする（Q4） |
| 子供が記録したことをグループに知らせる（`intent-statement.md`） | グループには知らせない（`wireframes.md` の Q8） |

上の原則に沿って、この書類のなかで作り手が決めた点には「（承認時の指示による決定）」と付けています。

## 用語

| 用語 | 意味 |
|------|------|
| 家族 | アプリを一緒に使う人のまとまり。管理者 1 人と、子供のメンバーからなる |
| 管理者 | 家族を作った人。この家族では母親 |
| 子供 | 招待を受けて家族に参加したメンバー |
| 担当 | 「ある日の、あるお手伝いを、ある子供がやる」という 1 件の割り当て |
| 担当の状態 | 「未」「済」「×（やらなかった）」のどれか（FR6.1） |
| 記録 | 担当を「済」にしたこと。記録した時刻、記録した人、その時点の単価を持つ |
| 確定 | 管理者が月ごとに行う操作。確定している月は誰も変更できない。取り消すとまた変更できる |
| お知らせ先 | 公式アカウントがお知らせを送る、家族のグループ LINE |
| 公式アカウント | このアプリ用の LINE 公式アカウント。1 対 1 のトークと家族のグループのトークで使う |

## Intent Analysis（目的の整理）

- 母親がお手伝いの回数を数え、お小遣いを計算する手間をなくす（intent-statement）
- 子供が自分で実施結果を記録し、母親は確認するだけで済むようにする（intent-statement の成功の目安）
- 月初に 1 か月分の割り当てを作れて、月末にお小遣い額が自動で計算される状態にする（intent-statement の成功の目安）
- 記録した時刻を残し、取り掛かる時間の現状を把握する。時刻の改善を成功の目安にするのは、あとの版から（intent-statement）
- 運用の費用は毎月 0 円とし、家族 4 人（母親と子供 3 人）で使う（`ideation/feasibility/constraint-register.md`、`ideation/feasibility/feasibility-questions.md` の Q9）

## Functional Requirements（機能の要件）

### FR1. 家族とメンバー

- **FR1.1** 利用者が公式アカウントを友だち登録したとき、システムはその利用者の LINE のユーザー ID と表示名を記録する。（Q1）
  - Given まだ記録されていない利用者がいる / When その人が公式アカウントを友だち登録する / Then その人のユーザー ID と表示名が記録される
  - Given すでに記録されている利用者がいる / When その人がいったんブロックしてから友だち登録し直す / Then 記録は重複せず、同じ人として扱われる
- **FR1.2** 記録された利用者がまだどの家族にも入っていないとき、システムは「家族を作る」か「家族からの招待を待つ」を選べるようにする。（Q1）
  - Given どの家族にも入っていない利用者がいる / When アプリを開く / Then 「家族を作る」と「招待を待つ」が表示される
- **FR1.3** 「家族を作る」を選んだ利用者は、その家族の管理者になる。（Q1）
  - Given どの家族にも入っていない利用者がいる / When 「家族を作る」を選ぶ / Then 新しい家族ができ、その人が管理者になる
  - Given すでに家族に入っている利用者がいる / When 「家族を作る」をもう一度実行しようとする / Then 2 つ目の家族は作られず、「すでに家族に入っています」と表示される
- **FR1.4** 管理者は招待用のリンクを作れる。リンクから参加した利用者は、その家族の子供になる。（Q1）
  - Given 管理者がいる / When 招待用のリンクを作る / Then そのリンクが表示され、LINE で送れる
  - Given 招待を待っている利用者がいる / When 招待用のリンクを開いて参加する / Then その人がその家族の子供になる
  - Given すでにほかの家族に入っている利用者がいる / When 招待用のリンクを開く / Then 参加せず、「すでに別の家族に入っています」と表示される
  - Given 招待用のリンクが無効になっている / When 開く / Then 参加せず、「この招待は使えません。管理者に新しい招待を頼んでください」と表示される
- **FR1.5** 管理者は、公式アカウントを家族のグループ LINE に招待し、そのグループをお知らせ先として登録できる。お知らせ先は 1 家族に 1 つで、登録し直すと新しいグループに置き換わる。（`scope-document.md`、Q1、承認時の指示による決定）
  - Given 管理者が公式アカウントをグループに招待した / When 管理者がそのグループをお知らせ先として登録する / Then FR9 のお知らせがそのグループに届き、FR7 の申し出がそのグループでできる
  - Given すでにお知らせ先がある / When 管理者が別のグループを登録する / Then お知らせ先は新しいグループに置き換わり、前のグループにはお知らせが届かなくなる
  - Given 子供がいる / When お知らせ先を登録しようとする / Then 登録できず、「お知らせ先を登録できるのは管理者だけです」と返事する
  - Given お知らせ先がまだ登録されていない / When 16 時や月末 21 時になる / Then 何も送らず、管理者がアプリを開くと「お知らせ先のグループが登録されていません」と表示される
  - Given 公式アカウントが、お知らせ先として登録されていないグループで話しかけられた / When 子供が FR7 の申し出をしようとする / Then 申し出は受け付けず、「このグループは家族のお知らせ先として登録されていません」と返事する
- **FR1.6** アプリの画面は、LINE の認証で利用者を見分ける。スマホでは LINE の中で開き、パソコンではブラウザで LINE にログインして開ける。（intent-statement、`wireframes.md` の Q1）
  - Given 家族のメンバーがパソコンのブラウザでアプリを開く / When LINE にログインする / Then スマホと同じ家族のカレンダーが表示される
- **FR1.7** 家族のメンバーではない利用者は、どの家族の担当・記録・お小遣い額も見たり変えたりできない。（`constraint-register.md` の C-R1）
  - Given ある家族のメンバーではない利用者がいる / When その家族のカレンダーやお小遣いを開こうとする / Then 中身は表示されず、「このアプリは家族のメンバーだけが使えます」と表示される

### FR2. お手伝いの種類

- **FR2.1** 管理者は、お手伝いの種類ごとに名前・単価・説明を登録し、変更できる。（`scope-document.md`）
  - Given 管理者がいる / When 名前「皿洗い」、単価 100 円、説明を入れて保存する / Then 種類の一覧に「皿洗い 100 円」が出る
  - Given 管理者が単価に -1 や小数や空欄を入れる / When 保存しようとする / Then 保存されず、「単価は 0 円以上の整数で入力してください」と表示され、入力した内容は残る
  - Given 子供がいる / When 種類を登録・変更しようとする / Then できない
- **FR2.2** 単価を変更すると、変更したあとに付いた記録から新しい単価を使う。すでに付いている記録の金額は変わらない。（Q7）
  - Given 皿洗いの単価が 100 円で、記録が 3 回ある / When 単価を 120 円に変え、そのあと 1 回記録される / Then その月の皿洗いの金額は 100×3 + 120×1 = 420 円になる
- **FR2.3** 管理者は種類を「使わない」にできる。「使わない」の種類は、新しい割り当てでは選べない。過去の記録とお小遣いは残る。（Q7）
  - Given 皿洗いを「使わない」にした / When 月の割り当てを開く / Then 皿洗いは選べず、過去の皿洗いの記録とお小遣いはそのまま表示される
- **FR2.4** 割り当てに一度も使われていない種類だけは、管理者が完全に消せる。（Q7）
  - Given 割り当てに使われたことがある種類がある / When 消そうとする / Then 消せず、「使わない」にするよう案内される

### FR3. 月の割り当て

- **FR3.1** 管理者は、月とお手伝いの種類ごとに、担当の子供と曜日を選んで保存できる。保存すると、その月の日ごとの担当ができる。（`wireframes.md` の Q3）
  - Given 2027 年 1 月の割り当てで、皿洗いを太郎の月曜・木曜に選んだ / When 保存する / Then 1 月のすべての月曜と木曜に「皿洗い=太郎」の担当ができる
- **FR3.2** 管理者は、日ごとに担当の子供を変更できる。状態が「未」の担当だけが変更できる。（`wireframes.md` の Q3、承認時の指示による決定）
  - Given 1 月 20 日の皿洗いが太郎で「未」 / When 管理者が担当を花子に変える / Then 1 月 20 日の皿洗いの担当が花子になる
  - Given 1 月 5 日の皿洗いが「済」 / When 管理者が担当を変えようとする / Then 変更できず、「記録を取り消してから変更してください」と表示される
- **FR3.3** 月の割り当てを保存し直すと、明日以降の日で状態が「未」の担当だけを作り直す。今日と過ぎた日、「済」と「×」の担当は変えない。日ごとに変更した担当と、FR7 で引き受けた担当も、作り直した内容で上書きする。上書きされる担当があるときは、保存する前に、その日とお手伝いと担当の変化を一覧で示して確認する。（Q5、承認時の指示による決定）
  - Given 今日は 1 月 10 日で、1 月 5 日は「済」、1 月 20 日の担当を日ごとに変更していた / When 月の割り当てを保存し直す / Then 1 月 5 日と 1 月 10 日は変わらず、1 月 20 日は作り直した内容になる
  - Given 1 月 22 日の皿洗いを、FR7 で太郎が花子から引き受けていた / When 月の割り当てを保存し直す / Then 保存の前に「1月22日 皿洗い: 太郎 → 花子」が確認として表示され、確認すると作り直した内容になる
- **FR3.4** 同じ日の同じお手伝いに担当が 2 人入る割り当ては、保存できない。重なっている日とお手伝いを表示する。（Q6）
  - Given 皿洗いを太郎の月曜と花子の月曜に選んだ / When 保存しようとする / Then 保存されず、「1月4日(月) の皿洗いに担当が 2 人います」のように重なりがすべて表示される
- **FR3.5** 確定している月の割り当ては変更できない。（Q11、承認時の指示）
  - Given 1 月が確定している / When 管理者が 1 月の割り当てを保存し直す、または 1 月の日ごとの担当を変えようとする / Then 変更できず、「この月は確定済みです」と表示される

### FR4. カレンダーの表示

- **FR4.1** アプリを開くと、最初に今月のカレンダーを表示する。日ごとに、お手伝い・担当の子供・状態を表示する。状態は「済」「未」「×（やらなかった）」の文字でも表し、色だけに頼らない。確定している月には「確定済み」と表示する。（`wireframes.md` の Q2・Q7）
  - Given 1 月 2 日の皿洗いが「済」 / When カレンダーを開く / Then 1 月 2 日に「皿洗い=太郎(済)」と文字で表示される
- **FR4.2** 日付を選ぶと、その日の担当ごとに、状態・記録した時刻・記録した人を表示する。（intent-statement の記録時刻）
  - Given 太郎が 1 月 2 日 16:42 に皿洗いを記録した / When 1 月 2 日を開く / Then 「済 16:42 太郎が記録」と表示される
- **FR4.3** 子供を含む家族の全員が、家族全員の担当とお小遣い額を見られる。（`scope-document.md`）
  - Given 花子がいる / When カレンダーとお小遣いを開く / Then 太郎と次郎の担当とお小遣い額も表示される
- **FR4.4** 割り当てがない月を開くと、「この月の割り当てはまだありません」と表示する。管理者には割り当ての画面へ進むボタンも表示する。（`wireframes.md`）
  - Given 2 月の割り当てがまだない / When 管理者が 2 月のカレンダーを開く / Then 「この月の割り当てはまだありません」と、割り当ての画面へ進むボタンが表示される
  - Given 2 月の割り当てがまだない / When 子供が 2 月のカレンダーを開く / Then 「この月の割り当てはまだありません」だけが表示され、割り当ての画面へ進むボタンは表示されない
- **FR4.5** 表示に失敗したときは、「表示できませんでした。もう一度お試しください」と表示し、読み込み直せるようにする。（`wireframes.md`）
  - Given 裏側の処理に一時的につながらない / When カレンダーを開く / Then 「表示できませんでした。もう一度お試しください」と「読み込み直す」ボタンが表示される
  - Given 失敗の表示が出ている / When つながるようになってから「読み込み直す」を押す / Then カレンダーが表示される

### FR5. 実施の記録（子供）

- **FR5.1** 子供は、公式アカウントとの 1 対 1 のトークのリッチメニューにある「やった」から、自分の今日の担当を選んで記録できる。記録した時刻を保存する。（`wireframes.md` の Q4・Q8）
  - Given 太郎に今日の担当「皿洗い」があり「未」 / When 「やった」をタップし、「皿洗い」を選ぶ / Then 皿洗いが「済」になり、記録した時刻が保存される
- **FR5.2** リッチメニューから記録すると、公式アカウントは記録した子供本人にだけ、返事として「皿洗いを記録しました（16:42）」のように知らせる。家族のグループには知らせない。（`wireframes.md` の Q8）
  - Given 太郎が 16:42 にリッチメニューから皿洗いを記録した / When 記録が終わる / Then 太郎との 1 対 1 のトークに「皿洗いを記録しました（16:42）」と返事が届き、お知らせ先のグループには何も届かない
- **FR5.3** 「済」と「×」の担当は選べないようにする。同じ担当が二重に記録されることはない。（`wireframes.md`）
  - Given 太郎の皿洗いがすでに「済」 / When 太郎が「やった」をタップする / Then 皿洗いは選べない状態で表示される
  - Given 太郎が同じ担当の記録ボタンを短い間に 2 回押した / When 2 回目が届く / Then 記録は 1 件のままになる
- **FR5.4** 今日の担当がない子供、または今日の担当がすべて「済」か「×」の子供が「やった」をタップすると、「今日記録できる担当はありません」と返事する。今月が確定しているときに「やった」をタップすると、「この月は確定済みです」と返事する。（`wireframes.md`、承認時の指示による決定）
  - Given 太郎に今日の担当がない / When 「やった」をタップする / Then 「今日記録できる担当はありません」と返事する
  - Given 今月が確定している / When 太郎が「やった」をタップする / Then 「この月は確定済みです」と返事し、記録はしない
- **FR5.5** 子供は、アプリの画面から、確定していない月の、今日までの自分の「未」の担当を記録できる。月をまたいでもよい。明日以降の担当は記録できない。画面から記録したときは、LINE では知らせない。（Q2・Q3・Q11、承認時の指示による決定）
  - Given 太郎が 1 月 5 日の皿洗いを記録し忘れ、1 月は確定していない / When 1 月 7 日にアプリから 1 月 5 日の皿洗いを記録する / Then 1 月 5 日の皿洗いが「済」になり、記録した時刻（1 月 7 日）が保存される。LINE のお知らせは送られない
  - Given 今日は 2 月 1 日で、1 月はまだ確定していない / When 太郎が 1 月 31 日の自分の担当を記録する / Then 記録できる
  - Given 1 月が確定している / When 太郎が 1 月の担当を記録しようとする / Then 記録できず、「この月は確定済みです」と表示される
  - Given 今日は 1 月 7 日 / When 太郎が 1 月 8 日の担当を記録しようとする / Then 記録できず、「まだ来ていない日の担当は記録できません」と表示される
- **FR5.6** 「×」の担当は、子供は記録も変更もできない。（Q2・Q3）
  - Given 1 月 5 日の太郎の皿洗いに、管理者が「×」を付けた / When 太郎がその担当を記録しようとする / Then 記録できず、「お母さんが『やらなかった』にしています」と表示される
- **FR5.7** 子供は、ほかの子供の担当を記録できない。（FR1.7 と同じ考え方）
  - Given 花子の担当がある / When 太郎がその担当を記録しようとする / Then 記録できない
- **FR5.8** 「済」の担当は、その時点でお小遣いの回数に数える。（`scope-document.md`）
  - Given 太郎の 1 月の皿洗い（100 円）の回数が 3 回 / When 太郎が皿洗いを 1 回記録する / Then すぐにお小遣いの画面で太郎の皿洗いが 4 回・400 円と表示される

### FR6. 担当の状態と、確認・修正・確定（管理者）

- **FR6.1** 担当の状態は「未」「済」「×」の 3 つで、次の操作だけで変わる。表にない変わり方はしない。（`scope-document.md`、Q2、承認時の指示による決定）

  | いまの状態 | 操作 | 操作できる人 | 次の状態 | 記録として残すもの |
  |------------|------|--------------|----------|--------------------|
  | 未 | 記録する（FR5.1、FR5.5） | 担当の子供 | 済 | 操作した時刻、記録した人（子供）、その時点の単価 |
  | 未 | 済にする（FR6.3） | 管理者 | 済 | 操作した時刻、記録した人（管理者）、その時点の単価 |
  | 未 | やらなかったにする（FR6.4） | 管理者 | × | なし |
  | 済 | 取り消す（FR6.2） | 管理者 | 未 | 記録を消す |
  | 済 | やらなかったにする（FR6.4） | 管理者 | × | 記録を消す |
  | × | やらなかったを外す（FR6.4） | 管理者 | 未 | なし |
  | × | 済にする（FR6.3） | 管理者 | 済 | 操作した時刻、記録した人（管理者）、その時点の単価 |

  - どの操作も、月が確定しているときはできない（FR6.5）
  - Given 太郎の 1 月 5 日の皿洗いが「済」 / When 管理者が「やらなかったにする」を選び、確認する / Then 状態が「×」になり、記録は消え、回数から外れる
- **FR6.2** 管理者は「済」の記録を取り消せる。取り消す前に、何が変わるか（お手伝い・子供・日付）を書いた確認を表示する。（`scope-document.md`）
  - Given 太郎の 1 月 5 日の皿洗いが「済」 / When 管理者が取り消しを選び、確認する / Then 状態が「未」になり、回数から外れる
- **FR6.3** 管理者は「未」または「×」の担当を「済にする」ことができる。記録した時刻には操作した時刻を残し、記録した人は管理者と表示し、単価は操作した時点のものを使う。（Q2、FR2.2、承認時の指示による決定）
  - Given 皿洗いの単価が 120 円で、太郎の 1 月 5 日の皿洗いが「未」 / When 管理者が 1 月 7 日 20:00 に「済にする」を選ぶ / Then 状態が「済」になり、「済 1/7 20:00 お母さんが記録」と表示され、120 円として数えられる
- **FR6.4** 管理者は「未」または「済」の担当を「やらなかったにする」ことができ、「×」を外して「未」に戻せる。どちらも、操作の前に確認を表示する。（`scope-document.md`、承認時の指示による決定）
  - Given 太郎の 1 月 5 日の皿洗いが「×」 / When 管理者が「やらなかったを外す」を選び、確認する / Then 状態が「未」に戻り、太郎がまた記録できるようになる
- **FR6.5** 管理者は、どの月でもいつでも確定でき、いつでも確定を取り消せる。確定している月は、担当・記録・状態・加算・減額・割り当てのすべてを、誰も変更できない。確定を取り消すと、また変更できる。確定していない月は、期限なくいつまでも変更できる。確定と取り消しの前には確認を表示する。月末のまとめ（FR9.2）は、確定していてもいなくても送る。（承認時の指示）
  - Given 1 月は確定していない / When 管理者が 1 月 20 日に 1 月を確定する / Then 1 月のお小遣い額が確定済みとして表示され、それ以降の 1 月の記録・取り消し・加算・減額・割り当ての変更はすべて断られる
  - Given 1 月が確定している / When 管理者が確定を取り消す / Then 「確定済み」の表示が消え、また 1 月の記録と修正ができる
  - Given 2026 年 12 月を確定しないまま 2027 年 3 月になった / When 太郎が 12 月 28 日の自分の「未」の担当を記録する / Then 記録できる
  - Given 子供がいる / When 確定や確定の取り消しをしようとする / Then できない
- **FR6.6** 子供は、FR6.2〜FR6.5 の操作ができない。
  - Given 太郎がいる / When 自分の「済」の記録を取り消そうとする / Then できない

### FR7. 代わりにやる（子供同士）

- **FR7.1** 子供はお知らせ先のグループのトークで、確定していない月の、自分の今日以降の「未」の担当を「代わってほしい」と申し出られる。公式アカウントは返事として、申し出られる担当をボタンで示す。確定している月の担当はボタンに出さない。今月が確定していて申し出られる担当がないときは、記録しようとしたときと同じく「この月は確定済みです」と返事する。（Q4、`wireframes.md` の Q5、承認時の指示）
  - Given 花子に 1 月 8 日の皿洗い（未）がある / When 花子がグループで「家事交代」と送る / Then 返事として「1/8 皿洗い」のボタンが表示される
  - Given 1 月が確定していて、花子の今日以降の担当は 1 月にしかない / When 花子がグループで「家事交代」と送る / Then 返事として「この月は確定済みです」と表示され、ボタンは出ない
  - Given 花子に今日以降の「未」の担当がなく、今月は確定していない / When 花子がグループで「家事交代」と送る / Then 「申し出られる担当はありません」と返事する
- **FR7.2** 子供が担当を選ぶと、公式アカウントは返事として、グループに申し出を知らせ、「引き受ける」と「申し出をやめる」のボタンを出す。（Q4、`wireframes.md` の Q5、承認時の指示による決定）
  - Given 花子が「家事交代」の返事のボタンから「1/8 皿洗い」を選んだ / When 選ぶ / Then グループに返事として「花子が 1月8日 の皿洗いを代わってくれる人を探しています」と、「引き受ける」「申し出をやめる」のボタンが表示される
- **FR7.3** 申し出た子供以外の子供が「引き受ける」を押すと、その担当は押した子供のものになる。押した子供の自分の担当は動かない。最初に押した 1 人だけが成立する。（Q4）
  - Given 花子が 1 月 8 日の皿洗いを申し出た / When 太郎が「引き受ける」を押す / Then 1 月 8 日の皿洗いの担当が太郎になり、「太郎が 1月8日 の皿洗いを引き受けました」と返事が届く
  - Given 太郎がすでに引き受けた / When 次郎があとから「引き受ける」を押す / Then 担当は変わらず、「この申し出はもう引き受けられています」と返事する
  - Given 申し出た花子本人か管理者が「引き受ける」を押す / When 押す / Then 担当は変わらず、「この申し出には応えられません」と返事する
- **FR7.4** 申し出た子供は、引き受けられる前なら「申し出をやめる」で取り下げられる。（承認時の指示による決定）
  - Given 花子の申し出がまだ引き受けられていない / When 花子が「申し出をやめる」を押す / Then 申し出がなくなり、そのあと誰かが「引き受ける」を押しても「この申し出はもうありません」と返事する
- **FR7.5** 1 つの担当に出せる申し出は 1 つだけ。次のどれかになると、申し出は自動でなくなる: 担当の日が過ぎた、担当の状態が「未」でなくなった、管理者が担当を変更した（FR3.2・FR3.3）、その月が確定された。なくなった申し出の「引き受ける」を押すと「この申し出はもうありません」と返事する。（承認時の指示による決定）
  - Given 花子の 1 月 8 日の皿洗いにすでに申し出がある / When 花子がもう一度同じ担当を申し出る / Then 新しい申し出はできず、「この担当はもう申し出ています」と返事する
  - Given 花子の申し出がある / When 管理者が 1 月 8 日の皿洗いの担当を次郎に変える / Then 申し出はなくなる

### FR8. お小遣いの計算

- **FR8.1** システムは、子供ごと・月ごとに「記録が付いた時点の単価 × 回数」を種類ごとに合計し、そこに加算・減額を足して、内訳つきで表示する。（intent-statement、FR2.2）
  - Given 太郎の 1 月に、皿洗い 100 円が 8 回、風呂掃除 150 円が 4 回、減額 200 円がある / When お小遣いの画面を開く / Then 800 円・600 円・-200 円の内訳と、合計 1,200 円が表示される
  - Given 次郎の 1 月の記録がまだない / When お小遣いの画面を開く / Then 「今月の記録はまだありません（0 円）」と表示される
- **FR8.2** 管理者は、子供・加算か減額か・金額（1 円以上の整数）・理由（必須）を入れて、加算・減額を記録できる。（`scope-document.md` の IB-9。遅れた場合は最初の版から外してよい）
  - Given 管理者が理由を空欄にする / When 保存しようとする / Then 保存されず、「理由を入力してください」と表示され、入力した内容は残る
  - Given 管理者が太郎に「減額 200 円、理由: 片付けをしなかった」を入れる / When 保存する / Then 太郎のお小遣いの内訳に「-200 円（片付けをしなかった）」が加わる
- **FR8.3** 金額はすべて円の整数で扱う。合計が 0 円を下回る場合も、計算どおりのマイナスの金額をそのまま表示する。0 円にそろえることはしない。（承認時の指示による決定。家族で見て話し合えるよう、隠さずに出す）
  - Given 次郎の 1 月は記録 1 回 100 円と減額 300 円 / When お小遣いの画面を開く / Then 合計は -200 円と表示される

### FR9. お知らせ（お知らせ先のグループ）

- **FR9.1** 毎日 16 時に 1 回、その日の担当をお知らせ先に送る。同じ日のリマインドは 1 通だけにする。その日が含まれる月が確定しているときは送らない。（`scope-document.md`、`constraint-register.md` の C-T4、承認時の指示「確定したら16時のリマインドは送らない」）
  - Given 今日、家族の誰かに担当がある / When 16 時になる / Then その日の担当の一覧が 1 通届く
  - Given 今日、誰にも担当がない / When 16 時になる / Then 何も送らない
  - Given 今日の 16 時のリマインドはすでに送った / When 送信の処理がもう一度動く / Then 2 通目は送らない
  - Given 今月がすでに確定している / When 16 時になる / Then リマインドは送らない（承認時の指示）
  - Given 1 月 20 日に 1 月を確定し、1 月 25 日に確定を取り消した / When 1 月 26 日の 16 時になる / Then その日の担当があればリマインドを送る
- **FR9.2** 月の最後の日の 21 時に、各子供のその月のお小遣い額をお知らせ先に送る。1 か月に 1 通だけにする。（Q8）
  - Given 1 月 31 日 21 時になった / When まとめを送る / Then 「1月のお小遣い 太郎 1,200円 / 花子 900円 / 次郎 600円」が 1 通届く
- **FR9.3** 月末のまとめを送ったあとも、確定していなければ記録と修正ができる。アプリには常に最新の金額を表示する（届いた金額と違うことがある）。（Q8・Q11、承認時の指示）
  - Given 1 月のまとめを送ったあと、1 月は確定していない / When 管理者が 1 月 31 日の記録を取り消す / Then アプリの 1 月のお小遣い額は新しい金額になる。まとめは送り直さない
- **FR9.4** 返事ではないお知らせは、FR9.1 と FR9.2 だけにする。（`constraint-register.md` の C-T4）
  - Given 1 か月がたった / When その月に送った返事ではないお知らせを数える / Then 最大で 31 通（リマインド）+ 1 通（まとめ）になる
- **FR9.5** FR9.1 と FR9.2 の送信に失敗したときは、15 分以内に作り手に知らせが届く（NFR2）。失敗した送信を自動でやり直すときも、同じお知らせを二重に送らない。（承認時の指示による決定）
  - Given 16 時のリマインドの送信に失敗した / When 15 分たつ / Then 作り手に失敗の知らせが届いている

## Non-Functional Requirements（機能以外の要件）

- **NFR1 費用:** 毎月の運用費用は 0 円にする。AWS の無料枠と、LINE 公式アカウントの無料プランの範囲で動かす。本番のお知らせ先のグループは 4 人（母親と子供 3 人）を前提とし、返事ではないお知らせは月最大 32 回 × 4 人 = 128 通で、無料枠の月 200 通以内に収める。グループの人数が増えたときは見積もり直す。（`constraint-register.md` の C-F1、`ideation/feasibility/feasibility-assessment.md`）
  - 確かめ方: 本番の公式アカウントの月の送信数が 200 通を超えないこと、AWS の請求額が 0 円であること
- **NFR2 止まらないこと:** 稼働率の数値目標は置かない。メンテナンスのとき以外は止めない。裏側の処理でエラーが起きたとき、または決まった時刻のお知らせが送れなかったときは、15 分以内に作り手に知らせが届く。（Q9）
  - 確かめ方: ステージングでわざとエラーを起こし、15 分以内に作り手に知らせが届くこと
- **NFR3 構成:** 裏側は、常に動かしておくサーバーを持たない作り（フルサーバーレス）にする。（Q9）
  - 確かめ方: AWS CDK で作る構成に、常に動かしておく仮想サーバーやコンテナ（EC2、常時起動の ECS など）が含まれていないこと
- **NFR4 安全:** アプリの画面から裏側へのすべての要求で、LINE の認証の結果と、その利用者が家族のメンバーであること（管理者の操作では管理者であること）を確かめる。LINE から届くトークの操作は、LINE から届いたものであることを確かめる。（FR1.7、`constraint-register.md` の C-R1）
  - 確かめ方: 認証のない要求、ほかの家族のメンバーからの要求、子供による管理者の操作が、すべて断られること
- **NFR5 秘密の情報:** 鍵・トークン・パスワードなどはリポジトリに入れない。公開リポジトリのため、設定は環境ごとの安全な保管場所から読む。（`aidlc/spaces/default/memory/project.md` の決まり、`team-practices.md`）
  - 確かめ方: リポジトリに秘密の情報がないことを、取り込み前の CI で検査する
- **NFR6 データ:** 本番のデータを手で書き換えない。データを直すときは、アプリの操作（取り消し、状態の変更、確定の取り消しなど）か、手順やコードとして用意して通常の流れで反映する。（`project.md` の決まり）
  - 確かめ方: FR6.1 の表のすべての変わり方と、確定・確定の取り消しが、アプリの画面から行えること（データを直接書き換えなくても、間違いを直せること）
- **NFR7 速さ:** 画面の表示と、トークでの操作への返事は、95% が 3 秒以内に終わる。（承認時の指示による決定。家族 4 人で使う量を前提にした目安）
  - 確かめ方: ステージングで画面とトークの操作を各 20 回行い、19 回以上が 3 秒以内であること
- **NFR8 テスト:** 機能ごとに、先に Given/When/Then の筋書きを書き、それが通るように作る。行カバレッジは 80% 以上とし、`main` に取り込む前に GitHub Actions で自動テストを動かす。（`team-practices.md`）
- **NFR9 見やすさ:** 文字と背景の色の差は 4.5:1 以上、押す場所は 44×44 ピクセル以上にし、状態を色だけで伝えない。（`wireframes.md` の Q7）
- **NFR10 環境:** ステージングと本番の 2 つの環境を持つ。ステージングには、本番とは別の LINE 公式アカウントとチャネルを用意し、作り手だけのグループで確かめる。`main` に取り込むとステージングに自動で反映し、本番は作り手が確認してから反映する。（Q10、`team-practices.md`）
  - 確かめ方: `main` に取り込むとステージングだけが更新され、本番は変わらないこと。ステージングの公式アカウントからのお知らせが、本番のお知らせ先には届かないこと
- **NFR11 時刻:** 日付の区切り、16 時のリマインド、月末 21 時のまとめは、日本時間で扱う。[assumption: 家族は日本で使う]
  - 確かめ方: 日本時間の 23:59 と 0:00 に付けた記録が、別の日の記録として扱われること。リマインドが日本時間の 16 時に届くこと

## Constraints（制約）

- LINE から使うアプリとし、LINE の認証で利用者を見分ける（intent-statement）
- 画面は React、裏側は AWS Lambda 上の Node.js（TypeScript）で作る（intent-statement の依頼）
- 利用者の記録には DynamoDB を使う（Q1 の回答で指定）
- AWS への反映は AWS CDK（TypeScript）で行う（`team-practices.md`）
- 作るのも手入れするのも 1 人。不具合は気づいたときに対応する（`constraint-register.md` の C-O1）
- 2026 年 12 月の月初から使い始めることを目指す。間に合わない場合は、2027 年 1 月の月初から全部そろえて使い始める（`constraint-register.md` の C-O3）

## Assumptions（前提）

- [assumption] リッチメニューは家族のグループのトークには表示されず、公式アカウントとの 1 対 1 のトークにだけ表示される。そのため、リッチメニューからの記録は 1 対 1 のトークで行う（`wireframes.md`）
- [assumption] グループのトークで公式アカウントに話しかけた子供を、システムは見分けられる。LINE の説明で、グループのメッセージにも送った人のユーザー ID が含まれることを確認した（[LINE Developers: グループトーク](https://developers.line.biz/ja/docs/messaging-api/group-chats/)）
- [assumption] 1 つの LINE のユーザーが入れる家族は 1 つだけ
- [assumption] 1 つの家族の管理者は 1 人だけ（家族を作った人）
- [assumption] FR7 の申し出は、お知らせ先のグループに「家事交代」と送ると始まる（U8 の機能設計 Q1 で「代わって」から変更）（`wireframes.md` では「交換」としていたものを、Q4 に合わせて置き換えた）
- [assumption] 担当がない日には、16 時のリマインドを送らない。通数を抑えるため
- [assumption] NFR11 の日本時間は、上に書いたとおり

## Out of Scope（最初の版でやらないこと）

- お小遣いの実際の支払い（送金や決済）（intent-statement）
- 割り当て作業の自動化（前月のコピー、自動割り当て）（intent-statement）
- 過去の月の履歴をグラフなどで振り返る機能（intent-statement）
- アプリの中で家族が話し合って割り当てやルールを決める機能（intent-statement）
- 「やらなかった」の自動判定（`scope-document.md`）
- 決まった条件で自動的に付くボーナス・ペナルティ（`scope-document.md`）
- 1 日 2 回以上のリマインド（`constraint-register.md` の C-T4）
- 子供が記録したことを家族のグループに知らせること（`wireframes.md` の Q8 で、前の決定から変更）
- 担当どうしを入れ替える「交換」。最初の版は「代わりにやる」だけにする（Q4）
- 月末のまとめを、修正のたびに送り直すこと（FR9.3）
- 管理者を 2 人以上にすること、1 人が複数の家族に入ること
