# NFR 設計 — U3 お知らせ先 — 質問

U3（`u3-notification-group`）の NFR 要件を、どう作るかを決めます。U1・U2 の設計はそのまま使います。

- LINE 用の受け口の確かめ（秘密のヘッダー、署名、同じイベントを二度処理しない）
- 構造化ログ
- 条件つきの TransactWriteItems と `CancellationReasons` の読み分け
- 1 回だけのやり直し
- 同時実行数の上限

ここで決めるのは、お知らせ先の記録の置き場所の 1 つだけです。ほかの作り方（グループの操作の入口、グループの名前の 2 秒の時間切れ、ログの項目など）は、NFR 要件と機能設計のとおりに設計に書きます。

## Q1. [アーキテクト] お知らせ先の記録の置き場所

お知らせ先は、グループ ID で探す（グループでの操作、公式アカウントが外されたとき）ことと、家族から探す（画面、U10 のお知らせ）ことの 2 通りで読みます。U2 では招待を新しいテーブルに置きました。

A. 新しく `NotificationGroups` テーブルを作り、グループ ID をキーにする（1 グループ 1 記録）。家族（Families）の記録に「いまのお知らせ先のグループ ID」を持ち、家族からはそこから読む。登録し直しと解除は、2 つのテーブルにまたがる条件つきのトランザクションで行う（U2 の招待と同じ形）
B. 家族（Families）の記録の中にお知らせ先を入れ、グループ ID で探すために Families にグループ ID の索引（GSI）を足す。索引の読み取りは少し遅れて反映される（結果整合）ため、「1 つのグループは 1 つの家族だけ」の確かめは、索引ではなく別の仕組みが必要になる
