# 安全の要件（Security）— U3 お知らせ先

U3（`u3-notification-group`）の安全の要件です。U1 の要件（NFR4.1〜NFR4.13、NFR5.1〜NFR5.6）と U2 の要件（NFR4.14〜NFR4.26、NFR5.7）は、そのまま使います。ここでは U3 で足すものを、U2 の番号の続きで書きます。

## LINE から届いたことの確かめ

| ID | 要件 | 確かめ方 |
|----|------|---------|
| NFR4.27 | join、leave、グループの message と postback も、U1 の LINE 用の受け口の確かめ（秘密のヘッダー、`x-line-signature`、同じイベントを二度処理しない）を通ってから処理する（U1 の NFR4.7、NFR4.8、NFR4.13）（BR4.1、BR4.2、BR4.9） | 署名のない join・leave・postback が処理されないこと |
| NFR4.28 | postback の data は、決まった形（`action=group.register`）とちょうど同じときだけ登録の操作として扱う。知らない data・長すぎる data（300 文字を超える）は何もしない。message の文字は、前後の空白を除いて「登録」とちょうど同じときだけ扱う（BR4.2） | 似た文字（「登録して」「とうろく」）や別の data で登録されないこと |

## 認可

| ID | 要件 | 確かめ方 |
|----|------|---------|
| NFR4.29 | 登録するのは、source.type が group で、source.userId の利用者が友だちで、家族に入っていて、役割が admin のときだけ。1 対 1 のトークと room からの登録の操作は登録しない（BR4.13）。家族は利用者の記録から決め、イベントの中の値（groupId 以外）からは決めない（BR4.3、BR4.4） | 子供・家族に入っていない人・ブロック中の人・source.userId がないイベント、1 対 1 と room のイベントで登録されないこと |
| NFR4.30 | 1 つのグループは 1 つの家族だけ。別の家族のお知らせ先になっているグループは登録しない（BR4.5）。確かめられるのは「そのグループが登録済みかどうか」だけで、グループにいる人がどの家族かは確かめられない（脅威と備えの表のとおり受け入れる） | 別の家族の管理者の登録が断られ、元の家族のお知らせ先が変わらないこと |
| NFR4.31 | グループでのアプリの操作（U8 で足す）は、グループが登録済みで、操作した人が友だちで、そのグループの家族のメンバーのときだけ通す。断るときの返事に、そのグループの家族の情報（家族の名前、メンバー、担当）を入れない（BR4.10） | U3 ではテスト用の操作で、登録されていないグループ・別の家族の人・ブロック中の人の操作に決まった文言だけが返ることを確かめる。実際の操作（「代わって」など）での確かめは U8 に引き継ぐ |
| NFR4.32 | `GET /v1/family/notification-group` は家族のメンバーだけ（U1 の NFR4.5）。応答はグループの名前と登録した時刻だけで、グループ ID を返さない（BR4.12） | 応答に groupId がないこと。メンバーでない人が 403 になること |

## グループの情報の扱い

| ID | 要件 | 確かめ方 |
|----|------|---------|
| NFR5.8 | グループ ID は秘密の情報ではないため、ログに全体を書いてよい（LINE の管理画面と突き合わせるため）[Q1]。ただし、グループの名前・メッセージの本文・利用者の表示名はログに書かない（U1 の NFR2.8 と同じく、Webhook の本文そのものも書かない） | ログの出し方の単体テストで、グループの名前と本文が出ないこと |
| NFR5.9 | グループの名前は、登録のときに 1 回だけ LINE から受け取って DynamoDB に残す。お知らせ先を外す（登録し直しで前のグループを消す、公式アカウントが外される）ときは、名前も一緒に消す [Q2]。DynamoDB は保存時に暗号化される（U1 と同じ AWS 管理の鍵） | 外したあとに、前のグループの名前が残らないこと |
| NFR4.33 | 画面では、グループの名前を HTML として差し込まない（U1 の NFR4.12）。名前は 100 文字までにして残す（それより長ければ切る。`entities.md` の groupName の max 100 と同じ数値） | 画面のテストで、名前の中のタグが文字として出ること |

## 脅威と備え

| 脅威 | 備え | 扱い |
|------|------|------|
| 偽の Webhook で登録・解除させる | NFR4.27 | 備える |
| 子供や家族以外の人が登録する | NFR4.29 | 備える |
| すでにほかの家族のお知らせ先になっているグループを登録し直して取る | NFR4.30 | 備える |
| 同じグループにいる別の家族の管理者（親戚など）が、先にそのグループを登録する | 先に登録した人は `NOTIFICATION_GROUP_REGISTERED` のログ（NFR2.21）で追える。取り戻す手順（先の家族が別のグループを登録する、または公式アカウントをグループから外して招待し直す。BR4.6、BR4.9）を README の「困ったとき」に書く（NFR10.5） | 受け入れる（LINE のイベントからは、グループにいる人がどの家族かを確かめられないため。先に登録した家族が使う） |
| ログのグループ ID と、家族・利用者の ID の対応が知られる | ログは作り手だけが見られる（CloudWatch Logs、30 日）。グループ ID だけでは、チャネルアクセストークンがなければ何も送れない | 受け入れる（チャネルアクセストークンが漏れていない前提。[Q1]） |
| グループの中で、別の家族の情報が見える | NFR4.31 | 備える |
| ログからグループの名前や会話が漏れる | NFR5.8 | 備える |
| 登録できたときの返事の家族の名前が、グループにいる家族以外の人に見える | — | 受け入れる（機能設計の rules.md の Assumptions） |

## Assumptions & Open Questions

- [assumption] LINE のグループ ID は、その公式アカウントのチャネルアクセストークンがなければ、push の宛先などに使えない値です。トークンはパラメータストアに置き、リポジトリやログに出さない（U1 の NFR5.1、NFR5.4）ので、ログにグループ ID の全体を書くことを受け入れます [Q1]。LINE の仕様での確認は B3 で行い、違っていれば U2 と同じく先頭だけを書く形に変えます（レビュー R-03）
- 同じグループにいる別の家族の管理者が先に登録した場合の取り戻し方は、`tech-stack-decisions.md` の NFR10.5 のとおり README に書きます（レビュー R-01）
