# 量と費用の設計（Scalability Design）— U5 割り当てとカレンダー

U5（`u5-assignment-calendar`）の量と費用の要件（NFR1.19〜NFR1.22、NFR3.6）を、どう作るかを書きます。U5 は U1〜U4 の作りを使うだけで、決まっていないことがないため、この段階では人に聞くことはありませんでした。データの置き方は、下の ADR で複数の案を比べて決めました。

## テーブルの形（NFR1.19、NFR1.20）

新しいテーブルを 1 つ足します。名前は `Calendar`（U4 の `ChoreTypes` と同じ型付きプレフィックスの単一テーブル）です。割り当て・担当・月の状態・担当の ID の引き当てを、家族をパーティションキーにして同じテーブルに置きます。

| テーブル | キー | 索引 | TTL |
|---------|------|------|-----|
| `Calendar`（新しく作る） | パーティションキー `familyId`、ソートキー `sk` | なし（GSI も LSI も作らない） | なし |

| 項目 | `sk` | 主な属性 | 書く人 |
|------|------|---------|-------|
| 月の割り当て（Assignment） | `M#<month>#A` | `month`、`rules`（AssignmentRule の並び）、`choreTypeIds`（文字列の集合。行が 0 行のときは属性を置かない）、`updatedAt`、`updatedByUserId` | U5 |
| 日ごとの担当（Duty） | `M#<month>#D#<date>#<choreTypeId>` | `dutyId`、`month`、`date`、`choreTypeId`、`childUserId`、`status`、`origin`、`version`、`createdAt`、`updatedAt`（U6〜U8 が `recordedAt`、`recordedBy`、`unitPrice` を足す） | U5〜U8 |
| 月の状態（MonthState） | `M#<month>#S` | `confirmed`、`confirmedAt` | U7（U5 は読むだけ） |
| 担当の ID の引き当て（DutyRef） | `DID#<dutyId>` | `month`、`date`、`choreTypeId` | U5（作るときと消すときだけ。あとから変わらない） |

- `<month>` は `YYYY-MM`、`<date>` は `YYYY-MM-DD`（どちらも日本時間）で、並べ替えがそのまま日付の順になる
- 担当のキーは「家族・日付・種類」そのものなので、同じ日の同じ種類の担当が 2 つできることはない（作るときの条件 `attribute_not_exists(sk)`）
- 1 か月分は `M#<month>#` で始まる `sk` の Query 1 回で読める。割り当て（`A`）、担当（`D#…`）、月の状態（`S`）の順に返る（`A` < `D` < `S`）
- 割り当ての `choreTypeIds` は、`rules` の種類の ID だけを集めた集合。種類の使用を `contains` で確かめるための重複で、`rules` と一緒に書く
- オンデマンド。1 年で担当が約 1500 件（約 0.6 MB）と、引き当てが同じ数、割り当てが 12 件。無料の保存量（25 GB）の中

## 読み方（NFR1.20、NFR1.21、NFR1.22）

| 読みたいもの | 読み方 | 整合性 |
|-------------|-------|--------|
| 1 か月のカレンダー（F1） | `Calendar` の Query 1 回（`familyId = :f AND begins_with(sk, 'M#<month>#')`、続きがあれば最後まで）と、C6 のメンバー一覧と C7 の種類の一覧の読み取りを同時に行う | 強い整合性（`Calendar`）。C6・C7 はそれぞれの作りのまま |
| 今の割り当て（F3） | `Calendar` の GetItem（`M#<month>#A`） | 強い整合性 |
| 月が確定しているか | 1 か月の Query に含まれる `S` を見る。単独では GetItem（`M#<month>#S`） | 強い整合性 |
| `PATCH /duties/{dutyId}` の担当（NFR1.22） | GetItem で `DID#<dutyId>`（キーの家族は `ctx.familyId`）→ GetItem で担当（`M#<month>#D#<date>#<choreTypeId>`）。担当の `dutyId` が呼ばれた ID と同じことを確かめる。月の確定の判断のために `M#<month>#S` の GetItem も行う（引き当てと担当の 2 回で担当を探し、月の状態は担当の `month` で読む） | 強い整合性の GetItem 3 回 |
| 保存・PATCH の子供の確かめ（NFR4.45） | `Users` の GetItem（`userId`、`childUserId` の重複を除いて同時に）。`familyId` と `role` を見る。索引は使わない | 強い整合性 |
| `isChoreTypeAssigned`（NFR1.22） | `Calendar` の Query（`familyId = :f AND begins_with(sk, 'M#')`、`FilterExpression: contains(choreTypeIds, :c) OR choreTypeId = :c`、`ProjectionExpression: sk`）。1 件でも見つかったら、そこで読むのをやめる | 強い整合性 |

- Scan は使わない。どの読み方も `familyId = ctx.familyId` を条件に含める（NFR4.44）
- カレンダーの表示は、担当 1 件ごとに種類や子供を読まない。種類と子供は一覧を 1 回ずつ読み、メモリの中で突き合わせる（NFR1.21）
- `isChoreTypeAssigned` は、U4 の「消す」でしか呼ばれない（まれな操作）。1 年分（約 1500 件、約 0.6 MB）の読み取りは、強い整合性（4 KB で 1 ユニット）でおよそ 150 読み取りユニット（1 回約 0.00002 ドル）。月 1 円を超えることはない（NFR1.22）。履歴が増えても 1 回の呼び出しの量が増えるだけで、呼び出しの回数は増えない

## 読み書きの量の見込み

| 操作 | 読み書き |
|------|---------|
| カレンダーを開く | `Calendar` の Query 1 回（約 40 KB、強い整合性で約 10 読み取りユニット）+ C6 の Query 1 回 + C7 の Query 1 回 |
| 割り当てを初めて保存（4 種類、124 件を作る） | 読み取り: 上の 3 つ + 子供の `Users` の GetItem（重複なし、数回）。書き込み: 担当 124 + 引き当て 124 = 248 項目 + 確かめ 5 × 3 チャンク = 15 項目の **3 回**（47、47、30 件）+ 割り当て 1 + 確かめ 5 = 6 項目の 1 回。**ConditionCheck も書き込みの項目として数える**ので、269 項目 × 2（トランザクションは 2 倍）= **約 540 書き込みユニット** |
| 割り当てを保存し直す（数件が変わる） | 読み取り: 上の 3 つ + 子供の GetItem。書き込み: 変わる担当（作る・消すは 2 項目、変えるは 1 項目）+ 確かめ（1 + 種類の数）+ 割り当て（1 + 1 + 種類の数）。1〜2 回のチャンク + 割り当て 1 回。数十書き込みユニット |
| 日ごとの担当を変える | `Calendar` の GetItem 3 回（引き当て、担当、月の状態）+ 子供の `Users` の GetItem 1 回 + TransactWriteItems 1 回（Update 1 + 確かめ 1 = 2 項目、4 書き込みユニット） |
| 種類を消す前の確かめ | Query（まれ） |

項目数の式は `reliability-design.md` と同じです（作る・消すは 2 項目〈担当 + `DID#`〉、変えるは 1 項目、各チャンクの確かめは 1 + 種類の数。上限は 1 回 100 項目）。

### 費用の見込み（NFR1.19）

- 家族 4 人で、月に保存が 2 回（今月と来月。確かめの ConditionCheck を含めて 1 回約 540 ユニット）、日ごとの担当の変更などの書き込みが数十ユニット、カレンダーを開くのが 1 日に数十回（月に約 700 回）の場合: 書き込み約 1100 ユニット、読み取り約 7000 ユニット
- 東京リージョンのオンデマンドの単価（書き込みが 100 万ユニットあたり約 0.71 ドル、読み取りが約 0.14 ドル）で、書き込み約 0.0008 ドル + 読み取り約 0.001 ドル = 合わせて約 0.002 ドル（約 0.3 円）。月 1 円に満たない
- **オンデマンドの読み書きは無料枠の対象外**（DynamoDB の読み書きの無料枠はプロビジョニング型のもの。無料なのは保存量 25 GB まで）。U5 の費用は無料枠で消えるのではなく、毎月約 0.3 円かかる見込みで、「請求額 0 円」（費用 0 円の条件）が成り立つのは、**約 0.002 ドルが請求の端数の丸めで 0.00 ドルになる前提**のときです。これは確かめていない前提なので、Infrastructure Design が最初の請求で確かめます（`logical-components.md` に引き継ぐ）。丸められず 0.01 ドルが載っても、月 1 円の見込みの範囲
- 新しい有料のサービスは足さない。Lambda は U1 の `api` に足す（無料枠の中）。CloudWatch のカスタムメトリクスも足さない（U10 で決める）

## ADR-U5-01 データの置き方

**Context**
- 割り当て（月に 1 つ）、担当（月に約 124 件）、月の状態（月に 1 つ）の 3 種類のデータを持つ。持ち主はどれも「カレンダー（担当と記録）」の部品（`components.md`）
- 担当の書き込みは割り当ての保存で 1 回に約 124 件変わる。U6〜U8 は担当と月の状態を同じ書き込みの中で確かめる必要がある（確定した月の担当を変えない、FR6.5）。DynamoDB のトランザクションは複数のテーブルをまたげるが、1 回に 100 項目まで
- 表示は保存の直後に必ず新しい内容を見せたい（結果整合の索引は使えない）
- U4 は `ChoreTypes` を「家族をパーティションキー、ソートキーを型付きのプレフィックス」の 1 つのテーブルにした

**Decision**
- 割り当て・担当・月の状態・担当の ID の引き当てを、`Calendar` という 1 つの新しいテーブルに置く。パーティションキーは `familyId`、ソートキーは `sk`（上の表）。索引は作らない
- 担当の ID から担当を探すために、引き当ての項目（`DID#<dutyId>`）を担当と同じトランザクションで作り、消す（ADR-U5-02）
- 種類の使用の確かめは、`M#` で始まる項目を絞り込み付きの Query で読む（ADR-U5-03）

**Consequences**
- よい点: 家族の範囲がキーで守られる（NFR4.44）。1 か月が Query 1 回。担当と月の状態と割り当てを同じテーブルの 1 つのトランザクションで確かめられるので、U6（記録）・U7（確定）・U8（引き受け）が同じ作りで書ける。新しい GSI がないので、保存の直後の表示が古くならない。ChoreTypes と同じ見た目なので、読む人が迷わない
- よくない点: 項目の形が 4 種類あり、`sk` の先頭で見分けるコードがいる（リポジトリの 1 か所に閉じ込める）。担当の作成と削除で書く項目が 2 倍になる（書き込みの量は月に数百ユニットで、費用に影響しない）。`isChoreTypeAssigned` は家族の履歴を絞り込み付きで読む（上で見積もったとおり、まれな操作で小さい）
- テーブルの定義は後から LSI を足せないので、最初から索引なしで作る（足りなくなったら GSI を足せる。結果整合になるので、その読み方は強い整合性を要しない用途に限る）

**Alternatives Rejected**

| 案 | よいところ | 選ばなかった理由 |
|----|----------|----------------|
| A. 割り当て・担当・月の状態を、用途ごとの 3 つのテーブルに分ける（U2・U3 と同じ） | 項目の形が 1 種類ずつ。権限を表ごとに分けられる | 1 回の保存で 3 つのテーブルを読み、トランザクションも 3 つのテーブルにまたがる。IAM の許可とテーブルが増える。家族の確かめを表ごとに繰り返す。U4 で決めた「家族の中に置く」と揃わない |
| B. U4 の `ChoreTypes` に足す | テーブルが増えない | 部品が違う（種類とカレンダーは別のサービス・リポジトリ。ADR-001）。権限を分けられない（U4 の権限に担当の書き込みが混ざる）。型付きのプレフィックスが混ざって、種類の一覧の Query に担当が入る事故が起きやすい |
| C. 担当を `dutyId` をキーにしたテーブルにして、月で引く GSI を足す | `dutyId` から 1 回で引ける | GSI は結果整合で、強い整合性の読み取りができない。保存の直後のカレンダーに担当が出ないことがある。「同じ日の同じ種類は 1 つ」をキーで守れない |
| D. 担当を `dutyId` をキーにして、月で引く LSI を足す | `dutyId` が 1 回で引け、LSI は強い整合性で読める | 「同じ日の同じ種類は 1 つ」をキーで守れず、同時の保存で二重にできる。LSI は後から足せず、家族ごとの項目の合計が 10 GB に制限される。LSI の分、書き込みの量が増える |
| E. 1 つの項目に 1 か月の担当をすべて入れる | 読み書きが GetItem 1 回 | 記録（U6）・引き受け（U8）が同じ項目を取り合い、競合しやすい。400 KB の上限に近づく種類の数もありうる |

## ADR-U5-02 担当の ID から担当を探す（NFR1.22）

**Context**
- `PATCH /v1/duties/{dutyId}` と、U6（記録）、U8（引き受け）は `dutyId` だけから担当を探す。Scan は使わず、強い整合性で読む（GSI は強い整合性の読み取りができない）
- 担当のキーは、月での Query と「同じ日の同じ種類は 1 つ」のために、`M#<month>#D#<date>#<choreTypeId>`（日付と種類を含む）にしたい
- 契約の `dutyId` は文字列で、NFR4.46 は UUID の形を先に確かめて、違えば DynamoDB を読まずに 404 にする

**Decision**
- `dutyId` は `crypto.randomUUID()` で作る。担当と同じトランザクションで、引き当ての項目 `DID#<dutyId>`（`month`、`date`、`choreTypeId`）を作る（条件 `attribute_not_exists(sk)`）。担当を消すときは、引き当ても同じトランザクションで消す
- 探すときは、パスの `dutyId` の形を確かめてから、`familyId = ctx.familyId, sk = DID#<dutyId>` の GetItem → 担当の GetItem（どちらも強い整合性）。担当が見つからない、または担当の `dutyId` が呼ばれた ID と違う（探している間に消されて作り直された）ときは、「ない」と同じ 404 `NOT_FOUND` にする
- キーの家族は、パスではなくセッションの `ctx.familyId` なので、ほかの家族の `dutyId` は引き当てが見つからず、ない ID と同じ 404 になる（NFR4.44）

**Consequences**
- 探すのは強い整合性の GetItem 2 回（約 10 ミリ秒。PATCH は月の状態の GetItem も足して 3 回）。担当の変更（PATCH）と記録は人が 1 回ずつ操作するので問題ない
- 引き当ては作ったあと変わらない項目なので、記録・引き受けの更新で書く項目は増えない。書くのは担当を作る・消すときだけ
- `dutyId` が UUID のままなので、形の確かめ（NFR4.46）と契約はそのまま使える。場所（日付・種類）が ID から読めることもない

**Alternatives Rejected**
- `dutyId` に家族の ID・日付・種類を入れる（キーを組み立てる）案: UUID の形を確かめられず（NFR4.46 と合わない）、内部のキーの作りが外に出る
- 日付と種類から決まる UUID（名前から作る）を `dutyId` にする案: 担当を消して作り直すと同じ ID が戻るため、古い申し出や LINE の古いボタンが新しい担当に当たる。BR6.6 の「新しい dutyId」とも合わない
- `dutyId` の GSI: 結果整合で、作った直後の担当が探せないことがある（NFR1.22 の「強い整合性」を満たせない）
- Scan: NFR1.22 が禁じている

## ADR-U5-03 種類が使われたかの確かめ（C8 `isChoreTypeAssigned`）

**Context**
- U4 の「消す」は、先に種類を「使わない」にして（`active = false`）から `isChoreTypeAssigned` を呼ぶ。BR6.10 は「どの月の割り当ての行か、どの担当にその種類があれば true」と決めている
- 直前に保存した割り当てを見落とさないよう、強い整合性で読む。Scan は使わない

**Decision**
- `Calendar` の `M#` で始まる項目を、1 回の Query で読む（強い整合性、家族のキー）。絞り込みの式は `contains(choreTypeIds, :c) OR choreTypeId = :c`（割り当ての項目は `choreTypeIds` の集合で、担当の項目は `choreTypeId` の文字列で当たる）。1 件当たれば、続きの読み取りをやめて true を返す
- 保存の側は、書き込みごとに種類の `active = true` を確かめる（`reliability-design.md`）。U4 の手順 1 のあとに入った保存は断られるので、`isChoreTypeAssigned` が false を返したあとに新しく使われることはない

**Consequences**
- BR6.10 のとおり、今あるものを正確に答える。保存の途中で失敗して担当だけができていても見落とさない（担当の項目も見る）
- 読む量は家族の履歴に比例するが、呼び出しはまれで、1 年分でも約 150 読み取りユニット。数年分（数千件）でも月 1 円を超えない

**Alternatives Rejected**
- 種類ごとの「使われた」印の項目を持つ案: 1 回の GetItem で済むが、割り当てから外すと印と実際がずれる（「一度も使われていない」の意味になり、BR6.10 と違う）。保存のたびに印を更新する書き込みが増え、確かめの項目が 1 トランザクションあたり増える。履歴が長くなったとき（数万件）の逃げ道として残す
- 割り当ての項目だけを読む案: 保存の途中で失敗し、担当だけができた状態（割り当てが未保存）を見落とす

## Lambda（NFR3.6）

- U5 の処理は U1 の画面用の Lambda（`api`）に足す。新しい Lambda は作らない。LINE 用の Lambda は U5 では `Calendar` に触れない（U6 以降で足す）
- 同時実行数の上限（5）の中で動く。保存は 1 つの Lambda の中でトランザクションを順に書く（並列にしない）ので、1 回の保存が占める同時実行は 1 つ

## 上限と余裕

| 項目 | 上限 | U5 の見込み |
|------|------|------------|
| TransactWriteItems の項目数 | 100 | 担当のチャンクは確かめ（1 + 種類の数）を含めて 100 を超えないように分ける。割り当ての書き込みは最大 1 + 1 + 90 = 92 項目（`rules` の種類を 90 までにしたため。`reliability-design.md`） |
| `rules` に含まれる種類の数 | 90（NFR4.47） | 家族の種類の数（4 つ）の 20 倍以上 |
| Query の 1 回の読み取り | 1 MB | 1 か月で約 40〜100 KB。続きがあれば最後まで読む |
| 1 項目の大きさ | 400 KB | 割り当て（200 行）で約 20 KB、担当で約 0.4 KB |
| 割り当ての行 | 200 行（NFR4.47） | 家族の量（種類 4 つ、子供 3 人）の 10 倍以上 |
| 本文 | 64 KB（NFR4.46） | 200 行で約 20 KB |
| 1 か月の担当 | 種類の数 × 31 | 4 種類で約 124 件。10 種類（約 310 件）でも 3 秒以内（`performance-design.md`） |
