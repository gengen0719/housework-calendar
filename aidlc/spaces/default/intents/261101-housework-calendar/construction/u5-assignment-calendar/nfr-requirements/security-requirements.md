# 安全の要件（Security）— U5 割り当てとカレンダー

U5（`u5-assignment-calendar`）の安全の要件です。U1〜U4 の要件（NFR4.1〜NFR4.41、NFR5.1〜NFR5.9）は、そのまま使います。ここでは U5 で足すものを、U4 の番号の続きで書きます。U5 は画面用 API の操作を足すだけで、新しい秘密の情報も LINE の操作もなく、決まっていないこともないため、NFR の段階では人に聞くことはありませんでした。

## 認可と家族の範囲

| ID | 要件 | 確かめ方 |
|----|------|---------|
| NFR4.42 | `PUT /v1/months/{month}/assignment` と `PATCH /v1/duties/{dutyId}` は C6 の requireAdmin で管理者かを確かめ、子供は 403 `ADMIN_ONLY`（BR6.1、AC3.1.8）。管理者の確かめは、担当や月の確かめ（404・409・422）より先に行う | 子供のセッションで、どの月・どの担当にも 403 になり、何も変わらないこと |
| NFR4.43 | `GET /v1/months/{month}/calendar` と `GET /v1/months/{month}/assignment` は家族のメンバーだけで、その家族の担当・割り当て・子供・種類だけを返す（BR6.15） | ほかの家族の担当が含まれないこと |
| NFR4.44 | 担当・割り当て・月の状態の読み書きは、いつも `familyId = ctx.familyId` をキーに含めて行う。ほかの家族の `dutyId` は「ない」と同じ 404 `NOT_FOUND` を返す（U1 の NFR4.6、U4 の NFR4.36 と同じ考え） | ほかの家族の担当の ID で、ない ID と同じ応答になること |
| NFR4.45 | 割り当ての行の `choreTypeId` と `childUserId`、担当の変更の `childUserId` は、その家族の種類と子供であることを C7・C6 で確かめる。ほかの家族の種類や子供、管理者自身を担当にすることはできない（BR6.3、BR6.9） | ほかの家族の種類・子供、管理者の userId を入れて 404 になること |

## 入力の確かめ

| ID | 要件 | 確かめ方 |
|----|------|---------|
| NFR4.46 | パスの `month` は `YYYY-MM`（年は 2000〜2100、月は 01〜12）だけを受け、違えば 422 `INVALID_MONTH`（`0050-01` のような年を日付の計算に渡さない。レビュー）。本文は 64 KB まで（超えれば 413 か 422）。`childUserId` は U1 の利用者 ID と同じ形（UUID）だけを受ける。`dutyId` は形（UUID。小文字の 16 進数だけ）を先に確かめ、違えば DynamoDB を読まずに 404 | `2027-13`、`2027-1`、`abc`、形の違う ID が断られること |
| NFR4.47 | 割り当ての本文は zod で読む。`rules` は配列で、各行は `choreTypeId`（UUID の形）・`childUserId`（UUID の形。NFR4.46 と同じ）・`weekdays`（0〜6 の整数の配列、1〜7 個）。UUID は小文字の 16 進数だけを受ける。行の数は 200 行まで、`rules` に含まれる種類の数は 90 まで（家族の量を大きく超える要求で処理を重くさせない。種類の確かめを割り当ての書き込みの 100 項目に必ず収めるため）。`confirmedChangesHash` は任意の 64 文字の 16 進数。知らない項目は捨てる。違えば 422 `INVALID_ASSIGNMENT` | 形の違う本文、201 行、8 個の曜日、7 の曜日が断られること |
| NFR4.48 | 担当の変更の本文は `{ childUserId }` を zod で読み、違えば 422 `INVALID_REQUEST`。`childUserId` に加えた余分な項目は捨てる（NFR4.47 と同じ `strip`）。`childUserId` がない本文（余分な項目だけの本文を含む）は 422 | 本文なし・数・`childUserId` のない本文は 422、余分な項目つきの正しい本文は通ること |
| NFR4.49 | 画面では、種類の名前と子供の表示名を HTML として差し込まない（U1 の NFR4.12） | 画面のテストで、名前の中のタグが文字として出ること |

## 書き込みの整合（安全にかかわるもの）

| ID | 要件 | 確かめ方 |
|----|------|---------|
| NFR4.50 | 保存し直しで担当を変える・消すときは、担当が「未」で version が変わっていないこと、月が確定していないこと、種類が「使う」であることを、書き込みの条件にする（割り当ての記録の書き込みでも、種類の確かめを必ず同じトランザクションに入れる）。担当の子供を変える PATCH は、担当が呼ばれた `dutyId` のままであることも条件にする。確かめと書き込みの間に、記録（U6）・引き受け（U8）・確定（U7）・種類を消す（U4）が入っても、「済」の担当を「未」に戻したり、確定した月を変えたりしない（BR6.6〜BR6.8） | 書き込みの直前に別の書き込みを入れる差し替えで、条件で断られること |
| NFR4.51 | 上書きの確かめの印（`changesHash`）は、`familyId`、`month`、変化の一覧（日付・種類・前の子供・後の子供・担当の version を、日付と種類の順に並べたもの）を決まった形の JSON にしたものの SHA-256（16 進数 64 文字）。画面から受け取った印は、裏側でいまの一覧から作り直した印とちょうど同じときだけ受け入れる。形の誤り（64 文字の 16 進数でない）は 422 `INVALID_ASSIGNMENT`、形は正しいが合わないときは 409 `OVERWRITE_CONFIRMATION_REQUIRED`（新しい一覧と印つき）。この印は鍵のない計算なので、管理者の誤操作（見ていない一覧での上書き）を防ぐためのもので、認可の代わりではない（認可は NFR4.42）（BR6.7。レビュー） | 古い印や作った印で、確かめなしに上書きできないこと。形の誤りが 422、不一致が 409 になること |
| NFR4.52 | 確かめの順番は、セッション → 家族のメンバー → 管理者（PUT・PATCH）→ パスの形（`month` の 422、`dutyId` の 404）→ 担当の 404（家族の範囲。PATCH）→ 本文の 422 → （PUT）全行の種類の 404 → 全行の種類の 422 `CHORE_TYPE_INACTIVE` → 全行の子供の 404（BR6.3 の並び。PATCH は子供の 404）→ 月の状態と担当の状態の 409 → （PUT）今月か来月かの 422 `MONTH_NOT_EDITABLE` → 重なりの 422 → 上書きの確かめの 409。子供は `Users` の強い整合性の GetItem で `familyId` と `role` を確かめる。ほかの家族の `dutyId` には、本文が正しくても誤っていても 404 を返す（U4 の NFR4.41 と同じ考え。レビュー） | ほかの家族の担当の ID に誤った本文で送っても 404 になること |

## 脅威と備え

| 脅威 | 備え | 扱い |
|------|------|------|
| 子供が割り当てや担当を変える | NFR4.42 | 備える |
| ほかの家族の担当・割り当てを見る・変える | NFR4.43〜NFR4.45 | 備える |
| 大きすぎる本文で処理を重くする | NFR4.47（200 行まで） | 備える |
| 確かめを飛ばして、引き受けた担当を上書きする | NFR4.51 | 備える |
| 記録や確定と保存が重なって、記録や確定が壊れる | NFR4.50 | 備える |
