**Findings**

1. **R-01（Major）初めての保存と保存し直しの分かれ目が曖昧で、BR6.4 の範囲の書き方も食い違っている**
   - 場所: rules.md の BR6.5 の trigger（「その月にまだ担当が 1 つもないとき」）と BR6.6 の trigger（「担当がすでにあるとき」）。BR6.4 の logic の 1 文目と最後の 1 文。
   - 問題: 分かれ目が「担当の有無」になっています。行が 0 行の割り当ては保存できます（BR6.3）。たとえば 1 月 10 日に 0 行で保存し、15 日に 1 行入れて保存し直すと、担当が 0 件なので BR6.5 側に入り、今日（15 日）の担当を作ります。これは「今日は変えない」（AC3.1.4、BR6.6）と食い違います。逆に、前提データで過ぎた日の「済」だけがあり、割り当ての記録がない月では BR6.6 側に入ります。「初めて」の判定が Assignment の有無なのか Duty の有無なのか、決まっていません。また BR6.4 は 1 文目で「作る日の範囲の中で」、最後の文で「その月のすべての日で」と書いていて、どちらで確かめるのか読み取れません。
   - 直し方: 分かれ目を「その月の Assignment が保存済みか（`exists`）」に決めて、BR6.5 / BR6.6 / entities.md に書いてください。0 行の保存でも Assignment を残す、と明記してください。BR6.4 は「その月のすべての日で確かめる」に 1 本化してください。0 行のあとに保存し直す場合の確かめ（AC）を functional-spec.md に足してください。

2. **R-02（Major）上書きの確認が特定の一覧に結びついておらず、記録や引き受けとの競合を防げない**
   - 場所: rules.md の BR6.7 の logic 最後の 1 文（「確かめのあとに担当が変わっていたら、もう一度一覧を返す」）。BR6.8。BR6.18。contract-summary.md の `confirmOverwrite: boolean`。
   - 問題: 送り直しのときに届くのは true / false の 1 つだけです。サーバーには、人が見た一覧がどれだったかを知る手段がなく、「変わっていたら一覧を返す」を実装できません。確認の一覧を見たあとに、別の人が操作する場合もあります。たとえば、子供が U6 で「済」を記録する、U8 で引き受ける、管理者が別の画面で担当を変える、などです。このとき true で送ると、見ていない変化まで上書きされるおそれがあります。さらに、BR6.8 が条件にするのは種類の「使う」だけです。置き換える側の「未」の担当について、書き込み時に「いまも未で、読んだときの子供・origin のまま」を条件にする決まりがありません。子供が複数同時に使うので、BR6.18 の「家族に管理者は 1 人なので受け入れる」は、記録・引き受けには当てはまりません。作り直しと「済」の記録が重なると、記録が消えたり、「済」が「未」に戻ったりするおそれがあります。
   - 直し方: 次のどちらかに決めてください。(a) 確認済みの変化の一覧（または一覧の要約値）を送り直しの本文で送り、サーバーが再計算した一覧と比べて、違えば 409 を返し直す。(b) 担当ごとの版（version）を持たせ、置き換えは「読んだ版のまま」を条件にする。あわせて BR6.6 / BR6.8 に、置き換え・削除は status が todo のままであることを書き込みの条件にする、と書いてください。契約の追加（`docs/contract-changes-u5.md`）に、送り直しの本文の項目を足してください。

3. **R-03（Major）作り直しで dutyId が保たれるか、申し出（U8）がどうなるか、書き込みの原子性が未定**
   - 場所: rules.md の BR6.6（「置き換える」）と BR6.9。entities.md の Duty。要件 FR7.5（管理者が担当を変更・作り直したら申し出がなくなる）。
   - 問題: 置き換えが、同じ dutyId の更新なのか、削除して新しい dutyId で作り直すのか、書いてありません。U6 / U8 の LINE のボタン（postback）は dutyId を持つので、作り直しで dutyId が変わると、古いボタンが「見つからない」になるか、別の担当を指すおそれがあります。U8 の Offer は担当に紐づきますが、U5 の BR6.6 / BR6.9 に「担当が変わったら申し出をなくす」窓口や決まりがなく、U8 が U5 の保存の途中に割り込む設計になります（頼り方は一方向。ADR-001）。また、日ごとの担当は 1 回の保存で 100 件を超えることがあります。種類が 4 つ、31 日で最大 124 件です。割り当て・担当・種類の条件を「同じ操作の中」で原子的に書く（BR6.8）と言っていますが、途中で失敗したときの状態と、送り直したときの結果が決まっていません。
   - 直し方: 次を決めて書いてください。「(familyId, date, choreTypeId) が同じなら dutyId を保ち、子供と origin だけ更新する。なくなる担当だけ削除する」。「担当の子供を変える・削除するとき、C8 がその担当の申し出も同じ操作でなくす。または Offer に担当の子供を持たせ、一致しなければ無効とする」。1 回の保存が件数の上限を超えるときの方法（分割しても部分的な状態が残らない手順、または保存の途中状態を表す印と再実行で収束する決まり）を書いてください。

4. **R-04（Minor）日本時間の「今日」の出どころと、サーバーの純粋さが未定**
   - 場所: functional-spec.md の F1 手順 3（「今日の位置を見せる」）。contract-summary.md の C8 `saveAssignment(ctx, month, rules, confirmOverwrite)`。rules.md の BR6.2、BR6.5、BR6.6、BR6.18。
   - 問題: 「今月・来月」「今日」「明日」をだれがどう決めるかがありません。C8 の他の窓口は `today` / `at` を引数で受けますが、`saveAssignment` と `changeDutyChild` にはありません。時計を差し替えられないと、AC3.1.4 の「今日は 1 月 10 日」というテストを書けません。画面側で端末の時計を使うと、端末の時間帯が日本でないときに「今日の位置」と月の初期表示がずれます。
   - 直し方: C8 に `today`（日本時間の日付）を引数に足すか、注入できる時計を決めてください。`MonthCalendar` に `today`（サーバーが決めた日本時間の日付）を足し、画面はそれを使う、と書いてください。「記録した時刻（UTC）」から日本時間への変換をどこで行うかも決めてください。

5. **R-05（Minor）C8 の戻り値・エラーと、Duty の項目名が契約と食い違っている**
   - 場所: functional-spec.md「契約への追加」の表。entities.md の Duty の `recordedByUserId`。contract-summary.md の `Duty.recordedBy` と C8 `saveAssignment` の戻り値。
   - 問題: 契約の `Duty` は `recordedBy` ですが、entities.md は `recordedByUserId` です。画面用の `Duty` には名前の食い違いが残ります。契約の C8 `saveAssignment` は戻り値が `Assignment` で、エラーに `MONTH_NOT_EDITABLE`、`INVALID_ASSIGNMENT`、`INVALID_MONTH` がありません。C8 の追加の行は `getAssignment` と `isChoreTypeAssigned` しか触れていません。`changeDutyChild` も `INVALID_REQUEST` を持ちません。また BR6.3 は、保存の前に種類が見つからなければ 404、BR6.8 は書き込み時に「使わない」で 422 `CHORE_TYPE_INACTIVE` としていて、種類が保存の間に消えた場合に返すのがどちらか決まっていません。
   - 直し方: 項目名を契約の `recordedBy` にそろえるか、契約の追加表に「保存名と画面の名前が違う」と書いてください。C8 の追加の行に、エラー一覧と戻り値（PUT は内部では `Assignment` を返し、入口が `MonthCalendar` を作る、など）を足してください。書き込み時に種類が見つからない場合は 404 とするのか 422 とするのかを BR6.8 に書いてください。

6. **R-06（Minor）月の状態（MonthState）の初期値と、割り当てなし・担当なしの判定が曖昧**
   - 場所: entities.md の MonthState、functional-spec.md の F1 手順 4。contract-summary.md の `MonthCalendar.hasAssignment`。
   - 問題: MonthState の行がない月は「確定していない」と読む、と書いてありません。F1 手順 4 は「割り当ても担当もない月」と書き、`GET .../assignment` の `exists` と `hasAssignment` が何を指すか（R-01 の判定と同じか）が決まっていません。たとえば、割り当てはあるが担当が 0 件の月（0 行の保存、または月末近くの保存）で、「この月の割り当てはまだありません」を出すと、保存済みの事実と食い違います。
   - 直し方: 「MonthState の行がなければ確定していない」と書いてください。`hasAssignment` と `exists` は Assignment の保存済みの有無と同じものに決め（R-01 と共通）、割り当てはあるが担当がない月の表示を BR6.14 に足してください。

7. **R-07（Minor）作り直しで origin が rule に戻る場合の扱いが書かれていない**
   - 場所: rules.md の BR6.6（「置き換えた担当の origin は rule になる」）と BR6.7（「子供が変わる、またはなくなる」）。
   - 問題: 日ごとに変えた担当（manual）や引き受けた担当（swap）が、新しい割り当てと同じ子供になる場合、変化がないので確認は出ません。ところが origin が黙って rule に戻ります。以後の保存し直しで、この担当は確認の対象にならなくなります。直前に管理者が意図して変えた担当が、気づかないうちに通常の担当に戻ることになります。
   - 直し方: 子供が変わらない場合は origin も変えない、と決めてください。変えるなら、その理由と、確認の対象から外れる旨を書いてください。

8. **R-08（Minor）トレーサビリティの reverse の欄が実態と合っていない**
   - 場所: traceability.json の reverse（BR6.8、BR6.10）。
   - 問題: BR6.8 と BR6.10 は要件 FR2.3 / FR2.4 と U4 の BR5.9 に由来しますが、`N/A` と書かれています。BR6.12、BR6.17 は上流のストーリーに出てこない追加の機能（Q4、Q5）ですが、これも `N/A` で、追加であることが区別されません。AC4.1.7 は `OK` ですが、実際は一部（U5 の画面のみ）の対応です。
   - 直し方: reverse の欄に、由来する要件（FR2.3、FR2.4）と、「Q の決定による追加」の区別を書いてください。AC4.1.7 は部分的な対応であることが読み取れる状態にしてください。
