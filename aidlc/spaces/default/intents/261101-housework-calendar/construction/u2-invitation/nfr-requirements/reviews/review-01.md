### 所見

`security-requirements.md`（NFR4.14〜NFR4.23、NFR5.7）を、機能設計（`rules.md` の BR3.1〜BR3.12、`functional-spec.md`）、U1 の安全の要件（NFR4.1〜NFR4.13、NFR5.1〜NFR5.6）、要件（NFR1〜NFR11）と突き合わせました。招待の印の強さ（128 ビット以上、`crypto.randomBytes`、Base64URL）、形の先行確認、理由を分けない応答、家族を招待の記録だけで決めること、送り直しの扱いは、機能設計と U1 に合っています。Major は 2 件で、設計の前に直すことを勧めます。ただし、基準の「Major が 2 件以下なら通る」の範囲内です。

### 指摘

1. **R-01 (Major) 印がパスに入るため、リクエストのログから印の全体が漏れる。**
   `GET /v1/invitations/{token}` と `POST /v1/invitations/{token}/accept` は印を URL のパスに持ちます。NFR5.7 と NFR2.14 は「印の全体をログに書かない」としますが、要求ごとのログ（U1 の NFR2.6 のリクエスト ID 付きログ）と、U2 の NFR7.11（操作ごとにかかった時間をログに残す）がパスをそのまま書くと、印が全体ログに残ります。CloudFront や Lambda のアクセスログも同じです。印は取り出せる形で保存され（NFR4.18）、ログは 30 日残ります（NFR2.7）。
   **直し方:** リクエストのログとアクセスログでは、パスの `{token}` を伏せる（`/v1/invitations/{token}` のようなルートの形で書く）と決めます。あわせて、リクエストログ全体に印が出ないことを、NFR5.7 の単体テストの対象に足します。

2. **R-02 (Major) 招待の作成の回数の上限と、同時実行数の上限の値が決まらないまま、総当たり対策がそれらに頼っている。**
   機能設計の Assumptions は「招待の作成の回数の上限」「失敗が続いたときの制限」を NFR の段階で決めるとしていました（レビュー R-02）。NFR4.17 は利用者ごとの回数の制限を付けない（Q2 の A）と決めましたが、招待の作成（`POST /v1/family/invitations`）の頻度の扱いには触れていません。さらに NFR4.17 が頼る U1 の NFR1.6 は「例: 画面用 5」で、値が決まっていません。数値がないため、「当てられない」「費用 0 円が崩れない」を確かめられません。
   **直し方:** 作成の上限を決めるか、「付けない。理由は家族の管理者だけが作れて、作るたびに DynamoDB の書き込みが 2 回で無料枠に収まる」と明記します。NFR1.6 の値は U1 の NFR 設計で決める前提を書くか、U2 で採用する値を数字で書きます。あわせて 128 ビットの印と 24 時間の期限で当てられるおそれが十分小さい理由を、1 行の見積もりで足します。

3. **R-03 (Minor) 画面の URL に残る印の扱いが足りない。**
   NFR4.23 は URL のクエリの印を、形を確かめてから使うとだけ書いています。参加や無効の応答のあとも、印がブラウザの履歴や共有の URL に残ります。
   **直し方:** 参加・無効のいずれの結果でも、印を `history.replaceState` で URL から外す。外部へのリンクを出さない（U1 の NFR4.11 の Referrer-Policy を引く）と決め、画面のテストで確かめます。

4. **R-04 (Minor) 長さと形が測れる値になっていない。**
   NFR4.14 は「22 文字ほど」としています。16 バイトの Base64URL は 22 文字（パディングなし）に決まります。NFR4.16 は「決まった長さ」と書くだけです。
   **直し方:** 「22 文字ちょうど、文字は `[A-Za-z0-9_-]` のみ」と書き、NFR4.14、NFR4.16、NFR4.24 の 3 か所で同じ記述にそろえます。

5. **R-05 (Minor) 失敗が続いたことの検知の目標がない。**
   NFR4.17 は使えない印の要求をログに残すとしますが、気づく手段（しきい値や見る人）がありません。
   **直し方:** CloudWatch Logs のメトリクスフィルタとアラームは無料枠に収まるか、収まらないなら作り手が定期的にログを見る手順を README に書く、のいずれかを選び、NFR2.9 にひもづけます。

6. **R-06 (Minor) 同じ要件 ID が 2 つのファイルに分かれている。**
   NFR4.24（印の作り方）は `tech-stack-decisions.md` にあり、同じ内容の NFR4.14 は `security-requirements.md` にあります。`security-requirements.md` の Sources に `tech-stack-decisions.md` がありません。
   **直し方:** NFR4.24 を NFR4.14 の下に統合するか、相互に参照を書きます。

7. **R-07 (Minor) 追跡情報が NFR11 の扱いで食い違う。**
   `traceability.json` の NFR11 は `status: "N/A"` ですが、`target` に NFR2.13 を書いています。意味が食い違います。また NFR4 の項目は、機能設計の BR3.x への対応を持たないため、どの決まりをどの要件が守るか辿りにくい状態です。
   **直し方:** NFR11 は `OK`（NFR2.13）にするか、`target` を U1 の NFR11.1 に絞ります。NFR4.14〜NFR4.24 に対応する BR3.x を `traceability.json` かこの文書の表に足します。

8. **R-08 (Minor) 受け入れたリスクの対応が安全の要件の側で閉じていない。**
   転送されたリンクで家族以外の人が参加しうるリスクは、Assumptions に書かれ、機能設計の R-07 とつながっています。ただし、参加のたびにメンバーの一覧で気づける、という緩和が、参加のログ（NFR2.9）には「参加した」を残す、ほかの手段（管理者への通知など）はない、と対応づけて書かれていません。
   **直し方:** 脅威と備えの表を U1 のように U2 にも足し、このリスクを「受け入れる」として備え（24 時間の期限、作り直し、参加前の確認、メンバーの一覧、参加のログ）と並べます。

### 費用 0 円の確認

DynamoDB の既定の暗号化（AWS 所有の鍵）、TransactWriteItems、TTL、shareTargetPicker（公式アカウントのメッセージを使わない）は、新しい費用を生みません。この点は問題ありません（上の R-02 の値が決まることが前提です）。

### まとめ

U1 の安全の要件を壊さずに、招待の印の強さ・認可・送り直し・理由を分けない応答が、機能設計と一貫して書かれています。Major の 2 件（印がログのパスから漏れうること、回数と同時実行数の数値が決まっていないこと）は、設計に入る前に直す価値があります。
