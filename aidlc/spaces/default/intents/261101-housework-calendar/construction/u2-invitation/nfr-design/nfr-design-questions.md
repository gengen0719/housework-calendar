# NFR 設計 — U2 招待 — 質問

U2（`u2-invitation`）の NFR 要件を、どう作るかを決めます。U1 の設計（構造化ログ、入口のエラーハンドラー、認可の仕組み `requireAdmin` / `getMembership`、送り直しの記録 RequestRecords、TransactWriteItems、同時実行数の上限 画面用 5）は、そのまま使います。

ここで決めるのは、招待の記録の置き場所と、メンバーの一覧の読み方の 2 つです。ほかの細かい作り方（ログでパスの印を伏せる方法、画面での印の扱いなど）は、NFR 要件どおりに設計に書きます。

## Q1. [アーキテクト] 招待の記録の置き場所

招待は、リンクの印（token）で探す（招待を開く・参加する）ことと、家族のいまの招待を探す（管理者が家族の設定を開く）ことの 2 通りで読みます。U1 では、データの種類ごとに DynamoDB のテーブルを分けています。

A. 新しく `Invitations` テーブルを作り、印をキー（パーティションキー）にする。家族（Families）の記録に「いまの招待の印」を持ち、家族のいまの招待はそこから読む。作り直しと参加は、Families と Invitations の 2 つにまたがるトランザクションで条件を確かめる
B. 招待を家族（Families）の記録の中に入れる（家族ごとに招待は 1 つ）。印で探すために、Families に印の索引（GSI）を足す。索引の読み取りは少し遅れて反映される（結果整合）ため、作り直した直後の古い印の扱いは、参加のときに Families の本体をもう一度読んで確かめる
X. Other (please specify)

[Answer]: A

## Q2. [アーキテクト] メンバーの一覧の読み方

メンバーの一覧（`GET /v1/family/members`）は、家族の ID で利用者（Users）を探します。いまの Users テーブルは、利用者の ID がキーで、LINE のユーザー ID の索引だけがあります。

A. Users テーブルに家族の ID の索引（GSI `familyId-index`）を足し、その索引で読む。メンバーが増えても読む量は家族の人数分だけ
B. 家族（Families）の記録に、メンバーの利用者の ID の一覧を持ち、そこから Users を 1 人ずつ読む（参加のトランザクションで一覧にも足す）
X. Other (please specify)

[Answer]: A
