# 単体テストの手引き — U10 お知らせ

## 実行環境と構成

既存のVitestと@amiceli/vitest-cucumberを使う。Node.js22、ルートで依存が復元済みであること。backend/shared/infrastructureのtest/u10-notificationsに全てのU10テストを置く。既存vitest.config.tsのincludeと行80%の閾値を確認し、適用済みなら設定を増やさない。

まだU10テストがない段階の実行環境確認だけ:

```bash
npx vitest run u10-notifications --passWithNoTests
```

最初の筋書きを書いた後の通常実行:

```bash
npx vitest run u10-notifications
```

U10のカバレッジ:

```bash
npx vitest run u10-notifications --coverage --coverage.include='packages/*/src/**' --coverage.include='infrastructure/lib/**'
```

このコマンドはU10のテストだけを実行する。選択テストが全て通っても、ほかの単位のソースを含む全体閾値だけでexit1となる場合は、その区別を記録する。閾値を下げない。全体の80%以上は、記録済みConstruction Verification Commandの全テストで判定する。

構成の確認だけ:

```bash
npx vitest run infrastructure/test/u10-notifications/stacks.test.ts
```

## BDDとテストの量

| 切れ目 | 筋書き・結合 | 単体の目安 |
|---|---|---|
| 時刻と入力、識別 | 通知時刻、月末、うるう日、年越し、不正入力、15分の境界 | 各部品5〜8件 |
| 記録と本文 | 並行、版違い、所有期限、原子的保存、終端、本文削除、24時間、35日 | 各repository5〜8件 |
| 家族と担当 | 家族分離、登録なし、確定、担当なし、ページ続き、読込失敗 | 各公開窓口5〜8件 |
| 本文と配信 | 全担当、0円、負額、子供0人、上限、409受理済み/一般、429/5xx/timeout | 各部品5〜8件 |
| 送信全体とキュー | 重複起動、受理後の保存失敗、所有権解放、早期再配達、最大3試行、宛先変更 | 各部品5〜8件 |
| 運用 | メールの許可項目、初回失敗、起動欠落、0家族、清掃、バックアップ台帳/一覧、他テーブル拒否 | 各部品5〜8件 |
| CDK | 暗号化、IAM、環境分離、3入口、通知URLなし、Scheduler、可視性、監視10個、予算、有効化条件 | 約25〜35件 |

合計の目安は150〜220件。各部品は正常系に加え最低2つの異常・境界を持つ。筋書きを実装の前に書き、必要な層を通して成功させ、その後に細かい単体と整理を行う。共有AC1.2.4の「未登録なら外部送信0回」を省略しない。

## 差し替えとデータ

- 時刻・乱数・遅延・外部通信を差し替え、予定時刻前・期限直前・期限ちょうど・月末・年越しを固定する。実時間で15分待つテストを作らない。
- DynamoDBの偽は状態と条件式を扱い、競合を常に成功させる偽にしない。既存のfakeDynamoを拡張する場合は既存の期待を変えず、U10の補助へ切り出せるものは切り出す。
- SQSは受信時刻・可視性・受信回数を記録。成功として削除されたか、部分失敗で残したかを判定する。早期配達や所有中の重複で仕事が失われないことを確かめる。
- LINEは受理後の通信切断を再現し、同じキー・本文・宛先で再試行することを確認。実際のLINE・AWSへ接続しない。
- SNSとCloudWatchは要求内容を記録する偽を使い、名前・金額・本文・LINE識別子・メールアドレス・鍵の目印が含まれないことを検査する。
- 家族・利用者・担当・月・秘密らしい作り物の値は、各test/fixtures/fakeSecrets.tsからimportする。行ごとにgitleaks:allowを付ける。実値を使わない。
- バックアップは自分の表と別の表を混在させ、作成応答不明・台帳欠落・ページ続き・7日境界を再現。別の表の削除が0回であることを確認する。
- 初回60秒以内の実測、15分以内のメール受信、実LINEの1回受理、無料枠と費用、購読確認はステージングの手順で行う。未実行を成功と記録しない。
