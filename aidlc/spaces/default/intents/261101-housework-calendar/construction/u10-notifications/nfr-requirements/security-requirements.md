# 安全性の要件 — U10 お知らせ

| ID | 要件 | 確かめ方 |
|---|---|---|
| NFR4.101 | 定時起動の権限を持つ処理だけが通知入口を呼べる。一般公開の画面用入口から任意の家族・日付への通知を起こせない。 | 構成の権限検査と、想定外の入力・呼出元の拒否テスト。 |
| NFR4.102 | 家族の列挙とお知らせ先の参照はC6の所有する窓口で行い、家族ごとのsystem文脈だけを下位の読み取りへ渡す。家族Aの通知へ家族Bの名前・担当・金額が入るケースを0件とする。 | 複数家族の前提データと参照履歴で検査。 |
| NFR4.103 | 送信先が準備後に変更された場合、古い先への新しい送信と新しい先への別キーの再送を開始しない。外部配信との競合窓は仕様に明示し、原子的な保証と偽らない。 | 宛先変更の差し込みと通信履歴。 |
| NFR4.104 | 本文・子供の名前・金額・LINE識別子・メールアドレス・トークンをログと運用メールへ出さない。識別が必要な場合は運用専用の非可逆な家族識別子を使う。 | 成功・失敗・再試行・期限切れを含むログの目印検査。 |
| NFR5.101 | 秘密情報は環境ごとの保管場所から取得し、コード・テスト・成果物へ実値を書かない。作り物の値は既存のfixture規約に従う。 | 秘密検査と既存のlint。秘密検査が未実行なら配備前の未完了項目として残す。 |
| NFR5.102 | 通知本文のスナップショットを保護し、不要になった本文は予定時刻から24時間以内に読めなくする。非個人情報の重複防止記録は35日間保持する。削除済みの古い起動は時刻検証で再送しない。 | 時計を進めた削除処理と削除後の再起動のテスト。非同期の自動削除だけで24時間上限を保証しない。 |
| NFR6.101 | 配信済みの通知を直接データ修正して再送しない。復旧は記録された手順を使い、再試行キー・内容・宛先を変えない。 | 運用手順と復旧試験。 |

機能設計レビューで未定義だった更新の版は、次の設計で「0以上の整数、作成時0、更新ごとに増加」として状態更新の条件に含める。共有AC1.2.4の送信先未登録時の省略は、U10の統合テストにも明示的に追加する。これらは既存の機能設計レビューの軽微な指摘の引き継ぎであり、解決済みとは記録しない。

新たな業法・地域の適用は仮定しない。既定の日本での家族利用、秘密を公開リポジトリに含めないという前提を維持する。
