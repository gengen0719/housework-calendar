# 信頼性設計 — U10 お知らせ

## 永続化と再試行

NFR2.101〜NFR2.106、NFR8.101、NFR10.101を対象とする。家族・通知種類・対象日を論理キーとし、条件付き作成で1件だけ準備する。家族ごとの処理は保存した本文・宛先・再試行キーを固定して使う。所有権の期限は45秒、処理の上限は30秒とする。古い所有者は版が変わった記録を書き換えられない。

- 外部配信は最大3試行（初回を含む）。初回失敗の直後に作り手への監視を発火する。
- 次の試行は初回失敗後5秒、次の失敗後20秒を基本に0〜1秒のばらつきを加える。配信先の待機指示があるときはその時刻以降にし、期限内へ収まらなければ再試行しない。
- 通信タイムアウト、接続失敗、429、5xxを再試行対象とする。認証・入力・宛先の恒久的な失敗は対象外。SDKの自動再試行は外部配信では無効にし、試行回数を通知記録で数える。
- 同じ再試行キーを付けた要求が受理済みであることを、409と受理済み要求識別子から確認できる場合にsentへ進める。409だけで成功とみなさない。
- 配信受理後の保存失敗でも、本文とキーを変えず照合する。キーを変える復旧や自動再送は行わない。期限切れや回数上限の場合は失敗の分類を残し、送信済みと偽らない。
- キューへの受け渡し途中で中断した場合、同じ起動を再実行して未完了の仕事を再投入する。重複を許すキューでも状態と所有権で外部送信を制御する。
- 最終失敗を別の隔離先へ記録しても、自動的に別キーで再配信しない。手動の再投入にも同じ時刻・状態検証を適用する。

LINEの再試行キーは受理後24時間管理される。今回の自動再送は15分未満に限定し、この外部条件の中で動かす。受理済みの確認は端末への到達や既読の確認ではない。[LINE公式の再試行仕様](https://developers.line.biz/en/docs/messaging-api/retrying-api-request/)

## 失敗隔離と復旧

入力不正、家族列挙の失敗、キューへの保存失敗、家族内の読込失敗、外部送信失敗を分ける。家族内の一部データしか読めなければ、その家族の通知を送らない。別の家族は継続する。稼働率の数値目標は追加しない。

通知の記録はバックアップ対象とし、復旧後も期限前後の検証を省略しない。非個人情報の終端記録は35日保持。秘密・本文の復旧は保存期限を延長する理由にしない。実際のバックアップと復旧の構成はインフラ設計で具体化する。

ステージングと本番は配信先・キュー・記録・秘密・定時起動を分離する。BDDの筋書きを先に書き、部品ごと5〜8件・主要境界の結合テスト・全体行80%以上を維持する。受理後中断、同時実行、期限境界、他家族の失敗を自動テストし、実配信と15分以内のメール受信をステージングで確かめる。
