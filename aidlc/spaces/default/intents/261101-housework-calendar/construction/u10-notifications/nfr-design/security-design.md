# 安全性設計 — U10 お知らせ

## 信頼境界

NFR4.101〜NFR4.105、NFR5.101〜NFR5.102、NFR6.101を対象とする。通知入口は公開HTTPへ接続せず、許可した定時処理と内部キューからだけ呼ぶ。起動入力の種類・実在日付・月末・時刻を検証し、不正入力から家族の列挙や送信へ進まない。

家族部品が提供する内部のページ付き列挙だけが家族の範囲を決める。作るsystem文脈は通知入口の内部に限定し、一般利用者が渡すroleを信頼しない。C6〜C9の所有権を維持し、通知部品が他の部品のテーブルを直接読む形にしない。書き込みを許可するのは通知の記録とキューへの受け渡しだけ。権限は使用するテーブル・索引・操作ごとに列挙する。

## 内容と秘密の保護

- 外部通信は暗号化し、保存データも暗号化する。トークンは既存の秘密の保管場所から読む。受信メールアドレスは環境ごとの配備設定へ置く。
- キューの中身は論理通知の識別子と対象日のみ。名前・金額・本文・秘密・生のLINE識別子を入れない。
- 本文と送信先は保護された一時データとして分け、終端状態へ進めたら直ちに除去する。中断したデータも毎時の清掃で予定時刻から23時間以上の本文を除去する。
- 清掃が遅れても24時間以後は本文を取得する窓口が返さない。清掃失敗と24時間超の残留を監視し、残留があれば障害として扱う。保存先の自動削除だけに24時間という条件を委ねない。
- 重複防止記録は本文・宛先を取り除いて35日保ち、その後削除する。古いイベントは記録の有無にかかわらず時刻で拒否する。
- ログ・メールは許可項目から組み立てる。任意の例外や外部応答の本文を連結しない。家族の運用識別子には秘密の鍵を使う非可逆変換を用い、鍵はログへ出さない。

## 同時更新の版

機能設計で条件付き更新のために使う版を具体化する。`version`は0以上の整数で初回0、更新成功ごとに1増える。状態・所有者・版をすべて更新条件へ含める。本文の固定後は本文とキーを変更しない。版の不一致は再読込し、別の所有者の処理を上書きしない。これは機能設計レビューの未定義項目を実装可能な条件へ具体化したものである。

## 検証

他家族のデータ混入、偽の起動、偽のsystem文脈、宛先の変更、版の競合、本文の期限切れ、秘密のログ漏れをテストする。共有AC1.2.4は、送信先なしで外部送信0回を明示して検証する。秘密検査が実行できなければ、配備前の未実施項目として残す。
