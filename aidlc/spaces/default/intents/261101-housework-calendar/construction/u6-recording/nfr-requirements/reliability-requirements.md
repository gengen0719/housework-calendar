# 信頼性の要件（Reliability）— U6 記録

U6（`u6-recording`）の信頼性の要件です。U1〜U5 の要件（NFR2.1〜NFR2.32、NFR6.1〜NFR6.6、NFR10.1、NFR10.2、NFR11.1〜NFR11.4）をそのまま使います。U6 で大事なのは、記録が「ちょうど 1 回」だけ、「全部そろって」書かれることです。家族がお小遣いの回数と金額を見る元になるデータなので、二重に数えたり、金額の抜けた「済」を作ったりしないことを要件にします。

## 書き込み

| ID | 要件 | 確かめ方 |
|----|------|---------|
| NFR2.33 | 「済」にする書き込みは、1 回の取引（`TransactWriteItems`）で、担当の更新（`status`、`recordedAt`、`recordedBy`、`unitPrice`、`updatedAt`、`version`）、月が確定していないことの確かめ、種類の単価が読んだ値のままであることの確かめを、同時に行う。取引は全部成功するか、全部書かれないかのどちらかで、`status` が「済」で `recordedAt`・`recordedBy`・`unitPrice` のどれかが空の担当を作らない。記録の更新は、担当を作らず、消さず、`origin` を変えない（BR7.6） | 取引を失敗させる差し替えで、担当が「未」のまま、`version` も変わらないこと。成功したあとの担当で、「済」ならば 3 つの項目が必ずそろっていること |
| NFR2.34 | 取引の条件で断られたら（担当が変わった、`version` が違う、月が先に確定した、単価が先に変わった）、読み直して BR7.4 の確かめを最初からやり直す。やり直しは 1 回まで。やり直しても断られたら `INTERNAL`（もう一度押してもらう）にして、何も書かない。「競合」として扱うのは、`ConditionalCheckFailed` と `TransactionConflict` だけで、ほかの取り消しの Code（`ThrottlingError` など）は、投げ直す（U5 の NFR2.31 と同じ `classifyCancellation`）。読み直しで分かれ方が変われば、その印（`MONTH_CONFIRMED`、`DUTY_CHANGED`、`DUTY_ALREADY_DONE` など）を返し、何も書かない | 取引の直前に、(a) 管理者の担当の変更（`version` が増える）、(b) 月の確定、(c) 種類の単価の変更、(d) 同じ担当の別の記録を差し込む差し替えで、それぞれ期待の印になること、単価の変更のあとは新しい単価が書き写されること。2 回続けて断らせたときに `INTERNAL` になり、3 回目の書き込みがないこと |
| NFR2.35 | 同じ担当が、2 回「済」になることはない。次のどの重なりでも、記録は 1 件、`recordedAt` は最初の時刻、`unitPrice` は最初に書き写した単価のままにする。(a) 同じ LINE のイベントの再送（U1 の二度処理しない記録。BR2.7）、(b) 同じ子供が短い間に 2 回押す（別のイベント。BR7.8）、(c) LINE と画面の同時の記録、(d) 2 つの要求が同時に届く（片方だけが書き、もう片方は読み直して最初の結果を返す）。2 回目以降の要求は、すでに自分が記録していれば、書かずに成功として最初の結果を返す（`alreadyRecorded=true`）。管理者が先に「済」にしていれば `DUTY_ALREADY_DONE`。`onDutyRecorded` は、書けた 1 回についてだけ 1 回呼び、`alreadyRecorded` の結果と、取引をやり直した同じ記録について 2 回呼ばない（BR7.14） | 同じイベントを 2 回、別のイベントで同じ担当を 2 回、2 つの要求を同時に（条件つきの書き込みの動きを再現した差し替えで）送って、書き込みが 1 回で、記録が 1 件で、最初の時刻と単価のままであること。`onDutyRecorded` の呼び出しが 1 回であること |
| NFR2.36 | 「担当が変わった」場合（見せたあとに、管理者が担当の子供を変えた、取り消した、「×」にした、日付をまたいだ、月が確定した）は、何も書かず、BR7.5 と機能設計の表のとおりに返す。LINE では今の選択肢を付けて出し直し、記録できる担当がなくなっていれば「今日記録できる担当はありません」にする。月が確定していれば「この月は確定済みです」だけにする | 機能設計の表の印ごとに、LINE の返事と出し直しの有無、画面の応答と読み直しが一致すること |

## 失敗のときの扱い（LINE）

| ID | 要件 | 確かめ方 |
|----|------|---------|
| NFR2.37 | LINE のイベントの処理の失敗を、3 つに分ける。(a) 取引の読み直しが 2 回続けて断られた（`INTERNAL`）: 本人にだけ「うまく記録できませんでした。もう一度お試しください」と reply し、イベントは処理済みにして 200 を返す（U3 の NFR2.18 と同じ形）。(b) 思いがけない例外（DynamoDB に接続できない、`ThrottlingError` など）: U1 の NFR2.2 のとおり「処理中」の記録を消して 500 を返し、LINE に送り直してもらう。このとき reply トークンは使わない（送り直されたイベントで返事ができるようにするため）。送り直しても、記録は NFR2.35 で二重にならない。(c) 書けたあとに reply が送れなかった（トークンの期限切れ、LINE の障害）: 記録を取り消さず、警告のログ（`LINE_REPLY_FAILED`）だけ残して、イベントは処理済みにする。500 にしない（返事のトークンは 1 回しか使えないため。U3 の NFR2.20 と同じ）。子供は、もう一度「やった」を押すと、「済 16:42」の選べない並びで記録されたことを確かめられる | (a)(b)(c) それぞれを起こす差し替えで、返事の有無、ステータス（200、500）、イベントの記録（処理済み、消える）、記録の有無が上のとおりであること。(b) のあとの再送で記録が 1 件になること |
| NFR2.38 | 記録に必要な読み取りに失敗したとき、書き込みに進まない。種類の今の単価が読めない、または種類がない（`NOT_FOUND`）ときは `INTERNAL` として何も書かない（BR7.7）。利用者の読み取りの失敗は思いがけない例外として NFR2.37 の (b)。(a) と NFR2.38 の境目は、読み取りが例外で失敗したもの（単価・利用者の読み取りの失敗）は例外なので (b)、読み取りは成功して種類が見つからない `NOT_FOUND` は `INTERNAL` として返す結果なので (a)、とする。LINE の API が止まっていても、記録の保存はできる（返事を送れないだけ。NFR2.37 の (c)）。記録の経路は LINE への問い合わせ（プロフィールの取得）に頼らない | 単価の読み取りの失敗と種類なしの差し替えで、担当が「未」のまま残ること。LINE の API を失敗させても、記録が残ること |
| NFR2.39 | `onDutyRecorded` の登録された関数が投げても、記録の結果は変えず、警告のログ（`DUTY_RECORDED_HOOK_FAILED`。担当の ID だけ。名前は書かない）を残す（BR7.14）。U8 までは登録がなく、何もしない | 登録した関数が投げる差し替えで、記録が成功のまま返ること、ログが残ること。登録がないとき何も起きないこと |

## データと時刻

| ID | 要件 | 確かめ方 |
|----|------|---------|
| NFR6.7 | 記録のデータ（担当の `status`、`recordedAt`、`recordedBy`、`unitPrice`）は、アプリの操作（LINE の記録と画面の記録）でだけ変わる。U6 は、本番のデータを書き換えるスクリプト、一括の修正の手順、自分で「済」を取り消す入口を作らない（BR7.13）。間違って記録したときの直し方は、管理者が画面で取り消す（U7。FR6.2）ことで、U6 では作らないため、取り消しの確かめは U7 の受け入れ条件（AC6.1.x）に引き継ぐ。リッチメニューの設定はデータではなく、公式アカウントの設定で、手順に従って作り直せる（NFR10.7）。本番のテーブルは `RemovalPolicy.RETAIN`（U5 の NFR6.6） | U6 のコードに、`Calendar` の項目を直接書き換えるスクリプトと、取り消しの入口（API、postback、画面）がないこと。CDK の設定で `Calendar` が `RETAIN` であること |
| NFR11.5 | 「今日」と記録の時刻は、日本時間（`Asia/Tokyo`）で扱う。裏側は、要求の入口で裏側の時計の「今」を 1 回だけ取り（`options.now`）、(a) 今日の日付と月、(b) 担当の日付との比べ（今日より後か、今日か）、(c) `recordedAt` と `updatedAt` に同じ「今」を使う。LINE のイベントの `timestamp` と、画面や端末の時計は使わない（再送されたイベントの「今」が古くならないようにするため）。日付の計算は U5 の `packages/shared` の日本時間の関数を使う（NFR8.10）。`recordedAt` は UTC で保存し、表示だけ日本時間の時と分にする。すでに記録した担当の再送（`alreadyRecorded`）の返事は、最初の `recordedAt` の時刻を使う | 時計を差し替えたテストで、日本時間の 23:59:59.999（UTC の 14:59:59.999）と 0:00:00.000（UTC の 15:00:00.000）の記録が別の日の担当になること。再送の返事の時刻が最初の時刻であること |
| NFR11.6 | 日付またぎの扱いを確かめる。(a) 日本時間の 1 月 7 日 23:59 と 1 月 8 日 0:00 に今日の担当を記録すると、それぞれ 1 月 7 日と 1 月 8 日の担当が「済」になる（AC5.1.14）。(b) 1 月 7 日 23:59 に出した選択肢を 0:00 を過ぎて押すと、`NOT_TODAY_DUTY` として扱い、出し直す。(c) 月末（1 月 31 日 23:59 と 2 月 1 日 0:00）で、確定の確かめが担当の日付の月で行われる。(d) うるう年の 2 月 29 日と、12 月 31 日から翌年 1 月 1 日 | 上の (a)〜(d) の筋書きと、時計を差し替えた単体テスト |

## Assumptions & Open Questions

- [decision] 機能設計の BR7.17 と NFR2.37 (b) の食い違いは、NFR2.37 に合わせて決着しました。機能設計の BR7.17 と functional-spec の `INTERNAL` の行を直し（2026-11-09、理由: NFR 要件レビュー R-01）、本人へ返事するのは取引の読み直しが 2 回続けて断られたとき（(a)）だけ、それ以外の予期しない例外は reply せず 500 で LINE の再送に任せる（(b)。U1 の NFR2.2、U3 の NFR2.18 と同じ）としました。理由は、reply トークンを使い切ってから 500 で再送されると、再送された処理が黙って記録だけを書き、返事と実際が食い違うためです。「残り時間が足りないとき」は見ません。Lambda の時間切れ（30 秒）も (b) と同じ扱いです。LINE の再送がステージングと本番で有効なこと（U1 で有効にした設定）が前提で、再送が届かなかったときは、子供がもう一度「やった」を押せば状態を確かめられます
- [assumption] 書き込みの競合は、家族 4 人の量では、同じ担当を同時に押したときにほぼ限られます。1 回のやり直しで足りる見込みです
- 作り手への失敗の知らせ（15 分以内。NFR2）は U10 で入れます。それまでは、`INTERNAL` と 500 のログ（NFR2.40）を見て気づきます
