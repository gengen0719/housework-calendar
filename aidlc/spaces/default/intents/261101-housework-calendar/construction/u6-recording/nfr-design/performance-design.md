# 速さの設計（Performance Design）— U6 記録

U6（`u6-recording`）の速さの要件（NFR7.25〜NFR7.31）と、LINE の返事と画面の読みやすさ・押しやすさ（NFR9.6、NFR9.7）を、どう作るかを書きます。目標は、機能設計から預かった AC5.1.15（「20 回のうち 19 回以上で、3 秒以内に『記録しました』の返事が届く」）を中心に、すべて「95% が 3 秒以内」で、測るときは Lambda の起動の遅れ（コールドスタート）を含めます。サーバー側の補助の目標（NFR7.27）は 2,000 ミリ秒で、LINE の配送と端末の表示に 1 秒を残します。

## 時間の配分

下の数字は設計の目安で、確かめ方は NFR 要件のとおり、ステージングの LINE の実機で 20 回ずつ測ります（画面録画から読み取る）。

| 操作 | サーバー側の処理（暖まった状態） | 目安 | 起動の遅れを足したとき |
|------|------------------------------|------|----------------------|
| `record.do`（NFR7.25） | 署名の確かめ（CPU）→ `begin`（約 10 ms）→ 利用者の Query（約 10 ms）→ 担当の探索（GetItem 2 段、約 20 ms。種類の名前の Query は並行）→ 単価の GetItem（約 10 ms）→ 取引（約 30〜50 ms）→ LINE の reply（約 100〜300 ms）→ `markDone`（約 10 ms） | 500 ミリ秒以内 | 1.5 秒以内 |
| `record.list`（NFR7.26） | `begin` → 利用者の Query → 月の状態の GetItem + 今日の担当の Query + 種類の名前の Query（3 つ同時、約 15 ms）→ reply → `markDone` | 450 ミリ秒以内 | 1.45 秒以内 |
| 案内の返事（管理者・家族外・確定済み・担当なし） | 利用者の Query（+ 確定済みなら月の状態）→ reply | 400 ミリ秒以内 | 1.4 秒以内 |
| 画面の記録（NFR7.29） | `POST …/record`: 担当の探索（約 20 ms）→ 単価 → 取引 → `Duty` を返す。続けて `GET …/calendar`（U5。約 300 ms） | POST 250 ms + 読み直し 300 ms | POST 1.25 秒 + 読み直し 0.3 秒（同じ起動の遅れは 1 回） |

- 起動の遅れは、ARM64 の Node.js 22、メモリ 256 MB、まとめて小さくした 1 つのファイルで、`getConfig`（SSM の読み込み。モジュールで保持）を含めて **1 秒台**に収まる見込み（まだ測っていない。NFR 要件の仮定）。`Init Duration` は `REPORT` の行で読む
- サーバー側の目標 2,000 ms（NFR7.27）は、ここでは冷たい起動でも約 1.5 秒で収まる配分にしてある。LINE の Webhook の配送と端末への返事の表示は縮められないので、画面録画の時間とログの差から原因を分ける（下の「測り方」）
- 3 秒に届かないときの直し方は、NFR7.30 の 7. の順（配信物を小さくする → 起動時の読み込みをまとめる → メモリを 256 MB から 512 MB へ）。常に温めておく仕組み（Provisioned Concurrency など、費用がかかるもの）は使わない（費用 0 円。NFR1）

## 工夫（裏側）

- **読み取りを並行する**: 種類の名前の Query は、子供と分かった直後に始め、担当の探索（GetItem 2 段）と並行して走らせる。待つのは書く直前だけ（`reliability-design.md` の `settle`）。`record.list` では、月の状態、今日の担当、種類の名前の 3 つを `Promise.all` で同時に読む。**判断の順番は変えない**（読んだあとに BR7.4 の順で評価する）
- **読み取りの回数を絞る（BR7.17、NFR7.28）**: `record.do` は通常 9 回、取引の読み直しがあっても最大 14 回、`record.list` は 6 回（`scalability-design.md`）。担当の数、種類の数、家族の人数で増えない。月全体の Query（約 124 件）を記録のたびに読まず、今日の日付までのプレフィックスの Query にする（返る件数は種類の数まで）
- **LINE のプロフィール取得は呼ばない**: 友だちかどうかは保存してある `friendStatus` で見る（NFR2.38）。外への通信は reply の 1 回だけ（時間切れ 5 秒は U1 のまま。NFR7.31）
- **書き込みは 1 回の取引**: 担当の Update + 月の確かめ + 単価の確かめを 1 往復で行う（約 30〜50 ms）。確かめのための読み取りを別に挟まない
- **記録の処理を別のファイルにして、`line` の起動を重くしない**: 記録の関数（`recordDuty`、`listTodayRecordableDuties`、`onDutyRecorded`）は `services/recordingService.ts` に置き、`calendarService.ts`（U5 の保存の計画、上書きの印、チャンクなど大きい）を import しない。`recordingService` が頼るのは `calendarRepository`、`choreTypeService`、`familyMemberService` だけ。`line` のバンドルが U5 の保存の処理で太って、冷たい起動が遅くなるのを避ける。Build and Test で、`line` のバンドルの大きさの前後（U6 の前と後）を記録する（NFR7.30 の 7. の最初の手当て）
- **コールドスタートに効く作り**: DynamoDB のクライアントと日本時間の `Intl.DateTimeFormat`（`jstDate.ts`）はモジュールの先頭で 1 つだけ作る（U1、U5）。AWS SDK は Lambda のランタイムのものを使う（バンドルに入れない。U1 の `externalModules`）。`zod` は `line` の経路で使わない（画面用 API だけ。postback の data は正規表現）
- **返事の組み立ては CPU だけ**: Flex の carousel は素のオブジェクトを組み立てる関数（`lineApiService` に足す `buildRecordCarousel`、`buildTextMessage`）で、12 個のバブルでも 1 ミリ秒以内。LINE の SDK を入れない（NFR1.29）
- **返事を送り直さない**: reply は 1 回だけ。時間切れ・失敗でも再送しない（トークンが 1 回限り）。`markDone` を reply の後に置く U1 の順番は変えない

## 工夫（画面）（NFR7.29）

- **応答の `Duty` で先に「済」を出す**: `POST …/record` の 200 の応答（記録後の `Duty`。`status`、`recordedAt`、`recordedByName`）で、読み込み済みの月の担当を差し替えて「済 16:42 太郎が記録」を出す。続けてカレンダーを読み直して全体をそろえる（AC5.1.7 の読み直し）。ユーザーに見える「済」は POST の応答で出るので、`GET` の読み直しの時間を待たない（測定の終わりは「済」が最初に出た瞬間）。失敗（409 など）のときは、文言を出し、カレンダーを読み直す
- **押したらすぐ受け付けたと分かる**: 「記録する」を押したら、ボタンを押せなくして（`aria-busy`）送信中を示す。二重送信しない（サーバー側も二重押しを 1 件にする。BR7.8）
- **確認は画面の中の小さな部品**: 「1/5 皿洗いを記録しますか」の確認は、MUI のダイアログを `React.lazy` にしない（開く操作が速くなければならない）。最初に読むファイルに含める（小さい）
- **キャッシュしない**: 家族の誰かが「済」にした状態が古く見えないよう、画面の中のキャッシュは持たない（U5 と同じ）

## 測り方（NFR7.25〜NFR7.30）

測る環境は、ステージングに家族 4 人分のデータ（管理者 1 人、子供 3 人、種類 4 つ、1 か月分の担当約 124 件。U5 の NFR7.20 と同じ量）を、アプリの画面（割り当ての保存）で作ったものです。データを直接書き換えて用意しません。

| 目標 | 測ること | 回数 |
|------|---------|------|
| NFR7.25 | 実際の LINE のアプリで、「記録する」ボタンを押した瞬間から「…を記録しました（時:分）」が出るまで。画面録画（30 コマ/秒以上）から読み取る | 20 回（冷たい起動 10 回以上を含む） |
| NFR7.26 | 「やった」を押した瞬間から選択肢が出るまで（選択肢が出る返事 20 回）。担当なし・確定済み・管理者への案内・家族外への案内は各 3 回（全回の確認） | 20 回 + 各 3 回 |
| NFR7.27 | ログの `LINE_EVENT_DONE.durationMs` と `REQUEST_END.durationMs` の 95 パーセンタイル（`action` で `record.do` と `record.list` に分ける。`observability-design.md`）が 2,000 ms 以内 | 上の測定と同じ期間 |
| NFR7.28 | 呼び出しの数（単体テスト。DynamoDB のクライアントと `fetch` を差し替えて数える） | 担当 1・12・13 件、種類 4・10 個、読み直しの組み合わせ |
| NFR7.29 | 画面で「記録する」を押した瞬間から「済」が出るまで | 20 回（`api` の冷たい起動 10 回以上） |
| NFR7.31 | 返事の失敗で 2 回送らないこと、取引を 2 回断らせても 3 回目の書き込みがないこと（単体テスト） | — |

- **条件（NFR7.30）**: 担当は月の初回の保存だけで作られ、同じ日付と種類に担当は 1 件なので、1 つの家族が 1 日に記録できるのは多くて 4 件。20 回は (a) 5 日以上に分けて 1 日 4 件以内で測る、(b) 家族を複数用意して家族ごとに 4 件以内で測る、(c) 両方の組み合わせ、のどれかで行う。測定の日付、家族、回数を表に残す。「済」を「未」に戻す入口は U7 まで存在しないので、戻して用意し直さない。測る子供の今日の担当は、その日の最初の記録の前に、種類 4 つのうち 3 つ以上が「未」の状態から始める
- **冷たい起動を作る方法**: 20 回のうち 10 回以上は冷たい起動で行う。作る方法は次の 2 つだけ。(1) **コードが変わるステージングへの反映**（機能の変更や修正を含む反映のあとの最初の操作）、(2) 数十分以上要求を送らずに待つ。**環境変数や設定を手で書き換えて実行環境を入れ替える方法は使わない**（U5 の測定と違い、ステージングの設定を測定のために変えない）。日をまたぐ測定 (a) では、その日の最初の記録は冷たい起動になりやすく、5 日以上で 5 回以上は自然に含まれる。冷たい起動かどうかは `REPORT` の行に `Init Duration` があるかで見分け、10 回に届いたかを数えてから 20 回を数える（`line` と `api` で別々）
- **何を 1 回と数えるか**: NFR7.25 は「記録する」を押してから「記録しました」が出るまで。選ぶ前の人の迷う時間は含めない。失敗した回も 1 回と数え、3 秒以内に入れない。1 回も除かない
- **届かなかったとき**: 除外や目標の引き下げをしない。サーバー側の時間（NFR7.27）、冷たい起動の回数、DynamoDB の呼び出し数（NFR7.28）から原因を調べ、直してから、新しい日か新しい家族で 20 回を測り直す。前の表は残す
- **自動のテストに時間の目標を入れない**（NFR8.12）: ネットワークと LINE の配送に左右されて不安定になるため。自動のテストで確かめるのは呼び出しの回数の上限（NFR7.28）だけ。測定の手順は README に書き（NFR7.30、NFR10.7 と同じ節）、結果は Build and Test の成果物に表で残す（日時、環境、端末、20 回それぞれの時間と冷たい起動かどうか、サーバー側の `durationMs`、送信数の前後の比較、合格かどうか）

## 読みやすさ・押しやすさの確かめ（NFR9.6、NFR9.7）

### LINE の返事（NFR9.6）

| 確かめ | 方法 |
|--------|------|
| 状態を色だけで伝えない | 選べない並びは「皿洗い（済 16:42）」「掃除機（×）」の文字を付ける。バブルのボタンは「記録する」の文字 |
| 押す場所の高さ 44 ピクセル以上 | ボタンの高さの指定を LINE の標準の「大」相当にし、バブルの余白を含めて 44 ピクセル以上になる指定にする。値の対応は LINE の公式の資料でコード生成のときに確かめる |
| 文字と背景の色の差 4.5:1 以上 | LINE の標準の配色（既定）を使う。色を独自に指定する場合は、色の差を計算する単体テストを足す |
| 代替テキスト | `altText` を必ず付ける（型で必須にする）。「どのお手伝いを記録しますか」のように、通知や読み上げでも内容が分かる文 |

### 画面（NFR9.7）

| 確かめ | 方法 |
|--------|------|
| 文字と背景の色の差 4.5:1 以上 | MUI のテーマの色の組み合わせのコントラスト比を計算する単体テスト（U5 の NFR9.5 を U6 の画面に広げる。「やった」ボタン、確認、理由の文字、無効のボタンを含める） |
| 押す場所 44×44 ピクセル以上 | 「やった」「記録する」「やめる」の最小の大きさが、テーマで 44 ピクセル以上に決まっていることを確かめる単体テスト |
| 確認の動き | 開いたとき確認の中にフォーカスが移り、Esc と「やめる」で閉じ、閉じたあと元の「やった」ボタンにフォーカスが戻る。画面の筋書き（Gherkin）で確かめる |
| 送信中 | 「記録する」を押したらボタンを押せなくし、`aria-busy`（または無効の状態）で支援技術にも伝える |
| 状態が文字でも分かる | 記録できない担当は、ボタンの代わりに理由の文字を出す（「まだ来ていない日の担当は記録できません」「お母さんが『やらなかった』にしています」「この月は確定済みです」）。「済 16:42 太郎が記録」の文字。色だけで状態を伝えない |
| 対象の画面 | U6 で足す画面（カレンダー・日の詳細の「やった」、確認）。U5 までの画面の確かめは U5 のまま |

## ADR を立てない判断

速さの設計に独立した ADR は立てません。重要な判断（取引の形と読み直し）は `reliability-design.md` の ADR-U6-01、名前の読み方は `scalability-design.md` の ADR-U6-03 にあります。この文書の工夫は、それらの帰結（読み取りの並行、別のファイルへの分離）です。

## Assumptions & Open Questions

- [assumption] 各 DynamoDB の呼び出しの時間（約 10 ms）、取引（約 30〜50 ms）、reply（約 100〜300 ms）は設計の目安で、測っていません。ステージングの測定（NFR7.25〜NFR7.27）で違えば、配分を見直します
- [assumption] 冷たい起動の 1 秒台の見込みは、NFR 要件の仮定のままです。測って足りなければ NFR7.30 の 7. の手順で直します
- [assumption] `recordingService.ts` を `calendarService.ts` から分けると `line` のバンドルが小さく保たれる、という見込みは、バンドルの大きさの前後の記録（Build and Test）で確かめます。`choreTypeService.ts` が `calendarPort.ts` を import する関係は U4・U5 のままです
- 画面の「応答の `Duty` で先に『済』を出す」を採用します（F3-6 に反映済み。Minor 1/3）。200 応答の `Duty` で即「済」に切り替え、続けてカレンダーを読み直します（AC5.1.7 と両立。読み直しは続けて行う）。測定の終わりは「済」が最初に出た瞬間で、`GET` の読み直しを待ちません
- 画面の「やった」ボタンの置き場所と見た目は、U5 の画面に合わせてコード生成で決めます
