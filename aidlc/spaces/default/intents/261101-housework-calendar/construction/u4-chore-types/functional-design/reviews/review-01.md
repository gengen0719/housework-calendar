- 契約への追加は項目・操作・理由の印・文言を足すものだけで、契約の「足す変更は自由」の範囲に収まっています。

### 指摘

**R-01（Major）削除と U5 の割り当て保存の競合を、引き継ぎだけでは防げない**

- 場所: `construction/u4-chore-types/functional-design/rules.md` の BR5.9 と Assumptions & Open Questions の 2 つ目、`functional-spec.md` の F5 の 3
- 内容: 削除は「C8 `isChoreTypeAssigned` が false を確かめる → 削除する」の 2 段階です。U5 の保存は「C7 で種類があって『使う』ことを確かめる → 割り当てを保存する」の 2 段階です。この 2 つが交互に動くと、削除が C8 の確かめを通ったあとで U5 が割り当てを保存し、そのあとで削除が実行されます。その結果、存在しない `choreTypeId` を指す割り当てが残ります（AC2.1.7 の「完全に消える」と、カレンダーの整合が両立しません）。Open Questions の「U5 の保存のときに C7 で確かめて断る」は、U5 の確かめが保存の前なので、この順序では防げません。
- 直し方: 削除の手順を「(1) 先に `active=false` にする → (2) C8 `isChoreTypeAssigned` を確かめる → (3) 使われていれば 409 を返す（「使わない」のまま残るので、管理者が望んだ状態と近い。戻す必要があれば明記）→ (4) 使われていなければ削除する」に変えます。あわせて、U5 の保存は「種類が『使う』であること」を保存と同じ書き込みの条件にする（確かめと保存の間に隙間を作らない）ことを、U5 の機能設計への引き継ぎとして書きます。(1) の `active=false` が先に入るので、(2) のあとに新しい割り当てが入ることはなくなります。

**R-02（Major）`getCurrentUnitPrice` と `list` が「使わない」の種類にどう答えるかが決まっていない**

- 場所: `functional-spec.md` の「契約への追加」の C7 の行（`create`・`update` だけ書かれ、`list`・`getCurrentUnitPrice`・`delete` の結果の決まりがない）、`rules.md` の BR5.7、BR5.8
- 内容: FR2.3 は「新しい割り当てでは選べない」だけを禁じ、すでに作られた担当や過去の記録は残すとしています。そのため、「使わない」にしたあとでも、すでにある担当の記録（U6）や管理者の「済にする」（U7、FR6.3）は、その種類の今の単価を必要とします。契約の C7 は `getCurrentUnitPrice(...): integer | NOT_FOUND` としか書いておらず、U4 の設計もこれを決めていません。実装者が「使わない」を NOT_FOUND にすると、「使わない」にした種類の記録ができなくなります（ADR-003 の書き写しが成り立たなくなります）。
- 直し方: BR5.7 に「`getCurrentUnitPrice` は『使わない』の種類にも今の単価を返す。NOT_FOUND は種類がない、または他家族のときだけ」と書きます。BR5.8 に「`list` は『使わない』も返し、U5 は `active` で絞る」と明記します。C7 の `list`・`getCurrentUnitPrice`・`delete` の結果の型も、契約への追加の表に並べます。

**R-03（Minor）名前の重複を防ぐ仕組みと、比べ方の細部が足りない**

- 場所: `rules.md` の BR5.3、`entities.md` の name の constraints と Assumptions & Open Questions
- 内容: 「同時に同じ名前で登録されても 1 つだけ」は結果の約束だけで、守り方が書かれていません。DynamoDB 系の保存先では、重複を防ぐ一意の印（家族と正規化した名前の組）を、種類の保存と同じ書き込みで取る作りが要ります。この約束は、名前の変更（PUT）にも同じように必要ですが、BR5.3 は「登録」の同時実行しか書いていません（2 つの種類を同時に同じ名前へ変えられます）。また、「20 文字」の数え方（コードポイントか UTF-16 か。絵文字や結合文字）、改行などの制御文字の扱い、全角の空白を「前後の空白」に含めるか、が書かれていません。
- 直し方: BR5.3 に、登録と名前の変更の両方で「名前の一意の印を、保存と同じ書き込みで取り、取れなければ 409」と書きます。名前の数え方（例: Unicode のコードポイント。前後の空白は全角を含める。制御文字は断る）を entities.md に 1 行足します。

**R-04（Minor）古い画面からの全項目の PUT が、「使わない」や単価を気づかずに戻す**

- 場所: `functional-spec.md` の F3・F4（PUT は全項目を送り直す）、`rules.md` の Assumptions & Open Questions の 3 つ目
- 内容: 「あとから保存したほうが残る」と受け入れていますが、被害は単なる上書きでは済みません。古い画面で名前だけを直して保存すると、別の画面で行った「使わない」（`active` の値）や単価の変更が、気づかないまま元に戻ります。単価は金額に直結します（FR2.2）。また、DELETE を送り直すと、1 回目が成功していれば 2 回目は 404 になり、画面に失敗が出ます（BR5.12 は POST だけが対象）。
- 直し方: PUT に `updatedAt` を添えて送り、保存の条件にして、食い違えば 409（再読み込みを促す）にします。または、「使わない／使う」を PUT と分けた操作にします。DELETE の送り直しで 404 が返っても、画面は「すでに消えています」として一覧を更新する、と F5 に 1 行足します。

**R-05（Minor）同名の種類が「使わない」のときの断りの文言が、役に立たない**

- 場所: `rules.md` の BR5.3、`functional-spec.md` の C10 の `CHORE_TYPE_NAME_TAKEN` の文言
- 内容: 重なる相手が「使わない」の種類のとき、「別の名前で登録してください（例: 皿洗い（追加分））」とだけ出ると、管理者は一度「使わない」にした「皿洗い」を作り直せないと受け取ります。本当は、その種類を「使う」に戻せば足ります（Q4 の A）。Q1 の「追加分で促す」意図は、本当に 1 日に 2 回あるお手伝いのときの案内であり、この場合には合いません。
- 直し方: 重なる相手の `active` が false のときは、別の文言（例:「『使わない』になっている同じ名前の種類があります。『使う』に戻すか、別の名前で登録してください」）を出します。理由の印は同じ 409 で、文言だけ分けます。

**R-06（Minor）単価の入力の型の扱いと、上限なしの代償が決まっていない**

- 場所: `rules.md` の BR5.5、`entities.md` の unitPrice と Assumptions & Open Questions の 1 つ目
- 内容: JSON の `"100"`（文字列）、`1e3`、`100.0` を整数として受けるのか断るのかが決まっていません（AC2.1.2 は「小数」を断ると言うだけです）。また、上限なし（Q2 の答え C）のままで安全な整数の最大値（約 9000 兆）まで受けると、U9 の「単価 × 回数」の合計や月の合計が安全な整数を超えて、お小遣いの計算が壊れます。Q2 の答えを変える必要はありません。
- 直し方: BR5.5 に「JSON の数値で、整数のものだけ受ける（文字列は 422）」と書きます。U9 の機能設計への引き継ぎとして「合計が安全な整数を超える場合の扱い（例: 計算前に断る）を U9 で決める」を Open Questions に足します。

**R-07（Minor）部分的にしか U4 で確かめられない受け入れ条件が、すべて OK になっている**

- 場所: `construction/u4-chore-types/functional-design/traceability.json` の coverage（AC2.1.4、AC2.1.5、AC2.1.6）
- 内容: functional-spec.md の対応表は、AC2.1.4（金額は U9、書き写しは U6）、AC2.1.5（選べないことは U5）、AC2.1.6（使われたかは U5 でつなぐ）を「U4 で作る範囲」に限ると正しく書いています。しかし traceability.json は 3 件とも `OK` のままで、部分的なことが機械で読む形では見えません。また、U5 ができるまで C8 は常に false を返すため、AC2.1.6 の断る流れ（409）は、U4 の単体では確かめられません。
- 直し方: traceability.json の 3 件に、部分であることと引き継ぎ先の単位（U9・U6、U5、U5）を target か note で示します。AC2.1.6 の確かめのために、C8 の窓口を差し替えられる作りにして（テストで「使われている」を返せるようにして）、その旨を functional-spec.md に 1 行足します。

### まとめ

Critical はなく、Major は 2 件（R-01 削除と割り当て保存の競合、R-02 「使わない」の種類への単価の答え方）です。受け入れ条件の対応、Q1 の答えの反映、家族の範囲、契約との整合は保たれています。そのため冒頭の判定のとおり通しますが、R-01 と R-02 は後の単位（U5〜U7）の実装を左右するので、承認の前に直すことを勧めます。
