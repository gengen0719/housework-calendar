### 確かめたこと

U4 の nfr-requirements の 6 ファイルと traceability.json を、機能設計の rules.md・functional-spec.md、requirements.md の NFR4・NFR5、U1・U2 の security-requirements.md と突き合わせました。番号は U3 までの NFR4.33 の続きで NFR4.34〜NFR4.39 となっており、重なりはありません（grep で確認）。認可の順番（管理者の確かめ → 404）、家族の範囲（NFR4.35・NFR4.36・NFR1.17）、登録の送り直し（NFR4.39）は、機能設計の BR5.1・BR5.10・BR5.11・BR5.12 と合っています。費用は新しい AWS サービスを足さず（NFR1.16）、妥当です。質問を省いたことは、おおむね妥当です（新しい秘密の情報も LINE の操作もなく、決めることは U1〜U3 と機能設計の答えで決まるため）。ただし R-04 の単価の上限の扱いだけは、決めずに先送りした項目が残っています。Critical はなく、Major は 1 件なので、このまま次に進めます。次の指摘は、コード生成の前に直すか、コード生成の計画に書いてください。

### 指摘

1. **R-01（Major）PATCH の本文と、パスの種類 ID の確かめがない**
   - 場所: `nfr-requirements/security-requirements.md` の NFR4.37（入力の確かめ）
   - 内容: NFR4.37 は POST・PUT の本文（名前・単価・説明）だけを確かめる対象にしています。`PATCH /v1/chore-types/{choreTypeId}` の本文 `{ "active": boolean }` の確かめは、どこにも書かれていません。`"false"` のような文字列を真偽値として扱うと、「使わない」にしたつもりが「使う」になるおそれがあります。パスの `choreTypeId` の形（UUID）を先に確かめ、合わなければ DynamoDB を読まずに 404 にする要件もありません。U2 の NFR4.16 は印の形を先に確かめています。
   - 直し方: NFR4.37 に、次の内容を足してください。PATCH の `active` は JSON の true / false だけを受け、それ以外（文字列、数、欠けている）は 422 にする。PATCH では `active` 以外の項目を無視する。`choreTypeId` は形が合わなければ 404 `NOT_FOUND` にする。確かめ方に、`"false"`・`0`・本文なしでの PATCH が断られるテストを書きます。

2. **R-02（Minor）確かめの順番と、印の使い回しの扱いが POST・PUT・PATCH・DELETE で決まっていない**
   - 場所: NFR4.34、NFR4.36、NFR4.39
   - 内容: 管理者の確かめが 404 より先であることは書かれています。しかし、Idempotency-Key の 400、本文の 422、名前の重なりの 409、種類の 404 の並びは書かれていません。404 より先に 409 や 422 を返すと、ほかの家族の種類があるかどうかが漏れるおそれがあります。また U2 の NFR4.22 は、同じ印で操作や対象が違えば 422 `IDEMPOTENCY_KEY_REUSED` としていますが、NFR4.39 は「同じ印で 2 回送る」場合しか書いていません。
   - 直し方: 順番を「セッション → 家族のメンバー → 管理者 → 印の形 → 種類の 404（家族の範囲）→ 本文の 422 → 409」のように 1 行で決めてください。印の使い回し（別の本文や別の操作）は NFR4.22 と同じ扱いにすると明記します。

3. **R-03（Minor）名前・説明の文字の決まりが、機能設計と食い違っている**
   - 場所: NFR4.37 と `functional-design/rules.md` の BR5.2・BR5.3・BR5.6
   - 内容: NFR4.37 は「制御文字を断る」「コードポイントで数える」としていますが、BR5.2 には制御文字の決まりがなく、数え方も「文字」としか書かれていません。説明の改行（制御文字に当たる）を許すかどうかも決まっていません。名前の重なりは「ちょうど同じ」で比べるため、全角と半角の違いや、見た目が同じで中身の違う文字で、実質同じ名前が並んで登録できます。
   - 直し方: 機能設計と合わせて、次を決めてください。数え方はコードポイントでよいと BR5.2 に反映する。説明で改行を許すか許さないかを決める。名前の重なりの比べ方に、Unicode の正規化（NFC など）を使うか、使わないと理由つきで決める。

4. **R-04（Minor）単価の上限を先送りしており、確かめ方が足りない**
   - 場所: NFR4.37 と、脅威の表の「大きすぎる単価で…」の行
   - 内容: 上限は安全な整数（2^53−1）までです。この値を単価に付けても、U9 の「単価 × 回数」や月の合計はあふれます。表は「一部を受け入れる」とし、あふれたときの扱いは U9 に任せています。ただ、U9 に引き継ぐ内容と確かめ方が測れる形では書かれておらず、これは「決まっていないことがない」という質問を省いた理由と合いません。単価を変えられるのは管理者だけなので、被害は家族の中に限られます。
   - 直し方: U9 への引き継ぎとして「合計が安全な整数を超えるときは計算の前に断る」を、確かめ方つきの項目として残してください。または U4 で現実的な上限（例: 1,000,000 円）を決めます。この場合は [Q2]「上限なし」を人に確かめ直す必要があります。

5. **R-05（Minor）traceability.json の NFR5 の書き方が、セキュリティ要件と合っていない**
   - 場所: `nfr-requirements/traceability.json` の NFR5 の行と、`security-requirements.md` の冒頭
   - 内容: security-requirements.md は「NFR5.1〜NFR5.9 をそのまま使う」としていますが、traceability.json は `NFR5.1-NFR5.6` と書いています。U2 の NFR5.7 と U3 の NFR5.8・NFR5.9 が抜けています。NFR5.7 のログに印を書かない決まりは、種類の名前・説明をログに書かない NFR2.27 とも関係します。
   - 直し方: traceability.json を `NFR5.1-NFR5.9` に直し、NFR2.27 が名前と説明を書かない点を NFR5.4 とあわせて参照します。

6. **R-06（Minor）数に上限がないことと、一覧の読み方・書き込みの量の扱い**
   - 場所: `scalability-requirements.md` の NFR1.17、`performance-requirements.md` の注意書き
   - 内容: 種類の数に上限がなく（[Q6]）、一覧は 1 回で全部を返す前提です。DynamoDB の Query は 1 回で 1MB までしか返さないので、続きを読む処理がないと、数が多いときに一覧が途中で切れます。登録の回数の制限についても、U2 の NFR4.25 のような「管理者だけで、無料枠と同時実行数の中に収まる」という書き方がありません。
   - 直し方: NFR1.17 に「Query の続き（LastEvaluatedKey）を最後まで読む」と、確かめ方（1MB を超える件数のテスト、または件数を決めた上限）を足します。登録の回数の制限を付けない理由は、NFR4.25 と同じ形で 1 行書きます。

7. **R-07（Minor）PUT・PATCH・DELETE を CloudFront と Lambda の関数 URL が通す要件がない**
   - 場所: `security-requirements.md` の NFR4.34（および U1 の NFR4.13 の継承）
   - 内容: U1・U2 の画面用 API は主に GET・POST です。U4 は初めて PUT・PATCH・DELETE を使うため、CloudFront の許す HTTP メソッドの設定（既定は GET・HEAD のみ）と、CloudFront を通すヘッダーの確かめ（NFR4.13）が、これらのメソッドでも動くことを確かめる項目が必要です。ここが抜けると、ステージングで初めて 403 や 405 になります。
   - 直し方: 要件に「CloudFront の裏側への振り分けが PUT・PATCH・DELETE を許し、NFR4.13 の秘密のヘッダーの確かめが同じに働くこと」を足し、確かめ方に、ステージングでの 3 つのメソッドの実行を書きます。U3 ですでに許している場合は、それを参照するだけで足ります。

### 質問を省いたことの評価

大半は妥当です。新しい秘密の情報も LINE の操作もなく、U1〜U3 の仕組みを使うだけだからです。ただし R-04 は、決めずに先送りした項目が残っています。コード生成の前に、人に確かめるか、U9 への引き継ぎとして書き残してください。

### 結論

NFR4.34〜NFR4.39 は、認可の順番・家族の範囲・入力の確かめ・送り直しの大筋を、機能設計と U1〜U3 に合わせて満たしています。Major は R-01 の 1 件だけで、直し方も小さいため、このまま次に進めます。R-01 は NFR 設計の前に直してください。
