### Summary

主な根拠は、Q1〜Q5 どおりに FR7.1〜FR7.5 と AC7.1.1〜AC7.1.11 を設計に落とせていて、既存コードの上で成り立つことです。確かめた点は次のとおりです。(1) 申し出の保存は、Calendar の SWAP#<dutyId> を UpdateItem と取引だけで作成・取り下げ・引き受け・掃除できる。作成だけが項目を新しく作り、取り下げ・引き受け・フックは status=open の条件があるので、項目がなければ作らず断られる。line の権限（GetItem・Query・UpdateItem・ConditionCheckItem）で足り、SWAP# は M# の Query に入らない。(2) 引き受けの取引は、担当・申し出・月の 3 つの別の項目で、U5〜U7 の version・status 条件と、版が上がることで U6 の古いボタンや U5 の上書きの確認の印も正しく古くなる。先着 1 人は status=open の条件で守られる。(3) onDutyReassigned を呼ぶ書き込みは calendarService（api）だけで、line が呼ぶのは onDutyRecorded（recordingService）だけという主張は、コードの検索で正しいと確認した。U8 の引き受けが通知を呼ばないのも、同じ取引で accepted になるので矛盾しない。(4) 認可は runGroupOperation と BR9.3 で、グループの入口・1 対 1・管理者・家族外の各場合に漏れがない。reply だけで push は使わない。Critical や Major はなく、指摘はすべて Minor です。いちばん先に決めたいのは、月の確定時にフックが直列に走る件数と時間（NFR7）と、SET に dutyId がない点です。
