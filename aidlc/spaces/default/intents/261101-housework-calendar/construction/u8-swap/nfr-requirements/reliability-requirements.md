# 信頼性の要件（Reliability）— U8 代わりにやる

U8（`u8-swap`）の信頼性の要件です。U1〜U7 の要件（NFR2.1〜NFR2.53、NFR6.1〜NFR6.8、NFR11.1〜NFR11.7）をそのまま使います。U8 で大事なのは、次の 4 つです。(1) 担当の持ち主が移る書き込みが「全部そろって」だけ起き、一部だけ書かれないこと。(2) 同時に引き受けても成立するのが 1 人だけであること。(3) 申し出が有効かどうかの判断が、フックの成功・失敗・遅れに頼らないこと。(4) 本番のデータを手で書き換えずに、すべてアプリの操作で直せること。担当の持ち主が変わるとお小遣いの記録の持ち主も変わるので、二重に動かしたり、引き受けたのに担当が動かなかったりしないことを要件にします。

## 書き込み（取引の原子性と競合）

| ID | 要件 | 確かめ方 |
|----|------|---------|
| NFR2.54 | 3 つの書き込みは、どれも全部成功するか全部書かれないかのどちらかで、「一部だけ書かれた」状態はない（BR9.7、BR9.9、BR9.10）。(a) 申し出る: 申し出の項目の `UpdateItem`（`SWAP#<dutyId>`。条件は「項目がない、または `status` が `open` でない、または `dutyVersion` が今の担当の `version` と違う」）＋担当が読んだ値のままの `ConditionCheck`（`status`＝todo、`version`、`dutyId`、`childUserId`＝押した人）＋月が確定していない `ConditionCheck`。担当そのものは書き換えない。(b) 引き受ける: 担当の `Update`（`childUserId`＝引き受けた子供、`origin`＝swap、`version`＋1、`updatedAt`。条件は `dutyId`・`version`・`status`＝todo・`childUserId`＝`offererUserId`）＋申し出の `Update`（`status`＝accepted、`acceptedByUserId`、`acceptedAt`、`updatedAt`。条件は `status`＝open かつ `offerId` が同じ）＋月が確定していない `ConditionCheck` の 3 項目の取引。(c) 取り下げる: 申し出の `UpdateItem`（`status`＝withdrawn。条件は `status`＝open かつ `offerId` が同じ）。**不変条件**: 「担当の `childUserId` が引き受けた子供に変わった」と「申し出の `status` が `accepted`」は同時に起きる。担当の `status`・記録の項目（`recordedAt`・`recordedBy`・`unitPrice`）・`date`・`choreTypeId` は引き受けで変わらない。担当を作らず・消さない（U5〜U7 の引き継ぎ）。引き受けた子供の自分の担当に触れない | 取引を失敗させる差し替えで、(a)(b) で担当も申し出も元のまま、`version` も変わらないこと。成功したあとの状態が不変条件を満たすこと。引き受けのあと、担当の `status`・記録の 3 項目・`date`・`choreTypeId` が変わっていないこと。引き受けた子供の自分の担当の項目が書き換わらないこと |
| NFR2.55 | **引き受けは先着の 1 人だけ**（FR7.3）。2 人が同時に押しても、申し出の条件（`status`＝open かつ `offerId` が同じ）が片方だけを通し、成立するのは 1 人。負けた側は、担当・申し出・月の状態を読み直して、`OFFER_ALREADY_ACCEPTED`（「この申し出はもう引き受けられています」）か `OFFER_GONE`（その間に取り下げ・自動でなくなったとき）を受け取る。担当の `version` は 1 だけ増える。同じ子供が 2 回押したときは、2 回目に `OFFER_ALREADY_ACCEPTED`（BR9.9 の 4.）。申し出た本人が自分の申し出を引き受ける、管理者が引き受けることは、取引に進まず `CANNOT_ACCEPT_OWN_OFFER` | 条件つきの書き込みの動きを再現した差し替え（`Promise.all`）で、(a) 別々の 2 人の子供が同時に引き受ける、(b) 同じ子供が 2 回続けて引き受ける、(c) 引き受けと取り下げが同時、(d) 引き受けと管理者による担当の子供の変更が同時、の 4 通りで、最終の状態が 1 つに決まること（担当の持ち主が 1 人、申し出の状態が 1 つ、`version` の増えが 1 回）。ステージングで、2 つのテスト用の利用者がほぼ同時に押す確認を 3 回行い、成立するのが 1 人であること（手の確認。人の指の同時性は保証できないので、保証は単体テストの差し替えで行う） |
| NFR2.56 | 取引・条件つきの書き込みが条件で断られたら、担当・申し出・月の状態を読み直して、それぞれの判定の最初から評価する。やり直しは 1 回まで（最初の 1 回を含めて最大 2 回。U5 の NFR2.30・U6 の NFR2.34・U7 の NFR2.45 と同じ `MAX_ATTEMPTS`。BR9.15）。やり直しても断られたら `INTERNAL`（LINE は「うまく申し出られませんでした。もう一度お試しください」または引き受け用の文）にして、何も書かない。「競合」として扱うのは `ConditionalCheckFailed` と `TransactionConflict` だけで、ほかの取り消しの Code（`ThrottlingError`・`ProvisionedThroughputExceeded` など）は、投げ直す（U5 の `classifyCancellation`）。読み直しで分かれ方が変われば、その印（`OFFER_ALREADY_ACCEPTED`・`OFFER_GONE`・`ALREADY_OFFERED`・`MONTH_CONFIRMED`・`DUTY_NOT_TODO`・`NOT_FOUND`）を返して何も書かない | 取引の直前に、(a) 管理者が担当の子供を変える（`version` が増える）、(b) 月の確定、(c) 別の子供が先に引き受ける、(d) 申し出の取り下げ、(e) 同じ担当への別の申し出、を差し込む差し替えで期待の印になること。2 回続けて断らせたときに `INTERNAL` になり、3 回目の書き込みがないこと。`ThrottlingError` を起こす差し替えで、読み直しをせずに投げ直すこと |

## 申し出の有効さとフック

| ID | 要件 | 確かめ方 |
|----|------|---------|
| NFR2.57 | 申し出が有効かの判断（BR9.8）は、**読んだときの担当と月の状態と申し出の状態だけ**から行い、フックの成功・失敗・遅れ・未登録に頼らない。有効 ＝ (a) `status` が `open`、(b) 担当が見つかり `version` が `dutyVersion` と同じ、(c) 担当の `status` が todo で `childUserId` が `offererUserId`、(d) 担当の `date` が今日以降（日本時間）、(e) 担当の月が確定していない。FR7.5 の 4 つの終わり方（管理者が担当の子供を変えた、日が過ぎた、「未」でなくなった、月が確定された）は、どれもこの判断で「なくなった」になる。判断のために項目を書き換えない（読むだけ）。「担当の日が過ぎた」はイベントがないので、読んだときに今日と比べて決める。引き受け済み（`accepted`）は「引き受けられた」、`withdrawn`・`cancelled`・(a) が `open` で (b)〜(e) を満たさないものは「なくなった」として、返事を言い分ける。**確定の取り消しのあと**: フックが成功して `cancelled` になった申し出は戻らず、フックが失敗して `open` のまま残った申し出は (e) を満たして有効に戻る。この差を許容する（BR9.11。戻す処理を足さない） | フックを登録しない・投げる・遅らせる、の 3 通りのそれぞれで、FR7.5 の 4 つの終わり方と、(b)〜(e) の各条件を 1 つずつ外した状態で、`acceptSwap` が `OFFER_GONE` を返し、`offerSwap` が古い `open` を上書きできること。時計を差し替えたテストで、担当の日が今日（有効）と昨日（なくなった）になる境（日本時間の 23:59:59.999 と 0:00:00.000）。確定の取り消しのあとの 2 通り（`cancelled` のまま戻らない、`open` のまま有効に戻る）が仕様どおりであること |
| NFR2.58 | フックの登録と動きを確実にする（BR9.11）。(a) `registerSwapHooks` を、Lambda の実行環境ごとに**1 回だけ**呼ぶ。二重に登録しない（`hooks` の配列は追加するだけなので、2 回呼ぶとフックが 2 回動く）。呼ぶのは、`api` の起動の枠（`onDutyReassigned` と `onDutyRecorded` の両方）と、`line` の起動の枠（`onDutyRecorded` だけ。`line` に担当の子供を変える書き込みはない）。(b) 申し出の項目の `UpdateItem` に `status = open` の条件を付け、`SWAP#<dutyId>` の項目がない担当では**項目を作らない**（NFR4.81）。(c) 条件で断られたとき（項目がない、`open` でない）は何もせず、その `ConditionalCheckFailedException` を握りつぶす（警告を出さない。申し出のない担当の方がほとんどなので）。ほかの例外は呼び出し側（`notifyDutyReassigned`・`notifyDutyRecorded`）に投げ、保存・記録・確定の結果は変えずに警告のログ（`DUTY_HOOK_FAILED`・`DUTY_RECORDED_HOOK_FAILED`。`dutyId`・`kind` だけ）を残す。(d) 取引をやり直した 1 つの変更について、フックは 1 回だけ呼ぶ（U5 の NFR2.39・U6 の NFR2.35・U7 の NFR2.50 の引き継ぎ）。U8 は `acceptSwap` から `onDutyReassigned` を呼ばない（申し出は同じ取引で `accepted` になっており、取り下げる申し出が残らない。BR9.9） | 登録を 2 回呼んでも、1 つのイベントでフックが 1 回しか動かないこと（書き込みの回数で確かめる）。`api` と `line` の起動の枠を読み込んだあと、それぞれで `onDutyRecorded` に対するフックが動き、`line` では `onDutyReassigned` に登録がないこと。フックが投げる差し替えで、保存・記録・確定が成功のまま返りログが残ること。`acceptSwap` が成功したときにフックが 1 回も呼ばれないこと |
| NFR2.59 | 月の確定のときのフックの掃除は、**失敗しても、遅れても、途中で止まっても**、確定の結果と正しさを変えない（BR9.11、NFR7.46）。確定の書き込みが済んだあとに、「未」の担当の一覧を読む `loadMonth` が失敗したときは、成功のまま返し、警告（`CONFIRM_POST_READ_FAILED`。既存）を残す。一覧の読み取りが成功しても、300 件のうち一部のフックが失敗したら、残りは続け、失敗は 1 件ずつ警告で残す。掃除されずに `open` のまま残った申し出は、月が確定されたので (e) を満たさず「なくなった」と読まれる（NFR2.57）。フックの数は確定の時点で「未」だった担当の数を超えない。NFR7.46 の段階 2 の締め切りで打ち切った場合も、同じ扱い（`DUTY_HOOKS_TRUNCATED` に件数だけ残す） | 300 件のイベントのうち、(a) 10 件目のフックが投げる、(b) 一覧の読み取りが失敗する、(c) すべてのフックが投げる、の各差し替えで、確定が成功のまま返ること、残りのフックが続くこと、残った `open` の申し出が `acceptSwap` で `OFFER_GONE` になること |

## 失敗のときの扱い（LINE）

| ID | 要件 | 確かめ方 |
|----|------|---------|
| NFR2.60 | LINE のイベントの処理の失敗を、3 つに分ける（U6 の NFR2.37、U3 の NFR2.18・NFR2.20 と同じ形）。(a) 取引の読み直しが 2 回続けて断られた（`INTERNAL`）: そのグループに「うまく申し出られませんでした。もう一度お試しください」（引き受けは「うまく引き受けられませんでした。もう一度お試しください」）と reply し、イベントは処理済みにして 200 を返す。(b) 思いがけない例外（DynamoDB に接続できない、`ThrottlingError` など）: U1 の NFR2.2 のとおり「処理中」の記録を消して 500 を返し、LINE に送り直してもらう。このとき reply トークンは使わない。送り直しても、書き込みは NFR2.62 で二重にならない。(c) 書けたあとに reply が送れなかった（トークンの期限切れ、LINE の障害）: 書いた結果は取り消さず、警告のログ（`LINE_REPLY_FAILED`）だけ残して、イベントは処理済みにする。500 にしない。(d) **書き込みの後に投げる処理を置かない**（BR9.14）。返事の組み立てに必要な読み取り（名前、種類の名前）は、書き込みの前に済ませるか、失敗しても言い換えの値（「だれか」「お手伝い」）で続ける。書いたあとの例外で 500 にして再送されると、すでに書けた結果の返事が出ない状態になるのを避けるため | (a)(b)(c) それぞれを起こす差し替えで、返事の有無、ステータス（200、500）、イベントの記録（処理済み、消える）、書き込みの有無が上のとおりであること。(d) 返事の組み立て用の読み取りを書き込みのあとで失敗させる差し替えで、書いた結果が残り、言い換えの値で返事が出て、200 であること |
| NFR2.61 | 書き込みに必要な読み取りに失敗したとき、書き込みに進まない。担当の探索（`findDuty`）、申し出の `GetItem`、利用者の記録が例外で読めなければ、思いがけない例外として NFR2.60 の (b)。読み取りは成功して見つからない場合（担当なし、申し出なし）は、結果の印（`NOT_FOUND`・`OFFER_GONE`）で返し、書かない。種類が見つからないときは、返事の名前を「お手伝い」と言い換えるだけで、書き込みは止めない（BR9.14）。LINE の API が止まっていても、申し出・引き受け・取り下げの保存はできる（返事を送れないだけ。NFR2.60 の (c)）。申し出の経路は LINE への問い合わせ（プロフィールの取得）に頼らない | 担当・申し出・利用者の読み取りの失敗の差し替えで、何も書かれないこと。LINE の API を失敗させても、申し出・引き受け・取り下げが保存されること。`getProfile` が呼ばれないこと |
| NFR2.62 | 同じ操作が重なっても、二重に動かない。(a) 同じ LINE のイベントの再送: U1 の二度処理しない記録で止まる（BR2.7）。(b) 別のイベントの二重押し: 「申し出る」の 2 回目は `ALREADY_OFFERED`、「引き受ける」の 2 回目は引き受けた人には `OFFER_ALREADY_ACCEPTED`、「やめる」の 2 回目は `OFFER_GONE` を返し、何も書かない。(c) 書き込みの成功の後で処理が止まって再送された同じイベント: 二度処理しない記録が「処理中」のまま消されて再度届くので、読み直して現在の状態から判定する（申し出る → `ALREADY_OFFERED`、引き受ける → `OFFER_ALREADY_ACCEPTED`、やめる → `OFFER_GONE`）。書き込みの後に投げる処理がない（NFR2.60 の (d)）ので、この状況は DynamoDB の障害のような稀な場合だけ | 同じイベントを 2 回、別のイベントで同じ操作を 2 回、送って、書き込みの結果が 1 回分であること。(c) は、`markDone` を失敗させる差し替えで再送したとき、書き込みが二重にならず、決まった返事になること |

| ID | 要件 | 確かめ方 |

- [assumption] **残る危険（機能設計に戻す候補）。** 「担当を選ぶ」の書き込みが成功したのに reply が失敗すると（NFR2.60 の (c)）、申し出の項目は `open` で残るが、グループには「引き受ける」「申し出をやめる」のボタンが出ていません。機能設計では、同じ担当をもう一度選ぶと `ALREADY_OFFERED`（文だけでボタンなし）になり、ボタンを再び出す手段がありません。申し出た本人は、その日が過ぎるか、管理者が担当を変えるまで、取り下げられず、ほかの子供も引き受けられません。害は「その担当で代わってもらえない」だけで、データは壊れず（BR9.8）、reply の失敗自体が稀（トークンの期限切れ、LINE の障害）なので、U8 では**要件にしません**。気になるなら、`ALREADY_OFFERED` を申し出た本人に返すときだけ、ボタンを添えて返す変更が考えられます（機能設計の変更になるので、このステージでは決めず、承認の場で人に確かめてください）。**承認の場で人が決めること（明示の確認点）**: (1) このまま許容する（U8 では要件にしない。現状の扱い）、(2) 申し出た本人に `ALREADY_OFFERED` を返すときだけ「引き受ける」「申し出をやめる」のボタンを添える（機能設計 BR9.7・BR9.8 付近の変更。ほかの人に返すときは文だけのまま）。**決めた内容（(1) か (2) か、日付）は、この文書のこの項目と機能設計の `rules.md` に書き戻すこと**（(2) の場合は NFR の追加ではなく機能設計の変更として扱い、`docs/contract-changes-u8.md` にも残す）。決める前に次の段階へ進めない
- [assumption] 同じ子供が 2 回「引き受ける」を押したときの 2 回目の返事は、機能設計（BR9.9）どおり `OFFER_ALREADY_ACCEPTED`（「この申し出はもう引き受けられています」）で、引き受けた本人にも同じ文です。本人にとっては「引き受けました」の再表示のほうが親切ですが、機能設計の文言の決めを変えないため、ここでは触れません
- [assumption] NFR2.55 の「ほぼ同時に押す」ステージングの手の確認は、人の指の同時性に左右されるので、保証にはなりません。保証は、条件つきの書き込みの動きを再現した差し替えのテストで行います（U6 の NFR2.35 と同じ考え）

- [assumption] 確定の取り消しのあとに申し出が戻る差（NFR2.57）は、機能設計が許容したものを引き継ぎます。戻る場合も、担当の `version`・状態・日付が申し出たときのままなら、引き受けは正しく成立します
