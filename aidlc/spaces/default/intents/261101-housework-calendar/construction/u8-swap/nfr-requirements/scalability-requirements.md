# 量と費用の要件（Scalability）— U8 代わりにやる

U8（`u8-swap`）の量と費用の要件です。U1〜U7 の要件（NFR1.1〜NFR1.31、NFR3.1〜NFR3.13）をそのまま使います。U8 は LINE のグループ経路が中心ですが、**返事はすべて reply で、push は使いません**。LINE 公式アカウントの無料のメッセージ数（月 200 通。返事ではないお知らせは月 128 通の枠。NFR1）には 1 通も足しません。費用 0 円（NFR1）を、push を使わないことと、新しい課金対象を足さないことで守ります。

## 量の見込み

申し出は、家族 4 人（子供 3 人）で 1 か月に多くて数回です。1 回の申し出につき、LINE の操作は 3〜4 回（「家事交代」、担当を選ぶ、引き受ける、まれに取り下げる）で、`line` の Lambda の無料枠（月 100 万回）のごく一部です。保存するのは、申し出られた担当 1 つにつき `Calendar` の項目 1 つです（上限は担当の数。NFR3.14）。月の確定のときだけ、確定の時点で「未」だった担当の数（多くて数百）の条件つきの書き込みが `api` から出ます（NFR3.15、NFR1.34）。

## 要件

| ID | 要件 | 確かめ方 |
|----|------|---------|
| NFR1.32 | U8 は push を 1 通も使わない。返事はすべて reply トークンで、イベントが届いたグループ（1 対 1 の案内は 1 対 1）に送る。`push`・`multicast`・`broadcast`・`narrowcast` を使わない。1 回の返事は reply の呼び出し 1 回で、見出し・carousel・案内の 3 通以内にする（LINE の 1 回の reply の上限 5 通に収まる）。公式アカウントの無料のメッセージ数（月 200 通）の数え方に、U8 の操作は 1 通も足さない（返事は数に入らない前提。NFR1 の「返事ではないお知らせは月 128 通」は U10 の枠）。申し出の「探しています」の知らせも、担当を選んだ人への返事として出すので push ではない。ほかの子供に個別に知らせる通知は作らない（FR7.2 は「グループに出る」で足りる） | 単体テストで、U8 のコード（一覧・申し出・引き受け・取り下げ・案内・フック）が LINE の API を `POST /v2/bot/message/reply` だけ、1 イベントにつき 0 回か 1 回呼ぶこと。`push`・`multicast`・`broadcast` を含む呼び出しが 1 件もないこと。ステージングの測定（NFR7.48）の前後で、公式アカウントの月の送信数（LINE の管理画面または送信数の取得）が増えないこと（返事は数に入らないことの確認も兼ねる） |
| NFR1.33 | U8 で新しく費用のかかる AWS のサービス、Lambda 関数、DynamoDB のテーブル・索引・TTL、CloudWatch のカスタム指標（メトリクスフィルター）、アラームを足さない（BR9.19）。申し出は U5 の `Calendar` の `SWAP#<dutyId>` の項目で、処理は U1 の `line` と `api` の Lambda に足す。ログは U1 の既存のログ（30 日。NFR2.7）に出す。権限と環境変数は足さない（NFR4.82）。指標とアラームは U10 で入れる（U10 が U8 の失敗のイベントも対象に入れる。NFR2.66） | CDK のテストで、U8 の前後に、テーブル・索引・Lambda・ログのグループ・指標・アラームの数が変わらず、`line`・`api` の権限と環境変数が変わらないこと |
| NFR1.34 | フックによる DynamoDB の従量の書き込みを、小さく保つ。フックは 1 回につき申し出の項目への条件つきの `UpdateItem` 1 回で、月の確定のときは確定の時点で「未」だった担当の数（多くて 300 件）だけ動く。条件に合わず断られる書き込みも 1 書き込み分の容量を使う。見積もり（未確認）: 300 件の書き込みは、オンデマンドの書き込み 300 単位で、1 回の確定あたり 1 円に遠く及ばない。確定は 1 か月に数回なので、U8 による DynamoDB の追加の費用は月に 1 円に満たず、AWS の請求額は 0 円のまま（NFR3.12 と同じ前提）。料金の単価は、コード生成で公式の料金表を確かめて数を残す | 単体テストで、フックの書き込みが「渡されたイベントの数以内」であること（余計な読み取り・書き込みがない）。毎月の請求を作り手が見る（NFR1.5）。ステージングの測定（NFR7.46）の前後で、`Calendar` の書き込みの数が想定の範囲であること |
| NFR3.14 | 申し出の項目の数と置き方を小さく保つ。項目は担当 1 つにつき 1 つ（`SWAP#<dutyId>`）で、1 つの担当に出せる申し出は 1 つ（FR7.5）。数は申し出られた担当の数以下、1 家族・1 か月に多くて 300 件、1 項目は数百バイトなので、1 年で 1 MB に満たない。引き受け・取り下げ・自動でなくなったあとも項目を残す（`Calendar` に TTL はない）が、件数が小さいので費用にも読み取りにも影響しない。`SWAP#` は `M#` と重ならないので、U5 の月の Query（`begins_with M#<month>#`）と種類の使用の確かめ（`begins_with M#`）には入らない。**家族のパーティション全体を読む Query（`begins_with` のないもの）を書かない**（項目が増えても読み取りが膨らまないようにするため）。Scan・BatchGetItem・BatchWriteItem も使わない。申し出の読み取りは、キーを指定した `GetItem`（強い整合性）だけ | 単体テストで、U8 のコードの `Query` がすべて `begins_with` を持つか、月の状態・種類の既存の Query であること。`Scan`・`BatchGetItem`・`BatchWriteItem` が 0 回であること。月の Query の結果に `SWAP#` の項目が混ざらないこと。担当 1 件、124 件、300 件でも、読み取りの回数が NFR7.44 の上限に収まること |
| NFR3.15 | 月の確定のフックの件数に比例して応答が伸び続けないよう、フックの並行数を制限する（BR9.11 の (b)。NFR7.46 の方針）。`notifyDutyReassigned` は、イベントを**最大 4 件ずつ並行**して呼ぶ（変えてよい範囲は 2〜5。5 にするのは `Calendar` のスロットルが 0 のままのときだけ）。1 つのイベントに登録された関数は、登録の順に待つ。並行数は 1 つの定数にまとめ、読みやすい名前を付ける。`Calendar` の項目は同じ家族の同じパーティションキーに集まるので、毎秒の書き込みを 1 つのパーティションの目安（毎秒 1,000 件）に収める。測定のとき、DynamoDB のスロットル（`WriteThrottleEvents`）が 0 であること。スロットルが出たら並行数を下げる | 単体テストで、300 件のイベントを渡したとき、同時に動く関数が 4 件を超えないこと、すべてのイベントが 1 回ずつ呼ばれること、関数が投げても残りのイベントが続くこと。ステージングで NFR7.46 の測定をし、`WriteThrottleEvents` が 0 であること |
| NFR3.16 | 返事の大きさを小さく保つ。「家事交代」の carousel は 1 バブル 1 担当で、**10 件まで**（LINE の carousel の上限 12 バブルに収まる）。候補が 11 件以上のときは、案内の文を 1 通添える（BR9.6）。1 回の返事は 3 通以内。一覧の読み取りは、担当の数で増えない（今月と来月の月の Query 各 1 回。NFR7.44）。`line` の同時実行の上限（U1 の NFR1.6、NFR3.6）は U8 で変えない | 単体テストで、候補が 1 件、10 件、11 件、124 件のとき、carousel のバブルが 10 以内で、案内の通が 11 件以上のときだけ付くこと。CDK のテストで `line` の同時実行の設定が U1 の決めた値のままであること |

## Assumptions & Open Questions

- [assumption] LINE の reply の送信は、公式アカウントの無料のメッセージ数（月 200 通）に数えられない、という前提です（U6 の NFR1.24 と同じ）。公式の説明をこの段階では確かめられていません。ステージングの測定の前後で送信数が増えないことを見て確かめます（NFR1.32）。数えられるとわかった場合は、NFR1 の枠の見積もりを見直す必要があります
- [assumption] DynamoDB のオンデマンドの料金の単価と、「条件で断られる書き込みも 1 書き込み分を使う」は、公式の説明をこの段階では確かめられていません。費用の見積もり（NFR1.34）は、数字を小さく見積もっても 1 円に満たない桁なので、結論は変わらない見込みです。コード生成で公式の料金表と照らします
- [assumption] 申し出の項目を消さずに残す（TTL なし）件数は、1 年で数千件以下と見ています。これが増え続けても、読み取りは `GetItem` だけで、`SWAP#` を一括で読む処理がないので影響しません。長く運用して気になったときの掃除の手順は、運用の段階で決めます（本番のデータを手で書き換えない。NFR6.9）
- [assumption] 並行数 4 は、1 つのパーティションの目安（毎秒 1,000 件）と、1 回の `UpdateItem` が 5 ミリ秒前後という見積もり（未測定）からの値です。測定で変えます（NFR7.46 の段階）
