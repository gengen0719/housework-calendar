# U11 安全性要件

## Requirements

| ID | 目標 | 確認方法 |
|---|---|---|
| NFR4.201 | 登録・削除の全要求で認証・所属・管理者を確認し、対象の子供と行は家族の範囲内だけ。認証情報のない要求・子供の要求・他家族のIDを100%拒否し無変更とする | APIと部品の拒否試験。共通AC1.1.12、AC8.2.4を明示して登録と削除の両方で検証 |
| NFR4.202 | 家族と作成者は信頼したコンテキストから決定。月・ID・kind・金額・理由を境界で検証する。理由をマークアップとして実行しない | 偽造familyId、金額文字列/小数/範囲外、空白、101文字、制御文字、HTML、別家族の操作キーの試験 |
| NFR5.201 | 新しい秘密情報を増やさず、既存環境の安全な設定読込を継承する。理由・金額・子供の名前・生の家族ID・認証トークンを運用ログやエラー通知へ出さない | ログ捕捉・エラー応答検証。リポジトリの秘密検査は使用可能な既存のコマンドで実施、未導入なら未検証を明示 |
| NFR10.201 | 二環境の保存先・秘密・実送信設定の分離を維持し、U11の変更で通知を有効化しない | 構成差分と環境分離の回帰試験。実通知は別途の有効化確認後 |

## Threat Considerations

IDの推測、本文による家族の差替え、子供からの直接API呼出し、他人の操作キー再使用、理由からのスクリプト実行、確定前の古い画面の操作を対象とします。存在しない対象と別家族の対象は同じNOT_FOUNDにします。原文の理由をログへ残して調査する方式は採りません。

## Contract Clarification

機能仕様の「既存INVALID_INPUT」は、共有inception契約には列挙されていません。NFR設計・実装では既存ソースでの定義を確認し、なければ追加理由として宣言します。INVALID_REASONも追加理由です。既存理由を削除・変更せず、共有型・文言・API・画面を一緒に検証します（上流機能設計のR-03）。
