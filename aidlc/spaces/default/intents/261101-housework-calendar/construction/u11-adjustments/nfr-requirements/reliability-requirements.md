# U11 信頼性・訂正可能性の要件

## Requirements

| ID | 目標 | 確認方法 |
|---|---|---|
| NFR6.201 | 有効な金額を複数登録して合計が正確な整数範囲を超えても、管理者はアプリから加算減額の一覧を開き削除・訂正できる。合計の読取エラーに編集入口を依存させない。誤った丸めや部分合計を表示しない | 上限額の加算2件、上限額の減額2件、範囲内へ戻る削除、正負相殺の順序違い。画面とAPIの回復経路を結合検証 |
| NFR6.202 | 未確定の確認と行の保存/削除と操作結果の記録に途中状態を残さず、確定との競合で確定済み月への変更を0件とする | 確定/登録、確定/削除の並行試験、保存の途中失敗、10要求の同一キー再送で1件だけ |
| NFR6.203 | 成功済みの同じ作成要求は有効な操作記録の期間内で元の結果を返す。同じキーの異なる入力は拒否。対象の削除後も同じ作成の再送で復活させない | 応答喪失、確定後再送、削除後再送、キー衝突、記録の論理失効境界の試験 |
| NFR6.204 | 月状態と所有データの保護を維持したまま訂正できる。合計・内訳を保存して修復する方式は採らない。既存データの移行・手修正を不要にする | 加算減額なしの既存月と既存バックアップ復元手順の互換性検証。新規保存種別が既存バックアップ対象か設計で明記 |

## Recovery and Graceful Degradation

上流機能設計R-01への対処として、合計とは独立した内訳の読取・削除経路をNFR設計で具体化します。業務上限なしを別の金額上限へ置き換えません。範囲内の正負相殺は中間計算で失敗させず、最終結果を正確に判定します。保存の成否不明と、成功後の表示失敗を区別し、後者では新しい作成を促しません。
