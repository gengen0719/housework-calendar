# 安全の要件（Security）— U1 最初の形と家族を作る

U1（`u1-skeleton-family`）の安全の要件です。U1 は、認証、家族の範囲の確かめ、LINE から届いたことの確かめ、秘密の情報の扱いの仕組みを作り、あとの単位がそれを使います。

## 認証（誰が使っているか）

| ID | 要件 | 確かめ方 |
|----|------|---------|
| NFR4.1 | セッションは、LINE の ID トークンを LINE の決まり（契約 C4 の verify）で確かめてから発行する。チャネル ID が自分のものでない、期限切れのトークンは 401 で断る（BR2.1） | 偽の ID トークン、別のチャネルのトークン、期限切れのトークンで、セッションが出ないこと |
| NFR4.2 | セッショントークンは JWT とし、裏側の鍵で HMAC-SHA256（`HS256`）で署名する。確かめるときは `alg` を `HS256` に決め打ちし、ほかの `alg`（`none` を含む）は断る。中身は利用者の userId と期限だけ。期限は 1 時間 [Q2]。期限切れや署名の合わないトークンは 401 で断る（BR2.2） | 期限切れ、書き換えた、`alg` を変えたトークンが断られること |
| NFR4.3 | 画面はセッショントークンをメモリにだけ持ち、ブラウザの保存場所（localStorage、sessionStorage、Cookie）には書かない。開き直すたびに ID トークンから取り直す [Q3] | 画面のコードに保存場所への書き込みがないことを検査する |
| NFR4.4 | セッションの発行で、記録がない人とブロック中の人は LINE に友だちかどうかを問い合わせ（BR1.11）、それでも友だちでなければセッションを出さない。セッションを持つ人がそのあとブロックしたら、画面用 API は 403 `NOT_FRIEND` で断る（BR1.5） | 友だちでない LINE アカウントで、案内しか出ないこと |

## 認可（何をしてよいか）

| ID | 要件 | 確かめ方 |
|----|------|---------|
| NFR4.5 | 家族のデータの操作は、セッションの利用者の家族だけに限る。家族は URL や本文から決めない。メンバーでなければ 403 `NOT_FAMILY_MEMBER`（BR2.3） | ほかの家族のメンバーのセッションで、ほかの家族のデータが見えないこと |
| NFR4.6 | 管理者の操作は管理者だけ（403 `ADMIN_ONLY`）、ほかの家族のデータの ID の指定は 404 `NOT_FOUND`。U1 で仕組みを作り、各操作を作る単位で使う（BR2.4、BR2.5） | 仕組みの単体テストで、子供と別の家族の要求が断られること |

## LINE から届いたことの確かめ

| ID | 要件 | 確かめ方 |
|----|------|---------|
| NFR4.7 | LINE の Webhook は、`x-line-signature` をチャネルシークレットで確かめ、合わなければ何もせず 401 を返す（BR2.6）。署名は、受け取った本文のバイト列そのもの（Base64 で届いたら戻したもの）で計算し、JSON として読み直したものでは計算しない。比べるときは、時間で差が出ない比べ方を使う | 署名のない、書き換えた本文の要求が処理されないこと。正しい署名の要求が通ること |
| NFR4.8 | 同じイベントは二度処理しない（BR2.7）。思いがけない失敗のときだけ 500 を返し、LINE に送り直してもらう。業務の決まりで断ったときは 200 [Q1] | 同じイベントを 2 回送っても、記録が 1 回分であること |

## 秘密の情報

| ID | 要件 | 確かめ方 |
|----|------|---------|
| NFR5.1 | チャネルシークレット、チャネルアクセストークン、ログインのチャネル ID、セッションの署名の鍵は、Systems Manager のパラメータストア（SecureString）に環境ごとに置き、Lambda が起動したときに読む [Q5] | CDK の構成と Lambda のコードに秘密の値が書かれていないこと |
| NFR5.2 | リポジトリに秘密の情報を入れない。取り込み前の CI で秘密の情報がないかを検査する（`project.md` の Forbidden） | CI の検査が通ること |
| NFR5.3 | Lambda が読めるのは、その環境の自分のパラメータだけにする（ほかの環境のパラメータは読めない） | CDK の権限の設定で確かめる |
| NFR5.4 | ログに秘密の情報、ID トークン、セッショントークンを書かない | ログの出し方の単体テストで確かめる |

## 入力の確かめ

| ID | 要件 | 確かめ方 |
|----|------|---------|
| NFR4.9 | 画面用 API の本文は、型と長さを確かめてから使う。家族の名前は前後の空白を除いて 1〜20 文字（BR1.9） | 長すぎる名前、型の違う本文が 422 で断られること |
| NFR4.10 | 新しく作る操作は `Idempotency-Key` を必須にし、同じ利用者の同じ印は 1 回として扱う（BR2.8）。印は UUID（36 文字）の形だけを受け付け、ほかの形や長さは 400 `IDEMPOTENCY_KEY_REQUIRED` で断る | 同じ印で 2 回送っても家族が 1 つであること。形の違う印が断られること |

## 画面に悪いスクリプトを入れさせない

| ID | 要件 | 確かめ方 |
|----|------|---------|
| NFR4.11 | CloudFront の応答ヘッダーで、画面に Content-Security-Policy を付ける。スクリプトは自分のドメインと LIFF の SDK の配信元だけ、通信は自分のドメインと LINE の API だけを許し、インラインのスクリプトは許さない。あわせて `X-Content-Type-Options: nosniff`、`Referrer-Policy: strict-origin-when-cross-origin`、`Strict-Transport-Security` を付ける。許す配信元の細かい一覧は NFR の設計の段階で決める | ステージングで応答ヘッダーを確かめる |
| NFR4.12 | 画面では、利用者が入れた文字（家族の名前、表示名）を HTML として差し込まない。`dangerouslySetInnerHTML` を使わない決まりを ESLint で検査する | ESLint の設定で確かめる |

## CloudFront を通さない呼び出しを断る

| ID | 要件 | 確かめ方 |
|----|------|---------|
| NFR4.13 | Lambda の関数 URL は、CloudFront を通った要求だけを処理する。CloudFront が裏側への要求に秘密のヘッダー（値はパラメータストアに置く）を付け、Lambda はそのヘッダーがない、または値が違う要求を 403 で断る。この方法は、LINE の Webhook（本文の要約のヘッダーを付けない POST）でも使える。関数 URL の認証の設定（`NONE`）はこの前提で使い、OAC（CloudFront の署名）は使わない | 関数 URL を直接呼ぶと 403 になること |

## 反映（デプロイ）の権限

| ID | 要件 | 確かめ方 |
|----|------|---------|
| NFR5.5 | GitHub Actions から AWS への反映は、OIDC で一時的な権限を受け取る形にし、長く使える AWS の鍵をどこにも置かない。権限を受け取れるのは、このリポジトリの `main` への push（ステージング）と、保護した環境 `production` の手での実行（本番）だけにする | IAM のロールの信頼の設定で確かめる |
| NFR5.6 | 公開リポジトリなので、フォークからのプルリクエストのワークフローには AWS の権限も秘密の情報も渡さない。プルリクエストでは、テストと検査だけを動かす | ワークフローの設定で確かめる |

## 考えられる脅威と備え

| 脅威 | 備え |
|------|------|
| 偽の LINE の Webhook を送られる | NFR4.7 |
| 他人の ID トークンやセッショントークンを使われる | NFR4.1、NFR4.2（期限 1 時間）、NFR4.3（保存場所に残さない） |
| ほかの家族のデータを見ようとされる | NFR4.5、NFR4.6 |
| 公開リポジトリから鍵が漏れる | NFR5.1、NFR5.2 |
| 画面に悪いスクリプトを入れられ、トークンを読まれる | 入れさせない: NFR4.11（CSP）、NFR4.12。読まれても害を小さく: NFR4.3（メモリだけ）、NFR4.2（期限 1 時間） |
| 関数 URL を CloudFront を通さずに直接呼ばれる | NFR4.13 |
| 反映の権限を盗まれる、フォークから悪用される | NFR5.5、NFR5.6 |
| 大量の要求で費用がかかる（費用 0 円が崩れる） | `scalability-requirements.md` の NFR1.6、NFR1.7 |

## Assumptions & Open Questions

- 契約 C3 の「確かめたあとは処理の結果にかかわらず 200 を返す」は、NFR4.8 のとおり「思いがけない失敗のときだけ 500」に変わります [Q1]。この変更は、U1 のコード生成で LINE 用の受け口を作るときに反映し、`contract-summary.md` の C3 は U1 のコード生成の計画で直します。LINE の管理画面で Webhook の再送を、ステージングと本番の両方で有効にします
- 秘密の情報があるかの CI の検査に使う道具は、コード生成の段階で決めます
