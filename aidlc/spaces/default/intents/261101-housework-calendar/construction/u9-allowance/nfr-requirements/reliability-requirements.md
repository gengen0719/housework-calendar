# 信頼性の要件（Reliability）— U9 お小遣いの額

U9（`u9-allowance`）の信頼性の要件です。U1〜U8 の要件（NFR2.1〜NFR2.66、NFR6.1〜NFR6.9、NFR11.1〜NFR11.9）は、そのまま使います。ここでは U9 で足すものを、U8 の番号の続きで書きます。U9 は**読み取りだけ**で、何も書きません。そのため、取引の競合・二重実行・書き込みの途中失敗といった書き込みの論点はなく、論点は次の 4 つです。

- 読み取りが失敗したときに、一部だけの額を返さないこと（NFR2.68）
- 読んだ時点の「済」から、ずれなく額を計算すること（NFR2.69）
- ありえないデータがあっても画面が開けること（NFR2.70）
- 日本時間の月の区切りで、どの月に入るかが決まること（NFR11.10、NFR11.11）

決めることに、人に聞くものはありませんでした。ただし、NFR2.73 の「`role: system` の ctx で `listMembers` が動くこと」は、コード生成で既存の型と実装を直す必要があります（Open Questions）。

## 読み取りの性質

| ID | 要件 | 確かめ方 |
|----|------|---------|
| NFR2.67 | `GET /v1/months/{month}/allowances` と `getAllowances` は**読み取りだけ**で、何度呼んでも副作用がない（BR10.14）。その間に記録・状態の変更・代わりにやる・確定が入らなければ、同じ要求は同じ答えを返す（`Idempotency-Key` は要らない）。書き込みのコマンドを 1 回も使わない。額も回数も保存せず、キャッシュにも持たない（読むたびに「済」の担当から計算する。BR10.2、ADR-005） | 単体テストで、同じ要求を 2 回送って同じ答えになること。書き込みのコマンドが 0 回であること。保存した合計・キャッシュを読む処理がないこと（レビュー）。記録→読み→取り消し→読み、で 400円→300円に戻ること（S6、S7） |
| NFR2.68 | **読み取りが 1 つでも失敗したら、全体を失敗にし、一部だけの額を返さない**（BR10.7、BR10.13、F5）。対象は、認証以外の次の読み取り: 月の Query（続きのページを含む。途中のページの失敗も全体の失敗）、`listMembers`（Families、Users 索引、本人の補い）、種類の `list`、抜けた子供の確かめ（`findFamilyChild`）と名前の読み取り（`findDisplayName`。ただし `NOT_FOUND` は失敗ではなく「名前が分からない子供」にする。BR10.19）、家族の作成時刻。失敗したときの扱い: 窓口 `getAllowances` は例外を投げる（U10 が送信前に失敗に気づく。BR10.17）。画面用 API は 500 `INTERNAL`（決まった文。NFR4.93）。「読めなかった子供は 0 円」「読めなかった種類は名前なし」のような**代わりの値で続けない**（種類が一覧に「ない」ことと、一覧が読めないことは別: 前者は異常なデータ（NFR2.70）、後者は失敗） | 単体テストで、上の読み取りを 1 つずつ失敗させて、(1) 窓口が例外を投げ、(2) 画面用 API が 500 `INTERNAL` で、応答に `allowances` が（空でも）入らないこと。月の Query を 2 ページに分け、2 ページ目で失敗させたとき、1 ページ目だけの額が返らないこと。`findDisplayName` が `NOT_FOUND` のときは 200 で「名前が分からない子供」になり、別の例外のときは 500 になること |
| NFR2.69 | **ずれのない額**にする。(a) 担当と月の状態は強い整合性で読み（BR10.12）、記録・取り消し・やらなかった・済にする・代わりにやるの**直後に読み直せば**、その時点の「済」だけが数に入る（AC5.1.13）。(b) 1 回の要求の計算は、1 回の月の読み取りの結果だけから行い、同じ担当を 2 回読んで食い違いを起こさない（途中で記録が入っても、1 回の答えの中は 1 つの時点の読み取りで整合する。ページが複数のときのずれは許容する: 300 件で 1 ページのため、通常は起きない）。(c) 次の式を、どの答えでも守る。`amount = unitPrice × count`、`total = Σ lines.amount + Σ adjustments.amount`、`count` は 1 以上の整数、金額はすべて整数。計算の中で金額を 0 円以上に直さない（マイナスはそのまま。BR10.5）。(d) 結果整合の読み（Users 索引）の遅れは、記録のある子供を強い整合性で補う（BR10.6）。許容する差は、家族に入った直後の子供が、記録もないまま数秒だけ行に出ないこと | 単体テストで、(c) の式を、さまざまなデータ（単価 0 円、単価の変更、種類 10 個、子供 10 人、減額で合計がマイナス）で確かめる（子供ごとに `total` が行の和と一致すること、すべての金額が整数であること、マイナスが 0 円にそろわないこと。S27、S28）。(a) は S6・S7・S9・S10 の筋書き。(d) は索引に出ない子供に記録があるとき、行が出ること |
| NFR2.70 | **ありえないデータがあっても、画面を止めず、額を壊さない**（BR10.13）。(a)「済」なのに `unitPrice` が空（`undefined` か `null` のときだけ）の担当は、**数えず**、`ALLOWANCE_DUTY_WITHOUT_PRICE` を残す。(b)「済」の担当の種類が一覧にないときは、名前を「不明なお手伝い」にして内訳の最後に並べ、`ALLOWANCE_CHORE_TYPE_MISSING` を残す（金額は担当の `unitPrice` で数える）。(c) 担当の子供が管理者の ID のときは、行を作らず、`ALLOWANCE_DUTY_OWNER_NOT_CHILD` を残す（`findFamilyChild`・`findDisplayName` を呼ばない）。(d) **単価 0 円は有効な値で、異常ではない**（「0円 x N回 = 0円」の行を出し、ログも残さない。S14）。(e) 状態が「済」でない担当は、単価が入っていても数えない。(f) これらの異常があっても 200 を返し、ほかの子供・ほかの行の額は変わらない。(g) 異常のログは 1 回の要求で多くても種類ごとに 20 行まで（NFR2.75）。通常の書き込みでは起きない前提のため、起きたときは額が実際より少なく見えうる（画面に注意書きは出さない） | 単体テストで、3 種類の異常を 1 件ずつ入れて、(1) 200 で、異常な担当が数に入らず（(b) は入る）、ほかの額が変わらないこと、(2) 該当のログが出ること（NFR2.75）、(3) 単価 0 円の担当のログがないこと（S14、S30、S30b）。管理者の ID の担当で `findFamilyChild`・`findDisplayName` が 0 回であること |
| NFR2.71 | **空・0 円・端の場面**で、決めた形を返す。(a) 記録のない今いる子供: `lines`・`adjustments` が空で `total` が 0（行は出る。AC8.1.2）。(b) 子供がひとりもいなくて、その月の記録もない: `allowances` は空（200）。(c) 家族の作成より前の月、未来の月、`firstMonth`〜`lastMonth` の外の月: 200（計算して返す）。(d) 月の状態の行がない月: `confirmed` は false。(e) 抜けた子供でその月の「済」がない: 行を出さない。(f) 並びは決まった順（今いる子供は家族に入った順、続いて抜けた子供を表示名、`userId` の順。内訳は種類の並び、同じ種類では単価の低い順。BR10.4、BR10.6）で、同じデータなら毎回同じ順 | 単体テストで (a)〜(f) の筋書き（S2、S17〜S19、S26）。同じデータを 5 回呼んで、順序が毎回同じであること。同じ時刻・同じ表示名の子供が `userId` の順で並ぶこと |
| NFR2.72 | **画面（S5）の失敗と古い応答**。(a) 画面は「読み込み中」「表示できた」「失敗」の 3 つの状態を行き来し（F5、画面 S5 の状態図）、失敗では「表示できませんでした。もう一度お試しください」と「読み込み直す」を出す。「読み込み直す」は同じ月でもう一度読む（二重に何かが起きない。NFR2.67）。(b) 月の移動は次の 1 つの作りに決める（BR10.12）。[<] [>] は読み込み中も押せる。押すたびに目標の月だけを更新し（連番も進めて、押した時点より前の要求の答えは、待ち時間の間に届いても捨てる。答えの月で目標を書き換えない〔最初の答えを除く〕）、最後の押しから 250 ms（debounce）待ったあと、**最新の目標の月だけ**を要求する。要求には連番を付け、最新の番号の答えだけを描き、古い番号の答えは捨てる。月を移している間は、直前の月の内容を薄く残さず、読み込み中を出す。(c) 「飛んでいる要求（in-flight）」は、連番が最も新しい要求とする。押しのあとでなく（連番が進んでおらず）、目標の月が最新の連番の要求の月と同じときだけ、重ねて出さずその答えを待つ（最初の読み込みの二重の呼び出しと「読み込み直す」の連打が対象）。違う月のときは、新しい連番の要求を出す（2 月の要求が飛んだあと 3 月の要求を出し、2 月へ戻ったら、新しい連番の 2 月の要求を出して描く）。(d) 401 は画面の共通の扱い（ログインし直し）、403 `NOT_FAMILY_MEMBER` は「このアプリは家族のメンバーだけが使えます」、422 `INVALID_MONTH` は「月の指定が正しくありません」を出し、いずれも額を描かない。(e) 自動の読み直しはしない（開いたとき・月を移したとき・「読み込み直す」を押したときだけ読む。NFR1.38） | 画面のテストで、(a) 失敗の文言と「読み込み直す」が出て、押すと同じ月で読み直されること。(b) 2 月の要求が飛んだあと（待ち時間 250 ms が過ぎてから）3 月へ移して 3 月の要求も飛び、3 月の答えが先に届いてから 2 月の答え（古い番号）が遅れて届いても、3 月が描かれたままであること（S32。差し替えた時計で待ち時間を進めて作る）。(b2) 2 月の要求が飛んでいる間に [>] で 3 月にし、待ち時間が過ぎる前に 2 月の答えが届いても、2 月は描かれず、目標は 3 月のまま、待ち時間のあとに 3 月の要求だけが 1 回出ること（S32）。(c) 2 月の要求中に [>] [<] で 2 月に戻ると、押しで連番が進むので古い 2 月の答えは捨てられ、待ち時間のあとに新しい連番の 2 月の要求が 1 回だけ出て、その答えが描かれること（押した回数に比例して要求が増えない）。同じ月の要求が飛んでいる間の二重の呼び出しは、要求が増えないこと。さらに、2 月の要求が飛んでいる間に 3 月の要求も出してから 2 月へ戻ると、新しい連番の 2 月の要求が出て、その答えが描かれ、古い連番の 2 月の答えや 3 月の答えで上書きされないこと（最新の連番の要求の月は 3 月なので、重ね出しの抑止の対象外）。(d) 各エラーで額が描かれないこと。(e) 時間が経っても要求が増えないこと（タイマーの差し替え） |
| NFR2.73 | **お知らせ用の裏側（U10）から呼ばれても動く**（BR10.7、BR10.17、S34）。`getAllowances(ctx, month)` は `ctx = { familyId, role: system }`（利用者の ID がない）でも、家族の全員分の `Allowance[]` を返す。そのために、`listMembers` の「本人がいなければ `Users` を強い整合性で読んで足す」補いは、本人の ID がない ctx では**呼ばない**（`undefined` の ID で読まない）。管理者である必要はない。失敗は投げる（NFR2.68）ので、U10 は送る前に失敗に気づき、送信の失敗と同じ仕組み（15 分以内に作り手へ知らせる。NFR2）に乗せられる。U9 は可用性の数値目標を置かない（NFR2：稼働率の数値目標はない）。メンテナンスのとき以外は止めない | 単体テストで、`role: system`（利用者の ID なし）の ctx で呼び、(1) 家族の全員分が返る、(2) 本人の補いの `GetItem` が 0 回、(3) 読み取りを失敗させると例外を投げること（S34）。型の確認（`FamilyContext` に `system` を足す変更が既存の呼び出しを壊さないこと）は、コード生成で `tsc` と既存のテストで確かめる |

## Assumptions & Open Questions

- [assumption] **`role: system` の ctx への対応（NFR2.73）。** 既存の `FamilyContext` は `role` が `admin`／`child` で、`listMembers` は `ctx.userId` で本人を補います。機能設計は U10 が `{ familyId, role: system }` で呼ぶことを決めているので、U9 のコード生成で型と `listMembers` を直す必要があります（利用者の ID がない ctx では本人の補いを飛ばす）。`FamilyContext` を広げるか、`getAllowances` だけ別の型の ctx を受けるかは、コード生成で既存の呼び出しへの影響が小さいほうを選びます
- [assumption] 「ありえないデータ」の 3 種類（BR10.13）は、U5〜U7 の書き込みの決まりでは作られない前提です。起きたときは数えずにログへ残し、画面を止めません。数えない扱いが望ましくない場合（例: 価格がなくても 0 円で数える）は、機能設計の変更になるため、承認の場で人が決めてください
