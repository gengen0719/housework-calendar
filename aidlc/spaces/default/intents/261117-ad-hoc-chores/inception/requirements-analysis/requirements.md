# 日付ごとの臨時のお手伝い

## Intent Analysis

家族の管理者が日付の詳細を開き、定期的な月割り当てとは別に、その日だけのお手伝いを子供へ依頼できるようにする。例として「お昼ご飯を作る」などを臨時用マスタに登録して利用する。

## Functional Requirements

全要件の優先度はMust。受け入れ基準をGiven/When/Thenで記す。

### FR1 日付詳細から依頼

出典: [desc]、[Q1]、[Q3]。

- Given 管理者が未確定の今月または来月の今日以降の日付を開く、When 詳細を表示する、Then 臨時のお手伝いを依頼する入口を表示する。
- Given 依頼フォーム、When 使用可能な臨時用マスタと同じ家族の子供1人を選び保存する、Then 選んだ日付に未実施のお手伝いを1件保存し、日付詳細とカレンダーに反映する。
- Given 月の通常割り当てが未入力、When カレンダーを開く、Then 日付を開いて臨時依頼できる。通常割り当ての入力入口も維持する。
- Given 子供・過去日・確定済み月・今月来月以外、When 表示またはAPIへの追加を試す、Then 追加を許可せず既存データを変更しない。

### FR2 臨時用マスタ

出典: [Q2]、[Q7]、追加指示bc9d9a24。

- Given 管理者、When 家族の設定を開く、Then 通常用と区別された臨時用マスタの管理入口を表示する。
- Given 管理画面、When 名前・円単価を登録または変更し、使用する・しないを切り替える、Then 家族単位で保存し、再表示しても保持する。名前と単価の入力制約は既存のお手伝い種類の制約に合わせる。
- Given 依頼フォーム、When 種類を選ぶ、Then 使用可能な臨時用だけを選べ、単価を確認できる。通常用は臨時一覧へ混ぜず、臨時用は通常の月割り当て候補へ混ぜない。既存の種類は通常用として維持する。
- Given マスタ未登録・使用可能な種類なし・子供未登録、When フォームを開く、Then 理由と必要な登録を案内し、不完全な依頼を保存しない。
- Given 子供または別家族の利用者、When マスタ変更や参照範囲外のアクセスを試す、Then 管理権限・家族の境界をサーバー側でも守る。

### FR3 重複・競合と保存失敗

出典: [Q4]、[調査]。

- Given 同じ日付に同じ臨時種類が存在する、When 再度依頼する、Then 追加せず既存担当の変更を案内する。担当者が異なる場合や既存分が実施済みでも重複追加しない。
- Given 二重押し・通信の再送・同時追加、When 同日同種類を保存する、Then 1件だけ保存し既存分を上書きしない。
- Given 保存時に月確定・種類の使用停止・子供の所属変更・競合が起こる、When 保存処理を実行する、Then 最新の条件を検証し、失敗理由を表示する。失敗時に成功表示や半端な保存をしない。
- Given フォーム入力中、When 通信に失敗する、Then 入力を維持し再試行可能にする。取消は保存しない。

### FR4 通常割り当てから独立して保持

出典: [Q5]、[調査]。

- Given 臨時のお手伝いがある月、When 通常の月割り当てを保存・変更・再生成する、Then 臨時分の担当者・状態・金額情報を変更または削除しない。
- Given 同じ日付に通常分と臨時分がある、When カレンダーと詳細を表示する、Then 両方を識別でき、片方が他方を隠さない。

### FR5 既存の実施記録・金額・確定への統合

出典: [Q2]、[調査]。

- Given 保存した臨時分、When 担当の子供が実施記録する、Then 既存のお手伝いと同じ記録権限・日付条件・状態遷移を適用する。
- Given 臨時分がある、When お小遣い確認や月確定を行う、Then 既存の単価確定タイミング・実施状態別の集計ルールを適用し、二重計上しない。マスタ変更が確定済み金額を変えない。
- Given 臨時マスタが使用停止になる、When 過去・追加済み担当を表示する、Then 名前や記録を失わず、新規候補からのみ除外する。

### FR6 通知

出典: [Q6]。

- Given 臨時分を追加する、When 保存が成功する、Then 即時LINE通知を送らない。
- Given 臨時分が定時通知の既存対象条件に該当する、When 既存の定時通知が実行される、Then 通常分とともに含める。配信条件・通知先・回数制限は変更しない。

## Non-Functional Requirements

### NFR1 既存認証・整合性

出典: [調査]、FR1–FR5の成立条件。

家族所属・管理者権限・日付・月確定・重複の検証をサーバー側で行う。臨時分の識別と既存データの互換性を維持し、通常割り当ての保存と臨時追加の競合でも臨時分を消さない。秘密情報は保存・出力しない。

### NFR2 操作性と品質

出典: [desc]、[memory]。

フォームの項目にラベルを付け、キーボードで入力・保存・取消できる。読み込み・保存中・空・失敗を区別して表示し、保存中は重複送信を防ぐ。BDDの実行可能シナリオを実装前に用意し、要件ごとの正常系と重複・権限・確定競合などの異常系を検証する。既存テスト・lint・パッケージ別型検査・ビルドを成功させ、全体の行カバレッジ80%以上を維持する。

## Constraints

既存React/MUI、TypeScript、Lambda、DynamoDBの構成を利用する。臨時用マスタの登録内容は家族が入力し、「お昼ご飯を作る」は用途例であって固定の初期データにはしない。デプロイは既存CIに任せ、ローカルからAWSへ直接デプロイしない。

## Assumptions & Open Questions

None.

## Out of Scope

担当未定の募集・引き受け機能、依頼ごとの自由入力や単価上書き、即時LINE通知、同日同種類の複数依頼、臨時用マスタの物理削除、臨時依頼の新しい削除機能。既存の担当変更・状態変更は維持する。
