# U8（代わりにやる）の手での確かめ

U8 の動作は、スモークチェック（`scripts/smoke-check.sh`。全 23 件のまま）では確かめられません。LINE の署名つきの確かめには本物のチャネルのシークレットが要り、スクリプトにシークレットを持たせないためです。この手順書の 14 件を、**ステージング**で作り手が手で行います。

**この手順書の確かめは、まだ 1 件も実行していません。** 結果を書く欄は空です。

## 準備

- ステージング用の公式アカウントと、作り手だけのグループを使います。グループに、子供の役割のテスト用の利用者を 2 人以上（できれば 3 人。A・B・C とします）と、管理者を入れます。
- ステージングの公式アカウントを、本番のお知らせ先のグループに入れません（NFR10.9）。
- データはアプリの操作（割り当ての保存、LINE の操作）で作り、`Calendar` を直接書き換えて用意しません（NFR6.9）。本番ではテストデータを入れません。
- 値の例を書くときは `<作り物の値>` と書きます。本物の ID・トークンをこの手順書にも結果の欄にも書きません。
- ログの問い合わせの番号は `construction/u8-swap/infrastructure-design/monitoring-design.md` のものです。

## 速さの測り方（確かめ 12。NFR7.39〜NFR7.42）

1. 一覧（「家事交代」と送ってから一覧が出るまで）、担当を選ぶ、引き受ける、申し出をやめるを、**それぞれ 20 回**測ります。
2. 20 回のうち **10 回以上は冷たい起動**にします。`line` のログの `REPORT` の行に `Init Duration` があれば冷たい起動です。作り方は U5〜U7 と同じです（コードが変わる反映をするか、数十分以上待つ）。**Lambda の環境変数や設定は書き換えません**（NFR6.9）。
3. 時間は、グループのトーク画面の画面録画（1 秒に 30 コマ以上）から、送った（押した）瞬間と返事が出た瞬間の差を読み取ります。
4. 失敗した回も 1 回と数え、除きません。
5. サーバー側は `LINE_EVENT_DONE.durationMs`（95% が 2,000 ms 以内）を補助に見ます。
6. 理由つきの返事（候補なし・確定済み）は、各 3 回測ります。
7. 結果は `build-and-test` の記録に残します。基準に届かないときは、目標を下げずに原因を調べて直し、新しい 20 回を測り直します。

## 確定とフックの測り方（確かめ 13。NFR7.46）

1. 確定の前に、いくつかの担当に開いた申し出を作っておきます。
2. 担当の作り直し（割り当ての保存）がある月と、ない月を**分けて**記録します。
3. 画面録画で確定の応答を測ります（20 回、うち冷たい起動 10 回以上）。
4. サーバー側は `REQUEST_END.durationMs` と `DUTY_HOOKS_DONE.durationMs`（`count`・`failed`・`concurrency` つき）を見ます。`failed` は 0 のはずです。
5. CloudWatch で `Calendar` の `WriteThrottleEvents`・`ThrottledRequests` が測定の間 0 であることを確かめます。
6. 1 回目の確定のあと、開いていた申し出がすべて `cancelled` になり（問い合わせ 6）、開いていなかった担当に `SWAP#` の項目が作られていないことを、申し出の操作とログで確かめます。直接書き換えて確かめません。
7. 並行数（`DUTY_HOOK_CONCURRENCY`、既定 4。範囲 2〜5）を変えたら、この測り方で測り直します。
